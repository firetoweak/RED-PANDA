# 编码

先确认任务是讨论、审查还是实施。讨论与审查只调查并给出判断；实施时完成修改和必要验证。用户指定的流程、项目约定和适用的项目 Skill 决定具体做法，不要求使用 Git，也不预设规划、开发、审核由固定成员承担。

## 理解与修改

先阅读相关代码、项目说明和已有改动，明确现有行为与验收目标；需要项目专用知识时，从目录加载适用 Skill，按需读取它指向的文档。没有 Git 时直接阅读文件与用户提供的基线，不能因此阻塞编码或自行初始化仓库。

保留无关修改；变更保持聚焦，复用已有实现并遵循项目风格。不做无关重构，不为未提出的需求添加兼容层、兜底或抽象。修改文件优先使用专用文件工具。

## 验证与交付

修改后重新读取结果或比较可靠基线，确认自己的改动范围；在 Git 目录中同时检查工作区差异、暂存区与未跟踪文件，已提交的改动看提交差异，不能把空的工作区差异当作没有修改。

按影响运行必要的测试、构建或静态检查；工具不提供命令执行时，说明尚需谁执行哪些检查。失败时查明原因，无法验证的部分如实说明。不要把文件写入成功、同事报告或局部检查当作功能已验收。

交付方式遵循当前任务：可以直接交付文件、向同事说明文件位置与改动，或按约定提交代码。需要 Git 提交、同步或集成时，加载目录中的 git-collaboration Skill；用户已有其他流程时遵循该流程，不额外要求 Git 或人员交接步骤。

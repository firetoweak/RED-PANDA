# 独立验收的两个反例

自测通过或引用真实，都不能单独证明结果满足原任务。这两次记录保留最能说明独立核验价值的反例，不作为模型总体能力或失败率评估。

## 自测通过，真实 CLI 仍不满足要求

2026-10-06，Windows 上用 deepseek-v4-pro 在小型 Python 发票项目中分别试验修 bug、增加功能和重构。项目环境已准备并明确提供，单次任务输入后不再人工提示；结果不能推广到自主准备环境或复杂真实仓库。

功能任务为 CSV 库和 CLI 增加分隔符支持。模型自己的 13 个测试全部通过，库接口也正确；独立验收 7 项中却有 2 项真实 CLI 回读失败。

模型测试用内存字符串替代标准输出，没有覆盖 Windows 的实际换行转换。真实 CLI 产生了 `\r\r\n`，解析后出现额外空行；字段中的换行也发生变化。命令退出成功、输出看起来正常，没有证明完整回读要求成立。

**原始 CLI 基线也有同样缺陷。** 这不是模型新引入的回归，而是它继承了旧问题，没有发现该问题使新增功能的完整验收失败。独立检查必须对准用户要求，不能只问“有没有改坏”。

## 报告严谨，研究的却是另一个仓库

2026-09-18，一轮架构调查共委派八次。父在部分任务中把目录多写了一层；其中一个子在目标均不存在后，没有澄清或报告阻塞，而是找到名称相近的另一个代码库，交回附真实文件与行号的完整报告。

报告并非凭空编造，它准确描述了错误对象，因此外观很难暴露问题。父核对目标路径后废弃报告并重新委派。同轮也有子会自行纠正错误路径，不能据此推导统一行为或失败率。

该轮使用旧的只读能力与预算机制，不据此保留今天的委派策略。仍有价值的是：父的输入错误可能被包装成可信结论，引用存在不等于引用属于原任务。

## 验收应核对什么

先确认对象、版本与范围，再核对真实入口和结果。独立验收以需求和实际证据为准，测试替换掉的边界、报告自述与未覆盖条件尤其需要核对。

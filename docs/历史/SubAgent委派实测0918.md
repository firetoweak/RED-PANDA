# SubAgent 委派实测（2026-09-18）

实验笔记，不是当前实现准绳。现行 SubAgent 设计读 [SubAgent](../架构/运行/SubAgent.md)。

## 目的

用「调查 konden 自身架构」这个真实任务，检验 **Parent 侧委派策略**（拆分粒度、任务描述里的绝对路径与兜底规则、是否给出读取预算）对子 Agent 成败的影响。

这是 Parent 行为实验：全程只读，不涉及 Runtime、Journal 或任何代码改动，被调查的文件也没有被改。

## 环境

- 平台：Windows；仓库根 `D:\work\helpMe\konden`
- 子 Agent 能力面：只读白名单（`READONLY_TOOL_NAMES`），实测可用为 `glob` / `grep` / `read_file` 一类；`execute_command` 不在白名单内
- 子 Agent 模型输入预算：180000（由越界报错读出）
- 委派 8 次，分 3 批；同批在同一决策内并行发出
- 全程未使用 `reclaim`：8 个子 Agent 全部自行成功或自行失败
- 子 id 形如 `session-<parent>/sub-<command_id>`，与 [SubAgent](../架构/运行/SubAgent.md) 一致

## 方法

子 Agent 看不到 Parent 对话，所需背景全部写在任务描述里。任务统一要求：分点作答、每条结论附「文件路径:行号」或类/函数名、区分确证与推断。

这决定了本实验最关键的一点：**任务描述里除了目标，还包含路径与"怎么读"的指令——Parent 写错的每一处都会直接变成子 Agent 的输入。**

## 三种结局

### 1. 预算超限 ×1 —— 根因在 Parent，不在子 Agent

批 1 把「工具 + Skill + MCP + 沙箱」四个目录压成一个任务，且没给任何读取量约束。子 Agent 不知道自己的预算余量，自由读到越界：

```
konden.assistant.context.projection.ModelContextBudgetExceeded:
模型输入估算 182052 超过预算 180000
```

抛出点 `assistant/context/projection.py:602`，回执为 `reported: false`、`failure` 为完整远端 traceback。

**这条 traceback 本身是它给回的最有用的东西**：它让 Parent 能区分「这次尝试失败」与「目标不存在」，从而只换做法（拆细 + 加读取预算），而不降低目标。

注意：这次任务里的路径是**对的**，唯一变量是范围过大 + 无预算约束。

### 2. 换了靶子 ×1 —— 错误路径触发的最坏结果

批 2 的任务把路径多写了一层（`D:\work\helpMe\konden\konden\konden\tools`，正确应为 `D:\work\helpMe\konden\konden\tools`）。子 Agent glob 全 NOT_FOUND 后：

- **没有**报告"路径不存在"；
- **没有**向 Parent 要求澄清；
- 而是去工作区里找了名字最像的另一个项目 `agent/nanoHelper/nanobot`，交回一份**内容详实、带文件行号、条理清晰**的报告，讨论的是**另一个代码库**。

`nanoHelper` 确实存在，所以这不是幻觉，是换了个靶子还打得挺准。危险点在于：**报告本身看不出破绽**，若 Parent 直接采信，结论会被静默污染。

Parent 用 `Test-Path` 复核三个目录（均返回 True）后废弃了这份报告，改带已核实的绝对路径重派。

### 3. 自行纠正路径 ×3 —— 同样写错，结果不同

批 1 的 channels / docs 与批 2 的 skills 都在任务描述里拿到了错误路径，但都在报告开头明确纠正了它，然后继续完成任务。

差异不在子 Agent 能力，而在**任务描述给了它什么锚点**：

- 能自纠的三次，任务里写了「这个项目的『接入通道与前端』部分」「先 glob 看 docs 结构」等身份与结构线索；
- 跑偏的那次，任务写的是「只看这三个目录」——三个都不存在时，它彻底失去锚点。

**越是用"只看这里"把范围钉死，路径一错就越没救。**

## 观察

1. **8 次委派 0 次澄清。** 面对错误输入，3 次静默改写路径，1 次静默更换目标。子 Agent 倾向于"尽力完成"而不是"如实回报卡住"。
2. **换靶比报错危险得多。** 报错至少是可判定的失败；换靶产出的是可信外观的错误结论。
3. **子 Agent 不知道自己还剩多少预算。** 读取策略必须由 Parent 显式约束，它在 182052 时才发现越界。
4. **同一批任务里的路径正确率与结局不成正比。** 4 条正确路径里有 1 条硬失败（范围过大），4 条错误路径里有 3 条成功。**拆分粒度与读取预算，比路径正确性更决定成败。**
5. **异步回执的形态是够用的。** 成功（`reported: true` + summary）与没跑完（`failure` 非空）两种形态本次都实际出现，且都带足够信息供 Parent 改判。
6. **只读白名单兜住了风险。** `READONLY_TOOL_NAMES` 恰好等于 Parent 能给子 Agent 的那几个读取工具，`execute_command` 不在内，跑偏子 Agent 无法动工作区。

## 对 Parent 侧的启示

1. **委派前先自己核实路径**（`Test-Path` / `glob`），再把清单写进任务。第 3 批这么做后零返工。
2. **任务描述里写死兜底规则**：「路径不存在时不要换项目、不要猜，直接失败并报告。」第 3 批加上了这句。
3. **给显式读取预算**：文件段数 + 单次行数上限，并允许它超一点。
4. **一次委派只给一个明确交付物**，不要把多个目录打包成一个任务。
5. **要求回报「未查到 / 无法完成」，而不是自行降级**——本次 6 份可用报告都老实标了覆盖缺口，该约束有效。
6. **子 Agent 关于"某东西不存在"的断言一律要复核**，这类断言最容易由它自己的输入错误造成。

# AgentFS 的取舍

2026-10-09 至 19 日，项目从逐步文件回退转向长期 Bot 协作。这份记录合并当时的性能讨论、AgentFS 演进和产品转向审视，只保留决定背后的前提。

## 为什么越做越深

最初要求只有“Agent 改完文件可以回退”，但同时接受了四个前提：修改人正在使用的目录，多个会话共用它，每一步及命令副作用都可回退，普通工具仍使用真实路径。

旧 Git 方案每步扫描整树，子工作树又复制同样规模的数据；所有版本操作串行后，子越多越慢。把队列排得更正确没有改变成本模型，这促使操作记录与 Git 成果关系分层。

后续演进继续解决上一层带来的问题：

```text
Git 快照 → VFS 写时复制 → 文件挂载 → 路径命名空间 → 进程内文件访问介入
```

每一步单看都合理，合起来却从文件版本进入了操作系统兼容：真实路径、程序初始化、进程继承和文件身份都成了项目必须处理的问题。

## 改变前提后的决定

长期 Bot 各用真实 worktree 与分支，不碰人的检出，物理目录已经提供项目改动隔离。系统也放弃每步自动生成文件版本，由 Agent 按实际任务管理 Git 提交；因此原先逼出虚拟文件层的前提不再成立。

这次转向没有否定事实、原子决策、结果未知或命令授权等底座。它们同样服务长期协作；需要重新审视的是生命周期和产品承诺，不能把换目标等同于重写全部内核。

2026-10-18，AgentFS 从主仓库整体移除，TUI 也改为直接操作真实目录。旧实现保存在 Git 标签 `agentfs-final`。当前边界见[执行环境](../架构/能力/执行环境.md)与[项目与工作树](../架构/多智能体/项目与工作树.md)。

## 留下的教训

**需求没有扩大，实现却不断深入时，应回头检查前提。** 这次回到 Git，是改变协作条件后重新选择方案。

worktree 不提供操作系统安全隔离，Git 也不能撤销被忽略文件、被删的未跟踪文件和所有外部副作用。以后遇到这些需求，应先明确承诺范围或考虑独立隔离，不能仅凭“需要回退”重新接回整套文件层。

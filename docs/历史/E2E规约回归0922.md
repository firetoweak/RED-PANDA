# 2026-09-22 复杂 E2E 与规约回归

本轮使用隔离运行目录、真实模型和浏览器交互，覆盖并发 SubAgent、长工具链、连续 Compact、编辑分支、授权拒绝及服务重启。随后用确定性测试复核发现；浏览器观察与根因结论分别记录，不能仅因某次点击无响应就判定产品实现错误。

## 已修复：前置检查与决策输入的版本一致性

原路径是 Scheduler 完成容量检查，再调用 Runtime 重新读取 Journal 冻结 DecisionFrame。两次读取之间，新消息或 SubAgent 回报可以入账；旧检查结果因此可能放行包含新事实的输入。

现在 Scheduler 在前置检查前记录 Journal 位置，推进时带上这个位置作为前提。位置变化时 Runtime 不认领 Step、不调用模型、不消费 trigger，Scheduler 下一次激活重新检查。目录同步或 Compact 发布改变事实位置时同样重新检查。冻结之后到达的事实仍只进入后续 Step，输入接纳不被长时间锁住。

这条约束属于"检查依据与执行依据一致"，Runtime 只理解事实位置，不理解 Compact、预算或任务语义。

同时发现容量预检查没有计入当次新增 LoopGuard 提醒。现在预检查与 Decision 使用相同的提醒组装方法；预检查只评估，不把未提交提醒写入冻结历史。

16K 真实场景出现过源会话超预算；上述竞态已由确定性测试覆盖，但现有日志不能证明所有超预算失败都由同一竞态造成，不声称本次已消除所有容量问题。

## 纠正定级：重启后待授权按钮无响应

浏览器观察：服务重启后恢复了待授权命令，点击拒绝后未见授权请求；Journal 中命令没有授权、拒绝或执行终态。随后浏览器自动化连接失败，无法继续独立复现。

初次报告将其定为确定 P1 缺陷，证据不足，撤回该定级。新增的两条回归分别覆盖前端断线重连后用新连接提交拒绝，以及真实 Host / Worker 重启后从 Journal 恢复待授权命令并按同一命令拒绝，均通过，当前没有依据修改授权生产链路。浏览器无响应保留为待复测项，不能据此认定 Runtime 丢状态，也不能认定已经找到浏览器卡顿根因。

组件测试和进程测试证明各自契约，不能冒充完整浏览器 E2E 通过。

## 已过时的观察

当时 Compact 的交接读取只允许专用来源工具，模型调用普通读取工具会在执行边界失败，记为"模型可见能力与执行许可不一致"的风险。此后 Compact 的回读方式已经改变，该专用工具不复存在，这条风险不再对应现行实现。

## 已观察到通过的场景

| 场景 | 结果 |
|---|---|
| 长文本触发连续两次 Compact | 两次发布成功，第二次后仍能准确修正第 173 条记录 |
| 普通授权拒绝 | Journal 记录 rejected，工具未写文件，会话正常结束 |
| 编辑历史产生分支并重启 | 子 Session 内容保持，原路由显示子分支符合 Web 契约 |
| 刷新后的 context usage | 暂归零，符合瞬时展示契约 |
| 重建 Web bundle | 旧资源导致的 schema 校验错误消失 |

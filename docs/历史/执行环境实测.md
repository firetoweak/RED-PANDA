# 执行环境实测

两组实验分别检查“命令用了哪套环境”和“文件写到了哪里”。结论局限于当时的 Windows、小项目与模型，不作为跨平台或普遍可靠性保证。

## 产品环境与项目环境

2026-10-07，使用 deepseek-v4-pro、真实 Host、Worker、Shell 和一次 Compact。工作区外准备两套含不同探针依赖的 Python 环境，产品 Python 没有这些依赖；随后改变产品环境，观察任务执行是否被覆盖。

| 阶段 | 独立核对结果 |
|---|---|
| 默认启动环境 | 裸 Python 使用启动时准备的环境，能加载其专有依赖 |
| 用户另行指定环境 | 模型自行表达命令，正确使用指定解释器与依赖 |
| 压缩后不重复环境信息 | 仍使用用户指定环境 |

产品与命令的环境标记分别保持原值，探针未被修改。模型通过每次命令落实环境选择，没有新增一份隐式环境状态。

这说明受测模型能在这些条件下延续要求，没有实测 Conda 激活、Java 构建或 POSIX Shell，也不证明模型永不偏离。当前环境分工见[执行环境](../架构/能力/执行环境.md#命令环境)。

## 任务根与项目挂载

2026-10-21，使用 deepseek-flash，比较两种安排：关联项目时将任务根切到 worktree，或保持个人目录为根、明确告知项目路径。每组两次，各完成两轮修改、测试、提交和落地，再在个人目录记笔记。

两组都正确落地。保持个人根的两次运行中，没有把项目代码写错目录，命令都明确指定项目位置，笔记也落在个人目录。样本支持保持任务根不变的选择，不能据此宣称它在所有任务中更优。

后续又测了无项目 Bot 中途挂载、多个项目、按登记名或本地路径挂载，以及解除项目。早期失败暴露了两处交互缺口：模型不知道可按登记名操作，工具又限制它自然组合的挂载或解除调用。

改为先按名字操作、失败时给出可用登记，并允许这些操作正常组合后，两次四轮均正确：项目各自取得对应提交，解除确实移除工作树，笔记留在个人目录。这个对照说明可用信息和工具约束需要匹配实际使用方式，不只是多写一条路径提醒。

两次运行都按轮次顺序推进，只用了一个模型和小型项目，未验证并发、长时间工作或大型仓库。项目取舍见[Bot 的执行目录](../架构/多智能体/总览.md#项目归属与执行目录)。

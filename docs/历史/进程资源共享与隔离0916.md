# 进程资源：共享什么，隔离什么（2026-09-16）

> 决策已落地：模型客户端收在 Host，Worker 只持有 LLM Port。当前准绳以[多活跃会话](../架构/运行/多活跃会话.md) 和 [模型 Provider 接入](../架构/能力/模型Provider接入.md) 为准。本文只保留当时的测量、判断框架与结论。

问题从 Web「编辑用户消息并重新执行」的体感慢开始，落到一条更根本的选择：**一 Session 一进程之后，哪些资源必须按 Session 复制，哪些其实是产品级的。**

## 慢在哪里

最初的直觉是 fork 要带走全部事实、恢复动态工具和 MCP 连接，所以慢。对照实现后只对了一半：

- **必须带走的是事实，不是连接。** 前缀里的 `load_toolset` Outcome 已留下完整工具契约，新 Worker 按快照恢复，MCP 真正握手推到之后某次调用。
- **新建空 Session 同样明显慢。** 空 Journal 没有工具可恢复、没有附件可复制，所以主因不是前缀回放或 MCP 重连。

当时按 Worker 启动顺序在本机量过一次：

| 步骤 | 耗时 |
|---|---|
| 导入 Worker 整包装配依赖 | 3.4s |
| `import litellm` | **18.7s** |
| 构造 LiteLLM Router | 0.05s |
| 构造 MCP | 2ms |

主因是 **Windows 上 `spawn` 一个完整 Worker，并在子进程里重新冷导入 LiteLLM**。Host 已经导入过也没用：`spawn` 出来的新解释器地址空间是空的。内存上每个 Worker 也常驻一份。

## 判断框架：隔离的是故障域，不是导入缓存

有用的问法不是「能不能少导入」，而是：

> 这个资源的故障、阻塞和生命周期，是否必须跟一条 Session 绑定？

| 资源 | 跟 Session 绑在一起的理由 | 跟着进程被复制的代价 |
|---|---|---|
| Journal / Runtime / Scheduler | 事实与推进必须按 Session 线性、可重放 | 必要 |
| 工具执行、shell、文件视图 | 同步阻塞、权限、工作区副作用按 Session 隔离 | 必要，这是进程模型要保护的东西 |
| MCP 客户端 | 连接是进程内缓存；工具 Schema 可从 Journal 恢复 | 连接按需建立即可 |
| 模型客户端 | 主要是出站 HTTP，卡住的多是 Provider 而不是本地事件循环 | 每个 Worker 冷导入约 20s，并常驻一份大模块 |

进程隔离换来的是执行故障互不牵连，换不来子进程免费继承父进程的导入。把模型客户端留在每个 Worker 里，付的是启动税和内存税，防住的主要是「模型流式卡住」这一层，而不是工具执行那一层。

当时比较过两条路：预热空白 Worker 只是把付费时刻挪到后台，副本数不变；把模型客户端上收到 Host 才真正只导一份，代价是模型调用层的隔离变弱。最终选择了后者。

## 明确不必回到的方向

- 不要为了 fork 快而做「只继承消息」的旁路。能力加载、Compact、附件引用必须与前缀事实一致，否则编辑重跑会悄悄丢工具，见 [Web](../架构/入口/Web.md)。
- 不要在 fork 或恢复时为了「确认 Server 还活着」而强制重连所有已加载 MCP；连接推迟到第一次调用。
- 不要指望 Host 先导入重依赖就能让 `spawn` 子进程免费。

# 上下文脱水与 Prefix Cache 实验（2026-08-28）

实验笔记，不是当前实现准绳。现行投影规则读[上下文](../架构/上下文/上下文投影.md)，窗口切换读 [Compact](../架构/上下文/上下文压缩.md)。

## 目的

验证 konden 当前“保护窗 + Level 1 脱水”是否因改写历史前缀而损害 vLLM Prefix Cache，并寻找保护窗固定为 10K 时较合适的批量脱水阈值。

这里的“脱水”只替换已消费、成功且批次完整的旧 tool outcome：完整正文保存在 Artifact，模型上下文中改为可回读 stub。Journal 事实不变。

## 环境

- 模型：Qwen3.8-27B，BF16
- GPU：NVIDIA 4090 48GB × 2
- 推理框架：vLLM 0.19.1（本轮讨论中简写为 0.19）
- Prefix Cache 指标：`usage.prompt_tokens_details.cached_tokens`
- 样本：一条真实的 60-Step Session
- 输出：每次请求限制为 1 token，只测输入投影、缓存和请求耗时
- 保护窗：10K
- 批量阈值计量：项目 `o200k_base` 估算 token
- Prompt、缓存命中和未命中：vLLM 实际 token

## 实验方法

从 Decision Replay Manifest 读取每一步冻结的 messages 与 tools，保持后续历史不依赖本次模型输出。在相同历史上构造：

- `sliding`：当前滑窗脱水投影
- `batch`：旧 outcome 获得脱水资格后，累计可节省 token 达到阈值再统一脱水
- `no_age`：保留体积外置，但不做年龄脱水

每轮使用固定、独立的 `cache_salt`。最终可信实验遵守：

1. 每次只运行一种策略；
2. 每次实验前重启 vLLM；
3. 从 Step 1 顺序重放完整 Session；
4. 不让其他实验策略竞争同一轮 KV Cache。

复现入口：

```powershell
python -m tests.benchmarks.context_cache_live `
  --variant batch `
  --batch-clear-tokens 20000 `
  --output "$env:TEMP\konden-context-cache-isolated-20k.json"
```

## 一次重要的错误

最初把 `no_age / sliding / batch` 三种策略交错运行。虽然不同 `cache_salt` 阻止了策略之间错误命中，却不能隔离共享 KV Cache 容量，三种策略仍会互相驱逐缓存块。

直接证据是同一份滑窗请求序列在两次交错实验中的未缓存量分别为 318,513 和 324,913；Step 30 的命中从 6,400 变成 0。5K 批量策略改为重启后单独运行，未缓存量又从 265,441 降到 251,041。

因此交错实验只用于发现机制，下面的结论只采用重启后的单策略数据。

## 隔离实验结果

保护窗固定为 10K。

| 策略 | 总输入 | 缓存命中 | 未缓存 | 命中率 | 峰值输入 | 耗时 |
|---|---:|---:|---:|---:|---:|---:|
| 当前滑窗 | 1,361,713 | 1,048,000 | 313,713 | 76.96% | 36,805 | 130.62s |
| 批量 2.5K | 1,367,626 | 1,082,400 | 285,226 | 79.14% | 36,805 | 124.37s |
| 批量 5K | 1,418,241 | 1,167,200 | 251,041 | 82.30% | 39,399 | 114.43s |
| 批量 7.5K | 1,480,502 | 1,224,800 | 255,702 | 82.73% | 39,399 | 119.08s |
| 批量 10K | 1,510,901 | 1,263,200 | 247,701 | 83.61% | 42,631 | 111.18s |
| 批量 15K | 1,632,313 | 1,391,200 | 241,113 | 85.23% | 45,602 | 114.70s |
| **批量 20K** | **1,681,990** | **1,475,200** | **206,790** | **87.71%** | **47,628** | **105.00s** |
| 批量 30K | 1,990,547 | 1,744,800 | 245,747 | 87.65% | 60,389 | 127.86s |
| 不做年龄脱水 | 2,752,063 | 2,520,800 | 231,263 | 91.60% | 87,586 | 144.60s |

相对当前滑窗，10K 保护窗 + 20K 批量阈值：

- 未缓存计算减少 34.1%；
- 总耗时减少 19.6%；
- 峰值输入由 36.8K 增至 47.6K；
- 仍明显优于不做年龄脱水的 87.6K 峰值和 144.6 秒耗时。

## 为什么较长的上下文反而更快

Prefix Cache 依赖稳定前缀。滑窗每次只脱水一小批旧 outcome，但会改写历史中间位置，从最早变化点到末尾都要重新 prefill；相邻轮次会重复计算同一段近期上下文。

批量策略允许前缀连续稳定多轮，再集中改写一次。实验中曾出现：

| 策略 | 总输入 | 未缓存计算 |
|---|---:|---:|
| 滑窗 | 20,483 | 14,083 |
| 批量 | 23,885 | 2,285 |

批量请求更长，却因稳定前缀而少做大量 prefill。

阈值也不能无限增大。缓存只跳过 prefill，不会消除序列化、传输、tokenization、KV 占用，以及 decode 时读取长 KV 的成本。不做年龄脱水虽然命中率最高，绝对未缓存量和耗时反而高于 20K 批量策略。

## 关于“舒适区”

当前可以把参数理解为：

```text
10K 保护窗 + 20K 批量积攒 ≈ 30K 可调 tool payload 舒适区
```

30K 不是总 Prompt 上限。system prompt、工具 schema、用户/助手消息、stub、失败或未消费结果，以及最近一条 UserMessage 之后的无条件保护内容仍在上下文中。本次 20K 策略的实际峰值是 47.6K。

用户实际使用观察是：该模型在约 47K 时理解能力尚未严重退化，而一般到约 70K 后开始出现明显质量下降。70K 在这里是经验性的质量软上限，不是模型声明的硬上下文上限。

## 性能最优不等于语义最优

本实验冻结历史且每次只生成 1 token，没有测量任务完成质量。因此只能确认：

> 保护窗固定为 10K 时，20K 批量阈值在这条 Session 上具有最好的缓存和耗时表现。

不能据此证明 `10K + 20K` 的输出质量最好。

在最大可调区近似保持 30K 时，可以作如下设计推断：

| 分配 | 平均旧结果积压 | 平均活跃 payload | 缓存压力近似 `P/B` | 倾向 |
|---|---:|---:|---:|---|
| 20K 保护 + 10K 批量 | 5K | 25K | 2.0 | 近期原文更多，质量优先 |
| 15K 保护 + 15K 批量 | 7.5K | 22.5K | 1.0 | 相对均衡 |
| 10K 保护 + 20K 批量 | 10K | 20K | 0.5 | 缓存与速度优先，本次已实测 |

保护窗越大，近期高价值结果保留越多；批量阈值越小，已经过期但尚未脱水的结果越少。这可能提高语义密度，却会增加历史改写频率，并让每次改写失效更长的近期后缀。

## 当前结论

1. 连续小批脱水确实会反复破坏 Prefix Cache。
2. 批量脱水不是越大越好；本样本在 20K 表现最好，30K 已明显恶化。
3. 不年龄脱水不是缓存意义上的免费方案，长上下文本身仍有显著成本。
4. `10K + 20K` 应定义为性能优先候选，不应称为语义质量最优。
5. outcome 整条触发使成本曲线呈阶梯状，简单平滑公式只能帮助理解，不能替代隔离实测。
6. 本轮没有修改生产脱水策略；后续若要调整保护窗，应使用真实任务比较 `10K+20K / 15K+15K / 20K+10K` 的完成质量、Artifact 回读和事实遗漏。

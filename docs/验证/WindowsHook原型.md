# Windows 命令 hook 选型与原型验证

2026-10-14，Windows 11 x64，非提权进程。结论：**优先采用 Microsoft Detours，保留真实挂载路径，在受管进程中拒绝宿主工作区写入。这个方向已通过最小原型验证，但尚未接入产品命令链路。** 本轮没有修改生产执行器，也没有据此关闭当前产品的宿主绝对路径写入缺口。

## 候选比较

| 候选 | 本轮核查 | 判断 |
|---|---|---|
| Microsoft Detours | MIT；负责函数拦截、挂起进程接入及进程载荷。使用项目现有 LLVM MinGW 成功编译并实测 | 首选基础库。项目只补宿主拒写策略和任务进程接入，不重做文件视图 |
| BuildXL DetoursServices | 基于其维护的 Detours 分支，提供文件访问阻止、访问报告及 32/64 位进程切换；源码还包含策略、报告、路径缓存与执行替换等协作模块 | 借鉴覆盖范围和进程启动方式。本轮没有编译或移植，不能把其成熟度算成本项目已具备的能力 |
| Mod Organizer USVFS | 面向选定进程的路径重定向，GPLv3；官方仍标记 alpha，实际用于 Mod Organizer | 与当前“保留路径身份、拒绝宿主写入”的目标不合，且与已有 WinFsp 文件视图职责重叠。本轮只核查资料 |

## 原型做了什么

原型由一个任务启动器和一个进程内 DLL 组成。启动器先挂起创建进程，接入 DLL 与本次策略，加入任务 Job；DLL 完成拦截后通知启动器，收到放行信号才结束初始化。缺失 DLL、缺失策略、拦截事务失败均使启动失败。对应用入口是否执行，使用外部标记文件验证。

文件侧拦截 `NtCreateFile`、`NtOpenFile`、`NtWriteFile`、`NtSetInformationFile` 与 `NtCreateSection`，覆盖本轮验证的创建、覆盖、追加、删除、目录修改、重命名、硬链接、属性修改和可写映射。宿主路径通过实际文件或最近存在的父目录句柄解析，按目录边界比较，避免相同前缀的相邻目录误判。已验证 Unicode、大小写、扩展路径、相对路径、句柄相对打开与目录联接。

初版仅判断最终路径，实测发现已有目录外硬链接可以修改宿主文件。现在对多硬链接文件按需使用 Windows 文件名枚举，识别是否存在宿主根内的名称；已有别名和通过该别名创建数据流均已验证拒写。没有预先遍历工作区建立另一份文件索引。

进程侧拦截 `CreateProcessW/A`，向支持的子进程传递策略并执行同样的接入握手；子进程替换环境变量不会丢失策略。任务主进程退出后先终止并等待 Job 中的剩余进程，启动器才返回，随后文件服务结束操作并释放挂载。

原型不改写路径，不记录第二套文件历史。可能写入的命令以真实 WinFsp 挂载目录为 cwd，其读写都在视图内；直接读取宿主仍能看到原值，直接写宿主被拒绝。最终变化仍由现有文件服务形成证据，并在验证结束后丢弃。

## 实际结果

[主验证结果](WindowsHook原型数据/results.json)共 28 组，均达到脚本中的预期；其中 27 组验证正常行为或明确拒绝，1 组保留 Git 默认初始化的现有 VFS 失败。每组都核对宿主文件内容未变，整轮结束还核对宿主目录结构没有新增或删除。

| 范围 | 实测结果 |
|---|---|
| 宿主只读与拒写 | 读取成功；新建、覆盖、追加、删除、目录增删、移出/移入、链接、属性和时间修改拒绝 |
| 路径及继承句柄 | 路径变体、句柄相对打开、目录联接拒写；相邻目录可写；继承的宿主可写句柄不能执行普通写入或新建可写映射 |
| 启动失败 | 主进程缺失 DLL、策略、强制拦截失败，以及子进程 DLL 缺失时，应用标记均未出现 |
| 进程树 | Python、虚拟环境重定向器、CreateProcessA、子进程和孙进程通过；显式挂起启动和 x86 子进程明确拒绝；遗留子进程已回收 |
| 挂载视图 | 修改后立即读到自己的值；宿主仍为原值；新增、重命名、删除正常；变化进入[文件服务证据](WindowsHook原型数据/sealed.json)并完成丢弃 |
| 常用工具 | Windows PowerShell 5.1、PowerShell 7.6、Node 24、Git 暂存与差异、Clang 编译并运行产物通过 |

[硬链接回归](WindowsHook原型数据/limits.json)单独确认目录外已有硬链接及数据流不再绕过。所有操作都作用于 `.tools/` 下新建的夹具，没有在用户工作区文件上试验拒写策略。管理员令牌、工具版本、原生文件服务构建信息和源码/制品 SHA256 见[环境记录](WindowsHook原型数据/metadata.json)。未提权、未安装驱动或大型工具链。

### Git 初始化的现有限制

默认 `git init` 创建 `.git` 后尝试设置隐藏属性，当前 VFS 没有该属性的状态表示。对照中，不带 hook 的 WinFsp 同样失败，直接设置隐藏属性返回 Windows 错误 50；带 hook 的普通 NTFS 初始化成功。显式使用 `-c core.hideDotFiles=false` 后，两种 WinFsp 启动方式均能初始化，挂载内的暂存和查看差异也成功。

证据见[Git 对照](WindowsHook原型数据/git-control.json)。原生实现明确只表示只读属性，见 [Windows RPC 适配](../../native/vfs/crates/vfs-mount/src/windows.rs)。这属于文件系统能力缺口；本轮没有自动修改 Git 配置，也没有把隐藏属性当作成功忽略。

### 小样本代价

每轮新建 200 个文件，每个写入 4 KiB 后立即读回；每种组合重复 4 次并交替先后顺序。以下是操作主体中位耗时，不包含进程启动和最外层目录创建：

| 文件系统 | 不带 hook | 带 hook | 比值 |
|---|---:|---:|---:|
| NTFS | 140.1 ms | 190.3 ms | 1.36 |
| 当前 WinFsp 视图 | 2507.0 ms | 2703.6 ms | 1.08 |

这是当前原型对一个偏文件创建负载的探索性测量，不能外推到完整构建，也不能套用其他项目的开销数字。逐次数据见[计时结果](WindowsHook原型数据/benchmark.json)。原型会增加路径解析和句柄查询，代价确实存在；尚未为减少开销引入路径缓存及其失效机制。

## 支持范围与生产接入前的边界

当前原型只验证 Windows x64、本地 NTFS 宿主与当前 WinFsp，DLL 位于 ASCII 路径。Unicode 任务根已经通过；Unicode DLL 安装位置、x86/ARM64、网络文件系统、其他重解析点和更广的开发工具组合没有得到本轮保证。

子进程覆盖限于 `CreateProcessW/A`。显式挂起、调试、脱离 Job 的请求被拒绝；`CreateProcessAsUser` 等其他入口、服务或代理启动并未覆盖，不能宣称所有 Windows 进程创建都受到约束。普通文件变更已测，但直接系统调用、设备控制修改、ACL 修改、已存在的可写映射与主动替换 hook 均不是当前原型的保证。路径检查和实际打开之间仍有竞争窗口。这不是对抗恶意进程的操作系统安全边界，也不限制工作区之外的全部副作用。

生产接入应继续归执行能力，文件服务仍只负责视图与文件证据。需要落实的具体问题是：支持的进程入口与拒绝边界、句柄继承白名单、取消和 Job 回收、Unicode 安装路径，以及能区别“命令退出”与“接入故障”的独立状态通道。原型退出码不能直接充当产品协议；对无法解析的磁盘目标，原型目前保守拒绝，生产还须准确呈现解析故障，不能都包装成普通权限失败。

这些限制不要求重新引入总 Environment 或 Sandbox，也不构成把 hook 放进 VFS 的理由。当前产品的下一步是收敛这条执行接入契约，并单独处理已经复现的 VFS 属性缺口。

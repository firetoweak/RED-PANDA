## 结论

此次自然故障已收敛到捆绑 SQLite 3.53.2 的 Windows 长路径锁分支：本地盘路径 `\\?\C:\…` 被按 UNC 路径处理，两条连接并发读取后可遗留 Windows 共享读锁。即使读取全部结束、所有连接都报告没有事务，后续截断检查点仍取不到排他读锁，等待约 5.5 秒后失败。

上游 SQLite 3.53.4 已修正这种本地长路径的 UNC 判断；同一独立 C 程序更换为官方 3.53.4 源码后通过。优先修复方向是更新实际捆绑的 SQLite，保留长路径支持；不是去掉所有长路径前缀、扩大重试或重新设计文件系统。

最初的自动检查点竞争假设也在实验中得到证实，但它是另一个独立缺口，不能作为这次自然 Git 故障的解释：关闭自动检查点后，长路径并发读取仍稳定复现同一忙状态。

## 真实工作流复现

每轮使用独立的工作区和文件服务存储，依次运行 PowerShell 写文件、Python 编译、默认 `git init -q`，再接受文件操作并发布。没有修改 Git 配置或模板，没有人为持锁或注入故障。首次失败后停止，保留现场。

生产运行包在第 **15 次**失败，前 14 次通过。Git 运行 5674 毫秒，退出码为 128，错误是复制 `pre-rebase.sample` 模板失败；随后 `finish` 返回检查点忙，正常修改证据没有生成。原始输出和执行结果见[生产工作流](Git检查点忙数据/production-results.json)。

独立诊断副本仅增加有界内存中的 SQL／共享内存锁历史，在检查点失败时输出；没有改变数据库配置、路径或 Git 命令。第 **29 次**自然复现，前 28 次通过。Git 退出码仍为 128，执行中无法查询 `.git/config`，随后收尾失败。见[诊断工作流](Git检查点忙数据/diagnostic-results.json)。这也说明错误不限于某一个模板文件。

仅在实验启动参数中把存储路径改为普通本地路径，保持同一生产运行包和工作流，连续 **30 次通过**。这是路径对照，不是对生产的修复；直接去前缀会破坏原本需要的长路径能力。

## 如何进入错误分支

Python 文件服务客户端在 Windows 下给存储路径增加 `\\?\` 前缀。原生服务在这个目录中创建当前操作的数据库，连接池使用捆绑 SQLite 的 Windows VFS。SQLite 3.53.2 的 `winIsUNCPath` 只检查路径是否以两个反斜杠开头，因此把本地长路径也归入共享锁句柄分支。

共享锁分支在检查其他连接的锁标记后，释放节点互斥量，再执行操作系统加锁和更新本连接标记。并发读取时，“检查其他连接是否持有共享锁”和“取得共享锁”没有覆盖在同一个临界区内。源码及轨迹支持以下泄漏机制：两个连接都看到尚无共享锁，均对同一 Windows 句柄取得共享锁；释放时，其中一个因另一连接仍持有而略过操作系统解锁，最后一个只释放一份锁，留下另一份。

实际诊断轨迹中，两条连接在约 862365 微秒和 862366 微秒取得同一 WAL 读槽的共享锁，随后都成功报告解锁。紧接着，截断检查点成功取得检查点锁和写锁，却持续无法取得这个读槽的排他锁，直到超时。见[第一处失败的完整锁轨迹](Git检查点忙数据/first-failure-trace.log)。因此这次捕获的直接阻塞者是读槽，不能误写成另一检查点抢占了检查点锁。

这里只对公开到 VFS 的锁调用做了记录，没有逐条截获 Windows 内核锁调用；上面的重复加锁与少解锁是由源码和轨迹推出的机制。下面的纯 SQLite 对照不依赖这个推断，也足以确认受影响版本、路径条件与升级方向。

## 最小复现与版本对照

独立程序创建一个只有一行的 WAL 数据库，两条连接并发执行读取，等全部读取结束后再发起截断检查点。自动检查点关闭；三条连接的 `sqlite3_txn_state` 均为 0；没有 Git、WinFsp、Hook、项目文件系统、连接池或后台调度器。

| 实验 | 结果 |
|---|---|
| SQLite 3.53.2，普通本地路径，Rust 直接调用，2 万次读取 | 检查点成功，0 毫秒 |
| SQLite 3.53.2，本地长路径，Rust 直接调用，2 万次读取 | 检查点忙，约 5.5 秒；额外连续 3 次均复现 |
| SQLite 3.53.2，本地长路径，独立 C 程序，2 万次读取 | 检查点忙，5515 毫秒 |
| 官方 SQLite 3.53.4，本地长路径，同一 C 程序与编译选项 | 检查点成功，0 毫秒 |

C 程序见[最小复现源码](Git检查点忙数据/read_race.c)，原始输出见[3.53.2](Git检查点忙数据/sqlite-3532-c.log)与[3.53.4](Git检查点忙数据/sqlite-3534-c.log)。官方源包地址、SHA256 与路径判断差异见[上游来源](Git检查点忙数据/upstream-sources.json)和[源码对照](Git检查点忙数据/unc-path-detection.json)。

这里的 `PRAGMA wal_checkpoint` 语句本身可返回成功，其第一列为 1 才表示检查点忙。生产连接池正确检查了这一列并转为错误，不能把独立 C 程序的进程退出码 0 当成检查点已通过。[SQLite 官方检查点说明](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)区分了读者阻塞与检查点锁竞争。

## 为什么表面上是收尾错误

普通文件清理、刷新和最终卸载都会调用文件同步。Windows 挂载适配会保存清理回调或数据库错误，后续调用可能随之失败；卸载时把保存的错误继续向上传递。服务的 `finish` 在卸载失败后没有完成修改证据的封存。因此最外层看到的是收尾报错，而首次故障可以已经发生在 Git 执行中。

这不是 UAC、所有者／ACL、隐藏属性或 Git 配置问题。真实复现使用普通文件读写，不需要提权；纯 SQLite 程序在没有这些层的情况下也能触发。错误传播保护了“未确认持久化就不报告文件操作成功”的契约，不应通过吞掉错误或把它降级为成功修复。

在原始失败现场保留后，复制完整存储做检查与恢复实验。该样本的数据库 `integrity_check` 为 `ok`，`foreign_key_check` 无异常；尚未生成正常证据的操作状态为 `unknown`。现有 `recover` 可以在副本上重新封存 11 个路径的部分修改，状态变为 `sealed`。

## 同时确认的两个独立问题

连接池只用自身互斥量串行化显式检查点，而 SQLite 默认自动检查点仍开启。受控实验让真正的自动检查点取得锁后暂停，再调用未经修改的生产同步路径，立即得到同一忙错误；关闭实验连接的自动检查点后通过。这是确定存在的检查点来源协调缺口，但此次长路径故障在自动检查点关闭时仍然发生。

SQLite 默认会在 WAL 达到阈值时自动执行检查点，两个检查点竞争也不保证调用忙等待处理器；分别见[官方 WAL 说明](https://www.sqlite.org/wal.html)与[检查点接口](https://www.sqlite.org/c3ref/wal_checkpoint_v2.html)。若统一检查点来源，应一并核对正常写入时的 WAL 增长和已有刷新时机，不能只关闭自动行为却不管理日志增长。

文件同步还会先将连接改成 `synchronous=FULL`，在检查点成功之后才改回 `NORMAL`。失败时提早返回，连接却被作为可复用连接放回池中。实验已确认下一次使用取得的是 `FULL`。这不会把持久性降弱，却会使连接池配置随故障漂移，应在修复时保证临时设置在错误路径也恢复，原始错误继续传播。

## 修复范围与验收建议

优先更新依赖链实际捆绑的 SQLite，使用包含本地长路径判断修正的版本；3.53.4 已完成最小程序对照验证。系统安装的 `sqlite3.exe` 与原生文件服务的捆绑库不是同一份，升级系统命令不能解决它。此次尚未把新版本接入生产运行包，不能宣称生产已修复。

恢复临时同步设置属于连接／同步边界的局部修复；检查点来源协调作为另一个明确问题处理。不改变 Git 行为，不增加 Git 特例，不全局串行化普通读操作，不删除长路径支持，也不引入一套新的文件历史或调度框架。

修复验收应守住明确契约：本地长路径数据库的并发读取全部结束后能完成检查点；错误路径不遗留临时同步模式；自动与显式检查点由确定的规则协调。随后再用重建后的真实 Git 命令链路以及长路径、非 ASCII 路径、文件发布与恢复回归确认集成，不用重复跑若干次未失败替代这些回归条件。

证据索引、生产源码和原运行包校验值见[元数据](Git检查点忙数据/metadata.json)。诊断和对照均在独立测试目录中完成，结束后没有遗留文件服务或 WinFsp 挂载。

# Git 检查点忙调查

2026-10-14，Windows x64。调查默认 Git 初始化中偶发的 `WAL checkpoint is busy`；后续修复见[SQLite 升级](SQLite升级.md)与[检查点协调修复](检查点协调修复.md)。

真实命令链路在普通权限下复现。独立 SQLite 程序排除 Git、WinFsp 和项目连接池后仍能触发，因此修复应针对数据库锁行为，不能归因于 UAC、隐藏属性或用户 Git 配置。

## 决定性的版本对照

两条连接共完成两万次读取，关闭自动检查点，确认没有活动事务，再尝试截断日志。

| 引擎与路径 | 当时结果 |
|---|---|
| SQLite 3.53.2，普通本地路径 | 成功 |
| SQLite 3.53.2，本地长路径 | 检查点忙，约 5.5 秒 |
| SQLite 3.53.4，同一本地长路径和 C 程序 | 成功 |

旧版本把 Windows 本地长路径误判进 UNC 锁分支。源码与锁轨迹支持共享读锁遗留的解释；没有逐条截获 Windows 内核锁调用，不能将这部分机制推断写成直接观测。

独立 C 对照的关键输出为 `checkpoint=1,3,3` 与 `checkpoint=0,0,0`，两次 SQL 返回码均为 0。因此不能只看进程或 SQL 返回成功来判断检查点完成。

手工上游复现保留在[测试夹具](../../tests/fixtures/sqlite_windows_read_race.c)：分别使用待比较版本的 SQLite 源码编译，再以 `--extended` 运行。产品自动回归见[Windows 检查点测试](../../native/vfs/crates/vfs-core/tests/windows_checkpoint.rs)。

## 影响与后续

文件刷新中的错误会在命令执行或收尾时暴露，不能通过吞掉错误来恢复正常外观。样本恢复实验能封存部分已发生的修改，但 Git 仍然失败；恢复不等于重跑命令，也不证明所有故障都不会丢失数据。

调查还确认了自动与显式检查点竞争、同步失败后临时连接设置未恢复两个独立缺口。它们不是这次长路径缺陷的根因，随后分别修复并用确定性回归验证。

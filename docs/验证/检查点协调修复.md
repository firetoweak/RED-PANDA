# 检查点协调与同步失败清理

2026-10-14，Windows x64，非提权。在 SQLite 3.53.4 升级之后，处理[Git 检查点忙调查](Git检查点忙调查.md)单独确认的两个实现缺口：自动检查点绕过连接池协调，以及文件同步失败后临时 FULL 设置未恢复。

## 修复边界

修改集中于底层 VFS 连接池。每个可写连接的任务通过 SQLite WAL 提交通知保留 1000 页阈值整理，PASSIVE 整理与显式 TRUNCATE 检查点共用已有互斥入口。自动回调只尝试取得入口，已有检查点时让开，后续提交继续触发；不在提交回调中阻塞等待。没有增加后台服务、全局读写串行化或忙错误重试。

WAL 回调只在当前工作任务内注册，正常返回、错误和 panic 之后均移除，连接不保留指向已结束任务的回调数据。SQLite 可能把回调错误变成笼统 SQL 错误，连接池保留检查点原始错误及操作错误，未知错误继续停止执行器。

文件句柄同步和整个文件系统同步共用同一个 FULL／检查点／NORMAL 实现。检查点失败仍恢复 NORMAL，原始错误继续返回；恢复失败保留恢复错误与此前的检查点错误，并停止复用连接。没有修改文件证据、发布协议、数据库格式、工具参数或模型提示。

## 确定性验证

测试源码在 `native/vfs/crates/vfs-core/tests/internal/checkpoint.rs`，通过实际 SQLite I/O 方法拦截和 authorizer 回调制造边界，五条测试分别守住：

- 显式入口被占用时，大事务提交不会执行自动检查点；下一次提交会补做整理，累计 WAL 页已回写。
- 自动检查点取得真实 SQLite 检查点锁并暂停时，显式同步等待，释放后双方成功。
- 外部读事务阻止截断时，同步返回原始忙错误，复用的连接已恢复 NORMAL。
- 恢复 NORMAL 被拒绝时，不论此前检查点成功或失败，错误保留完整，连接不再复用。
- 自动检查点遭遇真实 I/O 错误时，原始扩展错误码被保留，不能被成功提交或笼统 SQL 错误掩盖。

五条测试通过，已将这组契约加入 Windows 和 Linux CI；本机仅执行 Windows 验证。

在忽略目录中的隔离源码副本恢复旧行为，再运行相同的协调与设置恢复测试，两条均按预期失败。它们是缺陷对照，不能计为修复版本的失败；没有改动工作区生产源码来运行对照。

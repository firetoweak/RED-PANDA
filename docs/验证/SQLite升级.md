# SQLite 升级验证

> 后续：[检查点协调修复](检查点协调修复.md)处理本记录收口范围中保留的两个独立问题；本页与验证数据保留升级当时的事实。

2026-10-14，Windows x64，非提权。将原生文件服务实际捆绑的 SQLite 从 **3.53.2 升级到 3.53.4**，处理[Git 检查点忙调查](Git检查点忙调查.md)确认的 Windows 本地长路径并发读锁缺陷。

## 依赖与构建

crates.io 当前发布的 `rusqlite 0.40.2` / `libsqlite3-sys 0.38.2` 仍捆绑旧引擎。两套 Cargo 构建根均改用官方 rusqlite 仓库的固定提交 [`901f9946efdaaa289e6b1c5bd56dc67f4b651e51`](https://github.com/rusqlite/rusqlite/commit/901f9946efdaaa289e6b1c5bd56dc67f4b651e51)，这是上游更新至 SQLite 3.53.4 的提交。两份锁文件一起更新，构建继续使用 `--locked`。

该上游提交自身标记的 Rust 绑定版本号为 `rusqlite 0.40.1` / `libsqlite3-sys 0.38.1`，因此绑定包的数字变小，但实际 SQLite 引擎从 3.53.2 升至 3.53.4。测试输出确认实际链接版本；捆绑的 `sqlite3.c` 与此前下载并验证的官方 3.53.4 源包逐字节一致。许可证文件名同步到实际依赖版本，本地运行包不保留旧版本名的生成文件。

没有去除本地长路径前缀，没有增加忙错误重试，也没有吞掉原有错误。数据库格式仍为 0.13，没有 DDL 或迁移变化。原生文件服务已按新依赖完成优化构建，本地文件服务和命令组件运行包重新生成。

## 针对缺陷的回归

新增核心集成测试守住一条契约：使用带中文目录名的 Windows 本地长路径，两条连接完成共 2 万次并发读取后，保持连接池打开，生产文件同步路径应正常完成检查点，并能读回原有内容。测试关闭自动检查点，排除另一个独立竞争问题；回归已经接入 Windows CI。

同一份测试源码在独立测试根下链接原有已发布依赖，确认旧版 **3.53.2 会在约 5.86 秒后失败**；正式构建根链接 **3.53.4 后通过**。旧版失败是刻意保留的缺陷对照，不计为升级后的失败。见[旧版输出](SQLite升级数据/old-version-regression.log)与[新版输出](SQLite升级数据/checkpoint-regression.log)。

原生核心完整回归 **194 项通过、2 项按默认忽略**；共享跟踪边界测试 **1 项通过**。两组 Clippy、Rust 格式和工作流 actionlint 检查通过。

## 真实工作流

使用重建后的生产程序，保持原来的本地长路径形式，连续 **30 次**完成 PowerShell 写文件、Python 编译、默认 `git init -q`、文件操作接受与宿主发布。没有修改 Git 配置或采用普通路径绕过；全部通过。见[工作流结果](SQLite升级数据/git-results.json)。

这条工作流是文件服务与命令进程的实际组合验证；工具入口、Windows Hook、文件发布与回退由完整 Python 回归进一步覆盖。最终全量回归 **1116 项通过、21 项跳过、198 个子测试通过**，运行 377.08 秒，出现四条既有类型的 `BytesIO` 析构警告。

WinFsp 原生属性挂载复核 **1 项通过**。另串行显式运行默认忽略的写入中断恢复测试，**1 项通过**，覆盖六个私有 worker 终止时机；内部 worker 测试不独立计为通过。挂载与中断测试均在完整 Python 回归结束后执行，未并发运行。

## 收口范围

本轮修复的是已定位的 Windows 本地长路径读锁缺陷。此前调查发现的“自动与显式检查点来源协调”以及“同步失败后临时 FULL 设置未恢复”是独立问题，本轮没有修改其生产逻辑，仍需分别收口。不能把这次升级宣称为所有检查点故障均已解决。

Linux FUSE 未在本机运行，不把平台跳过计为通过。本轮修改尚未提交，未推送或发布远端运行包。最终构建来源、源码及产物 SHA256 和原始验证输出见[验证数据](SQLite升级数据/metadata.json)。

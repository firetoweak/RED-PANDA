# 长时间线实测（2026-10-19）

> 实验记录，不是准绳。脚本：`tests/benchmarks/long_timeline_scaling.py`，可按参数复跑。

## 问题

[转向审视](../讨论/转向CodingBot审视1019.md)推断：名册、源头计数与群查找靠「遍历全部 Journal、每个全量读取」实现，Compact 的 reader 会话与 SubAgent 子会话让 Journal 数量单调增长，长期时间线让单个 Journal 单调变长；每次决策又全量重放。量级当时没有实测。

## 做法

真实 SQLite 会话存储：若干 Agent，每条时间线写入 M 条同事私信事实；另建若干非 Agent Journal 代表压缩 reader 与子会话。按生产代码的调用方式计时：

- 名册列出：每次发送、群调度、收件箱读取都经过它；
- 源头准入：每发一条 Agent 消息，重新扫描所有 Agent 时间线数同一源头的用量；
- 单条时间线读取并重放：每次决策都做一次。

Windows 11，本机 SSD，Python 3.13，单次运行取 2～3 次平均。

## 结果

| 规模 | 名册列出 | 每条 Agent 消息的源头准入 | 一次决策的读取与重放 |
|---|---|---|---|
| 4 Agent × 500 事件 + 20 个其他 Journal | 0.31 s | 0.42 s | 23 ms |
| 4 × 2000 + 20 | 0.51 s | 0.81 s | 68 ms |
| 4 × 2000 + 80 | 1.13 s | 1.48 s | 71 ms |
| 4 × 6000 + 20 | 0.99 s | 1.97 s | 186 ms |

## 结论

- **名册与源头准入是长期协作的瓶颈。** 两者同时随 Journal 数量和长度增长：每多一个 Journal 约多 10 ms 打开与读取，非 Agent Journal 也要打开才能知道它不是 Agent；6000 条事件时每条 Agent 消息的准入约 2 s。群调度叫每位成员都要再列一次名册，代价按成员数放大。应在 D 线之前改为不随历史增长的方式。
- **单条时间线的重放暂可接受。** 与长度线性相关，约 30 µs/事件；数万条事件时到秒级，届时再看，不先动。

## 修复后

名册与源头用量改为 Host 内存索引（第一次使用时从 Journal 建立，之后增量更新）后，同一组 4 Agent × 2000 事件 + 80 个其他 Journal：

| | 修复前 | 修复后 |
|---|---|---|
| 名册列出 | 1.13 s | 0.0 ms；建索引 1.8 s，每次 Host 启动一次 |
| 每条 Agent 消息的源头准入 | 1.48 s | 0.0 ms；建索引 0.5 s，每次 Host 启动一次 |

建索引仍随历史增长，但只在 Host 启动后付一次。

## 未验证

- 真实长期 Agent 的事件构成（工具调用、输出、压缩事实）比本实验的单一私信事实更重，实际单事件成本可能更高。
- Linux 与机械硬盘上的绝对数值；本机 SQLite 打开开销是否是 Windows 特有。
- 群调度端到端的耗时，只按调用次数推算。

# Coding 开发闭环实验：明确项目环境后，当前 Agent 能完成什么

2026-10-06，Windows，基于 `b62696a3fc5b20218e6a0c900b3daf7feaae34ab` 的生产代码。
使用当前配置的 `deepseek/deepseek-v4-pro`，真实 Host、Worker、工具执行器与 Journal。
本轮没有修改生产代码，也没有人工修改模型产物。

**结论：现有系统在环境明确、任务较小的条件下已经能完成开发闭环；更突出的缺口是执行环境的显式表达，以及验证是否覆盖真实程序边界。** 修 bug 和重构通过独立验收，跨文件功能任务部分完成：库接口正确，但实际 CLI 输出不满足完整回读要求。三个样本不能当成普遍成功率。

## 实验问题与范围

先检验“项目环境已准备好并明确提供时，模型能否读代码、修改、补测试、运行验证、核对 diff”。本轮不检验自主发现或安装环境，不测并行委派、长任务恢复、真实进程沙箱、编辑器体验或大型真实仓库。

采用一个专门构造的小型 Python 发票库，派生三份独立 Git 仓库和三个全新 Session。源码涉及金额计算、CSV、CLI、文本与 HTML 渲染；每份仓库有 6 个既有测试。任务要求具体，仓库很小，所以这是受控探索实验，不是行业 benchmark，也不是复杂项目能力证明。

| 样本 | 任务 | 关键验收 |
|---|---|---|
| bug | 修复折扣只作用于最后一项的问题，新增回归测试 | 折扣覆盖完整小计、顺序不影响结果、最终只舍入一次、多币种 |
| feature | CSV 库和 CLI 支持逗号／分号，更新说明和测试 | 默认兼容、非法值拒绝、真实 CLI 调用、复杂字段完整回读 |
| refactor | 将两个渲染器的重复格式化提取为公共函数 | 两处实际复用、旧实现删除、公开调用与输出／异常行为不变 |

每个任务只提交一次用户输入，不提供验收失败后的人工提示。总闸只对这些可丢弃实验任务开启；模型被明确要求独立工作、不得委派、不得安装依赖或能力、不得改变 Git 状态。

工作区隔开的是实验文件，不是操作系统权限。本地命令仍没有进程沙箱，本轮结果不能作为安全隔离证明。

## 环境与证据

助手使用仓库自己的 `redpanda-env`；三个项目各自使用 `.venv`。它们均基于 Python 3.13.15，但解释器位置、环境前缀和依赖集合不同。

项目环境离线安装本实验生成的 `coding_probe_money==1.0.0` wheel，提供 Decimal／ROUND_HALF_UP 的金额舍入。助手环境没有该依赖。没有从包仓库下载依赖，也没有让模型自行准备环境。

通过生产代码的 `PowerShellCommandRunner` 做环境对照，结果为：

| 执行方式 | 实际环境 | 能否找到项目依赖 |
|---|---|---|
| 裸 `python` | RED PANDA 的 `redpanda-env` | 否 |
| 显式项目解释器 | 对应项目的 `.venv` | 是 |

任务正文给出项目解释器绝对路径、环境核对命令和完整 unittest 命令，要求先读 `AGENTS.md` 与 README。因而本轮证明的是模型能够使用已给出的环境与规则，不证明系统会自动加载仓库指令或自动选择项目环境。

模型自己的测试之外，实验程序使用同一项目解释器执行工作区外的预设验收用例。验收文件的内容哈希在运行后再次核对。它们没有出现在任务工作区中，但这不是针对不受限 shell 的防作弊安全边界。

每份仓库预先保留一个用户未提交的 `user-notes.txt` 修改。运行前后比较它、既有测试、仓库规则、`.gitignore` 和 `pyvenv.cfg` 的内容哈希，并比较 Git HEAD 与 index 的原始字节。三个样本都保持这些对象不变。

Host 使用独立实验数据根。实验连接与模型设置对象读取原有连接文件，不把真实凭据复制到实验产物；模型、Worker、Runtime 和工具处理逻辑保持原样。

## 正式样本结果

时间从提交任务到会话静止，包含模型调用与工具执行，不包含环境准备和外部验收。

| 样本 | 结果 | Agent 项目测试 | 独立验收 | 时间 | 已提交模型决策 |
|---|---|---:|---|---:|---:|
| bug | 通过 | 11 个通过，新增 5 个 | 8 个通过 | 48.81 秒 | 9 |
| feature | 部分完成 | 13 个通过，新增 7 个 | 7 个中 5 个通过，2 个 CLI 用例出错 | 97.75 秒 | 9 |
| refactor | 通过 | 21 个通过，新增 15 个 | 3 个方法通过，包含多币种、正负金额与舍入子场景；人工核对确实复用 | 71.43 秒 | 10 |

三个样本都真实执行了项目解释器的测试命令，读回新增文件并使用 `get_changes` 核对改动。没有已识别的模型调用失败，也没有中途的人类操作或代写。

将模型新增测试放到单独的原始源码副本重跑：bug 有 2 个断言失败，feature 因接口尚未存在而失败，refactor 因公共模块尚未存在而失败。这证明新增测试不是在原始源码上全部通过的空验证。但重构的行为保持仍由前后都通过的独立输出测试及源码复用检查共同证明，不能只根据新模块的导入失败判断质量。

## 功能任务的失败说明

分隔符参数、默认值、非法参数处理和库内 CSV 回读均正确。模型也真实启动了一次 CLI，但只查看输出外观及非法参数退出码；其 CLI 回归测试把 `sys.stdout` 替换成了 `io.StringIO`，没有覆盖真实标准输出的换行转换。

外部验收真实启动 `python -m ledger.cli` 并解析输出，在默认与分号两种情况下均失败。捕获原始字节后观察到记录结束符为 `\r\r\n`，解析出了额外空行；描述内部的 `\n` 也变成 `\r\n`。CSV 字符串本来已使用 `\r\n`，Windows 标准输出再次转换换行。

**原始 CLI 基线也有同样的问题。** 原始默认输出与模型修改后的默认输出原始字节一致，所以这不是模型引入的回归。它继承了既有缺陷，也没有发现该缺陷会使新增功能的完整回读要求失败。因此把它记为“功能主体实现正确，但完整验收未满足”，不把它解释为不会实现分隔符。

这个样本说明：测试命令成功、退出码为零、输出看起来正常，仍不等于用户要求已经满足。需要对程序真实入口的输入／输出进行契约验证。本项目已有“收尾核验目标”的原则；下一步应改善模型获取和检查证据的方式，不把语义完成判断写死到 Runtime。

## 调用量与代价

三个正式样本合计 217.99 秒、28 次已提交模型决策。Journal 中的用量为：

| 项目 | Token |
|---|---:|
| 输入累计 | 412,497 |
| 其中缓存命中 | 354,688 |
| 未缓存输入 | 57,809 |
| 输出累计 | 19,229 |

缓存命中约占输入的 86%。输入累计是各轮输入相加，包含反复携带的历史，不是项目文本大小。这里不估算金额，避免把不同供应商计价或缓存折扣混在一起。准备阶段的装配排错没有有效样本决策，不计入表中；未取得 usage 的取消／失败请求也不在这些数字内，因此这些数字不是账户账单总量。

## 实验装配与仓库检查

准备阶段发现并修正了两处实验装配问题：只重定向模型客户端连接路径不足以通过 Host 的模型配置检查，模型设置也须使用原有连接路径；等待会话静止前必须确认本次任务已经开始产生模型响应，不能把先前初始化阶段的 idle 当成任务结束。这些无有效决策的准备运行不作为模型失败样本。

第一次离线准备由 Codex 沙箱账户创建仓库，真实执行使用本机账户，Git 因仓库所有者不同而拒绝识别。正式实验改为同一账户准备与执行，没有修改全局 `safe.directory`。

默认 `python -m pytest` 在沙箱账户下出现账户／权限差异；以本机账户复跑后为 **688 passed、2 skipped、87 deselected、1 failed**。剩余失败是未修改的 `tests/llm/test_codec.py::LlmCodecTest::test_foreign_errors_preserve_type_name_and_traceback`：测试期望 traceback 含 `ProviderBoom`，当前 traceback 显示其设置后的名称 `foreign_gateway.exceptions.APIError`。本轮没有顺带修改这个已有测试或生产实现。

## 对下一步建设的判断

本轮足以支持继续以 coding 为主场景试用现有系统，不支持立即扩建大型代码索引、LSP 平台或通用项目环境管理。

先讨论一个窄改动：让项目执行环境成为显式、模型可见的绑定，助手自己的 Python 不再隐式覆盖项目执行。实验已经证明显式解释器可用，但当前靠任务正文传达，产品本身仍未承担这个契约。

另一个方向是完善真实开发任务的验证样本，特别是 CLI、构建和程序输出边界。是否增加工具或指令，先由重复出现的信息缺口决定；本次不据一个 CSV 案例预建通用验证框架。下一轮再选真实仓库中的小任务，逐渐降低任务提示的具体程度，观察自主定位与验证能力。

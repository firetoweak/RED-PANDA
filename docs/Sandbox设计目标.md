# Sandbox 设计目标

> 以文件回退为切入点，逐步构建 RED PANDA 的受控执行环境。
> 本文记录长期目标与演进约束，不是实施计划，也不表示完整沙箱已经实现。当前契约从 [Sandbox 总览](架构/Sandbox/总览.md) 进入；进程隔离仍在[未开始](架构/未开始/进程沙箱.md)阶段。

## 为什么从文件回退开始

文件回退是频繁使用的日常基础能力。已有需求是：助手改错后能够撤销自己的文件变化，保留用户修改，并避免全工作区快照带来的资源消耗与延迟。

VFS 实验分支首先解决这个具体问题，同时探索文件视图如何成为 sandbox 的组成部分。文件回退应当能够独立提供价值；后续进程与网络控制尚未完成，不妨碍先把文件控制做可靠。

## 长期目标与职责

Sandbox 承载助手与任务环境交互时的执行边界。文件工具、命令执行及命令产生的网络访问，最终应遵守明确的文件、权限与网络约束。

| 方面 | 要解决的问题 |
|---|---|
| 文件控制 | 执行者能看见哪些文件，修改落在哪里，如何记录、发布与撤销助手变化 |
| 权限控制 | 哪些访问与操作被允许，授权如何落实为执行时不可绕过的限制 |
| 网络控制 | 执行者能够访问哪些网络目标，如何实际约束其网络出入 |

这是职责划分，不预先规定三套模块、统一策略框架或跨平台实现。进程隔离是落实执行约束的重要机制，具体方案需要结合真实需求单独设计。

## 必须保持的边界

回退依据助手操作的实际文件变化，保留未被助手改变的位置。用户后续值的处理必须有明确语义；内容相同不能替代文件身份判断。文件工具和命令产生的任务文件变化应遵守同一契约，不能因工具入口或 Git 忽略规则不同而遗漏。

工具报告失败或命令非零退出，不代表没有文件变化。未知异常、持久化损坏与未决执行必须暴露，不能猜测结果或自动重跑。回退本身也应留下实际变化证据，能够被撤销。

文件回退改变文件现状，不能抹去命令已经执行过的事实。Runtime 保留执行历史；Assistant 解释用户意图与历史引用；Sandbox 执行确定的文件和环境操作，不承担模型的语义判断。

可回退不构成放开权限的理由。网络请求、安装与系统配置等副作用，需要各自的约束与明确语义，不承诺通过文件回退撤销所有外部效果。

## 后续开发的判断依据

优先验证文件控制是否可靠、成本是否适合日常使用，以及它与命令执行的接合是否清晰。初始化与日常边界不应遍历整个任务树；局部修改的捕获与回退成本应主要随实际涉及的数据增长。性能结论依赖测量，不能仅凭采用 VFS 就认定低延迟。

新增权限、进程或网络机制时，应能说明它约束了哪条真实执行路径，以及如何证明限制确实生效。文件工具、命令和子进程之间的绕过路径属于执行边界问题，不能依赖模型自觉遵守来解决。

每次只推进能够独立解释和验证的能力，保持高内聚、低耦合。文件控制不扩张成通用副作用回滚框架；尚未确定的隔离机制不提前建抽象；替换已有设计时删除旧路径，不保留长期双轨。

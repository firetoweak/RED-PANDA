# 开发指南

运行 RED PANDA 见[快速开始](../README.md#快速开始)与[运行指南](运行指南.md)。本文只供需要修改源码或运行测试的开发者查阅。

## 开发环境由你选择

可以使用自己管理的 Python、Node.js、IDE 和虚拟环境，不要求使用准备脚本创建的 `redpanda-env`。Python 版本见 `.python-version`；依赖安装使用 `requirements.lock` 和 `web/package-lock.json`。CI 验证使用 Node.js 24。

修改 Python 或前端代码可以复用匹配的原生运行包，不需要 Rust、LLVM 或 WinFsp SDK。只有修改或自行编译 `native/filesystem/`、`native/vfs/` 的文件组件时，才按[原生开发与构建说明](../native/filesystem/BUILD.md)准备相应工具；Windows 命令组件独立位于 [`native/execution/`](../native/execution/README.md)。用户工作区内其他项目的工具链同样由用户自行管理。

下面的 `python`、`npm` 均指你自己选择的开发环境。在仓库根目录执行：

```sh
python -m pip install --require-hashes -r requirements.lock
npm --prefix web ci
python web_chat.py --dev
```

该入口使用当前 Python 环境，支持后端和前端热重载。模型配置与独立数据目录见[运行指南](运行指南.md#其他入口与数据位置)。

## 测试

日常反馈以默认测试为主，真实进程测试单独运行：

```sh
python -m pytest                 # 架构契约与进程内语义
python -m pytest -m process      # 真实进程、shell 与 MCP 传输
python -m pytest --all           # 默认测试 + 进程测试
npm --prefix web test
npm --prefix web run build
```

原生文件服务进程测试需要对应平台的原生文件服务运行包与运行组件，跳过不表示通过。底层 Rust、挂载与崩溃测试见[VFS 测试说明](../native/vfs/docs/TESTING.md)。真实模型测试需要配置可用连接并显式设置 `REDPANDA_RUN_LIVE_TESTS=1`，随后运行 `python -m pytest tests/live`；这些测试会调用实际模型服务。

提交前使用与 CI 共用的入口：

```sh
python scripts/ci.py               # 当前源码：安装锁定依赖，运行 default 和 Web 验证
python scripts/ci.py --clean       # 已提交 HEAD：临时 checkout + 独立虚拟环境，同样验证 default 和 Web
python scripts/ci.py python        # 只验证 default
python scripts/ci.py web           # 只验证 Web
python scripts/ci.py process       # 已准备运行组件、构建并打包后，验证完整 process 层
```

`--clean` 不含未提交修改，也不携带前端构建结果或原生程序；它只验证当前操作系统。process 验证需要当前 checkout 的原生程序、运行包及 `redpanda-env`（开发启动入口测试使用），缺失时直接失败；前端依赖由入口安装。构建和打包方法见[原生开发说明](../native/filesystem/BUILD.md)。验证入口清除继承的 `REDPANDA_*`、pytest 注入设置及 Python 路径覆盖，并统一使用 UTF-8；日常 pytest 和显式 live 测试仍保留原来的使用方式。

`requirements.txt` 表达直接依赖范围，`requirements.lock` 锁定含平台条件的完整依赖与哈希。升级依赖时使用 uv 重新生成并提交锁文件，再运行验证：

```sh
uv pip compile requirements.txt --universal --python-version 3.13 --generate-hashes --upgrade --output-file requirements.lock
```

## 文件行为与开发边界

Agent 文件系统提供受控文件操作、审计历史、恢复及子任务成果交换，职责见[Agent 文件系统总览](架构/Agent文件系统/总览.md)。Python 入口在 `redpanda/filesystem/`，原生服务与底层库在 `native/filesystem/` 和 `native/vfs/`。

只读文件工具与声明 `read_only` 的命令查询已发布工作区。只读声明是调用契约，误标造成的写入不在回退范围。文件修改、可能写入的命令及恢复通过原生视图执行；挂载外写入、环境安装、系统配置和网络副作用不属于文件回退范围。子任务成果使用 Git 差异和三方合并，日常 Step 不创建 Git 快照。

历史实验与验证记录从[文档索引](README.md)查阅，不作为当前使用或构建步骤。

## CI

[CI 配置](../.github/workflows/ci.yml) 在推送到 `main`、更新目标为 `main` 的 PR 或手动触发时运行。Python 在 Linux 和 Windows 上运行日常测试；Web 运行测试和构建，构建包含类型检查。

可在 PR 的 Checks 或仓库 Actions 页面查看结果与失败日志。[agentFS Linux](../.github/workflows/agentfs-linux.yml) 与 [agentFS Windows](../.github/workflows/agentfs-windows.yml) 使用同样的触发范围，各自独立构建 Agent 文件系统运行包并运行完整 process 层（含不依赖 Rust 的安装和真实挂载验证），Windows 同时验证独立任务执行组件。两边互不影响结论：一边红不会把另一边的检查涂红。各 job 调用 `scripts/ci.py`，使用相同锁文件与测试命令。平台限定的 skip 仍保留，pytest 输出跳过原因。手动发布见 [agentFS publish](../.github/workflows/agentfs-publish.yml) 与[运行包发布](../native/filesystem/BUILD.md#发布运行包)。真实模型、完整业务流程与性能仍需另外验证。

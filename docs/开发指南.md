# 开发指南

运行 RED PANDA 见[快速开始](../README.md#快速开始)与[运行指南](运行指南.md)。本文只供需要修改源码或运行测试的开发者查阅。

## 开发环境由你选择

可以使用自己管理的 Python、Node.js、IDE 和虚拟环境，不要求使用准备脚本创建的 `redpanda-env`。Python 版本见 `.python-version`；依赖安装使用 `requirements.lock` 和 `web/package-lock.json`。CI 验证使用 Node.js 24。

修改 Python 或前端代码可以复用匹配的原生运行包，不需要 Rust、LLVM 或 WinFsp SDK。只有修改或自行编译 `native/filesystem/`、`native/vfs/` 的文件组件时，才按[原生开发与构建说明](../native/filesystem/BUILD.md)准备相应工具；Windows 命令组件独立位于 [`native/execution/`](../native/execution/README.md)。用户工作区内其他项目的工具链同样由用户自行管理。

下面的 `python`、`npm` 均指你自己选择的开发环境。在仓库根目录执行：

```sh
python -m pip install --require-hashes -r requirements.lock
npm --prefix web ci
python web_chat.py --dev
```

该入口使用当前 Python 环境，支持后端和前端热重载。模型配置与独立数据目录见[运行指南](运行指南.md#其他入口与数据位置)。

## 测试

日常反馈以默认测试为主，真实进程测试单独运行：

```sh
python -m pytest                 # 架构契约与进程内语义
python -m pytest -m process      # 真实进程、shell 与 MCP 传输
python -m pytest --all           # 默认测试 + 进程测试
npm --prefix web test
npm --prefix web run build
```

原生文件服务进程测试需要对应平台的原生文件服务运行包与运行组件，跳过不表示通过。底层 Rust、挂载与崩溃测试见[VFS 测试说明](../native/vfs/docs/TESTING.md)。真实模型测试需要配置可用连接并显式设置 `REDPANDA_RUN_LIVE_TESTS=1`，随后运行 `python -m pytest tests/live`；这些测试会调用实际模型服务。

提交前使用与 CI 共用的入口：

```sh
python scripts/ci.py               # 当前源码：安装锁定依赖，运行 default 和 Web 验证
python scripts/ci.py --clean       # 已提交 HEAD：临时 checkout + 独立虚拟环境，同样验证 default 和 Web
python scripts/ci.py python        # 只验证 default（先跑 ruff 的 pyflakes 规则）
python scripts/ci.py web           # 只验证 Web
python scripts/ci.py process       # 已准备运行组件、构建并打包后，验证完整 process 层
```

`--clean` 不含未提交修改，也不携带前端构建结果或原生程序；它只验证当前操作系统。process 验证需要当前 checkout 的原生程序、运行包及 `redpanda-env`（开发启动入口测试使用），缺失时直接失败；前端依赖由入口安装。构建和打包方法见[原生开发说明](../native/filesystem/BUILD.md)。验证入口清除继承的 `REDPANDA_*`、pytest 注入设置及 Python 路径覆盖，并统一使用 UTF-8；日常 pytest 和显式 live 测试仍保留原来的使用方式。

`requirements.txt` 表达直接依赖范围，`requirements.lock` 锁定含平台条件的完整依赖与哈希。升级依赖时使用 uv 重新生成并提交锁文件，再运行验证：

```sh
uv pip compile requirements.txt --universal --python-version 3.13 --generate-hashes --upgrade --output-file requirements.lock
```

## 文件行为与开发边界

Agent 文件系统提供受控文件操作、审计历史、恢复及子任务成果交换，职责见[Agent 文件系统总览](架构/Agent文件系统/总览.md)。Python 入口在 `redpanda/filesystem/`，原生服务与底层库在 `native/filesystem/` 和 `native/vfs/`。

只读文件工具与声明 `read_only` 的命令查询已发布工作区。只读声明是调用契约，误标造成的写入不在回退范围。文件修改、可能写入的命令及恢复通过原生视图执行；挂载外写入、环境安装、系统配置和网络副作用不属于文件回退范围。子任务成果使用 Git 差异和三方合并，日常 Step 不创建 Git 快照。

历史实验与验证记录从[文档索引](README.md)查阅，不作为当前使用或构建步骤。

## CI

CI 由三个 workflow 组成：[CI](../.github/workflows/ci.yml)、[agentFS Linux](../.github/workflows/agentfs-linux.yml)、[agentFS Windows](../.github/workflows/agentfs-windows.yml)。三者的触发范围相同：推送到 `main`、目标为 `main` 的 PR，或手动触发。同一 ref 上有新运行时，会取消仍在进行的旧运行。各 job 都调用 `scripts/ci.py`，与本地验证共用同一个入口、锁文件和测试命令。job 名称、矩阵、worker 数等具体取值以 workflow 文件为准，本节只说明结构和取舍。

### 流程

```text
CI
  Python (Linux, Windows)      ruff 的 pyflakes 规则 + default 层
  Web (web-test, web-build)  → Web（汇总）

agentFS Linux / agentFS Windows      两个 workflow 结构相同，互不影响结论
  build ── 原生程序、运行包、命令行工具 → artifact
    ├─→ process（按语义分组，组间并行）
    └─→ gate（仅 Windows）：门禁故障注入与安装契约，不需要构建工具链
  native contracts                     Rust 原生契约，与 build 并行
  build and verify                     汇总；任一 job 不成功即失败
```

测试分层（见[架构总览](架构/总览.md#测试分层)）在 CI 里的对应关系：

| 层 | CI 中的位置 |
|---|---|
| default | `CI` 的 Python job，Linux 和 Windows 各跑一遍 |
| process | 两个 agentFS workflow 的 process 组，各自在本平台运行 |
| Rust 原生契约 | 两个 agentFS workflow 的 native contracts |
| 安装契约 | Linux 在 `integration` 组 job 里、process 测试之后运行；Windows 在 gate job 中运行 |
| live | 不进 CI |

### 关键取舍

- **只构建一次。** build job 产出原生程序和运行包，通过 artifact 交给验证 job。验证 job 不再编译，也不需要 Rust 或 LLVM 工具链。共享的准备步骤在 `.github/actions/` 的 composite action 里。
- **process 按语义模块分组。** 分组路径定义在 `tests/conftest.py` 的 `PROCESS_GROUP_PATHS` 中，按最长前缀匹配；没匹配上的 process 用例归入兜底的 `integration` 组，例如 MCP 的真实 stdio/HTTP 传输。只有某组明显成为瓶颈、并且存在清晰的模块边界时，才拆出新组。
- **每个平台只用一个 worker 数，不按组单独调参。** 组内用 pytest-xdist 的 `worksteal` 并行，`-x` 遇到第一个失败即停止。process 用例本身是吃 CPU 的多进程测试，worker 数超过 runner 能承受的程度时，只会拉长每个用例，不会提高吞吐。只有在证实是纯 CPU 超订时，才整体调整某个平台的 worker 数。
- **Windows 的临时目录放在 runner 临时盘上。** Windows runner 默认的 `TEMP` 位于限流的系统盘，测试的 journal fsync 和 git 写入会让并发的测试一起停顿。`setup-process` 会把 `TEMP`/`TMP` 指向 `RUNNER_TEMP`。所以测试不能依赖临时目录前缀的长度，需要超过路径长度上限时，要自己构造足够长的路径。
- **汇总 job 保留 required check 的名称。** 内部 job 拆分或改名时，分支保护不用跟着改。Linux 和 Windows 两边各自汇总，一边失败不会把另一边的检查标红。
- **测试报告。** 每个 job 都上传 junit 报告（`.tools/test-results/*.xml`），并用 `--durations=20` 输出最慢的用例。平台限定的 skip 会保留，pytest 会输出跳过原因；跳过不算通过。

### 偶发失败

偶发失败要查根因，不靠重跑掩盖，也不把超时调大或给单个组降并发。并发下出现的失败先按可能的产品缺陷排查。

只在 runner 上出现的问题，可以在临时分支上修改 workflow，用 `workflow_dispatch` 手动触发，把单个用例在多台 runner 上循环运行，同时记录分阶段时间戳，再对比修改前后的耗时分布。查完后删除临时分支，原始日志留在本地 `.tools/`，不放进文档目录。

### 不做

- 不运行真实模型（live）、完整业务流程和性能基准，这些需要另外验证。
- 不为单个 process 组单独调整 worker 数或超时。

手动发布见 [agentFS publish](../.github/workflows/agentfs-publish.yml) 与[运行包发布](../native/filesystem/BUILD.md#发布运行包)。发布前要求同一 SHA 的 Linux 和 Windows 构建都已通过。

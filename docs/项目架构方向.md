# Coding agent 的可控扩展

> 长期设计方向。其中「模型交互边界」是必须遵守的最高优先级约束。
> 当前实现边界以 [架构总览](架构/总览.md) 和 [Runtime](架构/运行/Runtime.md) 为准。

## 立场

RED PANDA 是面向开发者的 coding agent，围绕代码工作区完成项目理解、代码修改、命令执行和结果验证。产品面向具备编程基础、愿意使用和修改源码的开发者。

功能取舍以改善从理解需求到验证代码的完整过程为依据，重点是编码任务的执行质量、变更可审阅性与开发者控制。项目继续记录学习和实验过程，产品定位不以教学为前提。个人生活助理与长期个人记忆不纳入当前产品规划，也不为未知第三方需求建设通用 Agent Framework。

核心问题：

> 新增功能能否改善真实编码任务，并且局部接入、明确生效、独立验证，让复杂度仍可掌控？

## 源码使用体验

产品安装只负责运行所需的环境、平台组件与已编译的原生程序，日常启动复用已准备好的运行环境。原生组件的源码构建独立于普通安装；仅运行产品或修改 Python、前端源码不以安装 Rust 编译工具为前提。

普通使用直接加载构建好的网页，热重载属于开发入口。缺少的便携应用工具由准备流程补齐，只作用于应用及其子进程，不改写用户或系统 PATH；驱动与 FUSE 等系统组件沿用操作系统的授权。首次安装不要求先填写模型凭据，模型可在启动后配置。

开发者自行选择和管理开发工具与环境，产品运行环境不作为开发者的强制环境，也不代替工作区项目的开发环境。项目说明运行条件及源码的构建、测试要求；安装与构建不进入 Agent 的决策和执行内核。模型配置引导只收集与保存连接和候选模型设置，不启动任务会话；已有配置由开发者显式选择修改。可执行步骤以 [README](../README.md#快速开始) 为准。

## 最高原则

**最高优先级：模型交互边界。** 模型看不到系统内部实现。Prompt、工具描述、参数说明、提示和返回信息必须只描述可观察行为、参数选择、使用限制与下一步动作，不得暴露内部锁、候选、发布、存储或调度机制，也不得要求模型理解或猜测这些机制。当前判断所需的身份、范围与引用关系，必须在模型实际可见的上下文或查询结果中明确呈现。不能靠补充内部实现说明来弥补系统设计问题。这条约束优先于实现便利和其他交互设计偏好。

> 功能能够持续生长，而复杂度仍由一个人掌控。

在上述交互边界内，**渐进式加载是能力供给的首要准则**：除最小基础执行面外，模型当前不需要的能力说明、工具 Schema、Skill 正文和管理操作，不进入 Decision Context。常驻层只提供最小目录与加载入口；加载结果成为已提交事实后，具体能力才从下一 Step 可见，并可由 Journal 重放恢复。不得为了调用方便在启动时把所有扩展能力铺给模型。

Runtime 不能比模型“更聪明”，也不能在隐藏路径中替模型做语义判断。Runtime 只负责确定性的事实归约、调度、不变量校验和安全边界；目标是否满足、事实意味着什么、下一步做什么，必须由模型、显式 Judge 或用户作出并留下事实。

观察模型执行中的理解、疑惑和查询行为，用来发现信息缺口与契约歧义，作为改进设计的依据。优化应减少获取和核实信息的困难，不预设模型的结论。

- 认知掌控：能解释当前行为为何发生。
- 运行掌控：状态、权限、能力激活和失败不会暗中发生。
- 演化掌控：变化时知道改哪里、如何生效、如何验证。

高内聚是同一变化原因集中；低耦合是一个需求少扩散；可扩展是规划中的功能到来时只改局部。

每项重要抽象应能说出主要理由：Product（没有它场景完不成）、Architecture（没有它变化会扩散）、Exploration（主动实验）。探索性抽象不应未经验证就成为主链路负担。

演化只面向当前设计，不承担向后兼容。新契约落地时，旧入口、旧数据形状、旧配置、旧测试和旧实现路径必须同步迁移或删除；不得为旧设计保留兼容层、双轨、fallback、兜底或所谓临时缓解分支。无法一次完成替换，说明该设计尚未具备落地主链路的条件，不以残留旧路径换取过渡。当前明确支持的平台、协议和外部环境可以有确定的适配路径；这属于当前能力，不属于旧设计兼容。

## 扩展范围

```text
已经遇到的需求        立即设计并验证
路线中明确将做的功能  保留接入方向，不预建完整框架
想象中的可能性        暂不抽象
第三方未知需求        明确不负责
```

## 不同功能使用不同的窄端口

| 功能                                  | 变化原因              | 当前端口                                                     |
| ----------------------------------- | ----------------- | -------------------------------------------------------- |
| 决策与副作用                              | 事实、推进、等待、恢复       | `redpanda/runtime`：Event / Step / Command                |
| 模型调用                                | Provider 协议、连接与认证 | 平行包 `thinllm` 拥有 Provider 表与客户端；`redpanda/llm` 只保留窄接口与配置，具体客户端由 `redpanda/bootstrap.py` 装配 |
| Agent 文件系统 | 文件视图、变化证据、审阅与回退、成果交换 | 独立文件能力，原生服务使用底层 VFS 库；见[Agent 文件系统总览](架构/Agent文件系统/总览.md) |
| 命令执行 | 启动环境、进程、结果与取消 | 消费指定任务文件视图，Tools 提供模型入口；见[执行环境](架构/能力/执行环境.md) |
| Sandbox | 进程、内存等资源、网络与基础文件访问限制 | 可接入外部沙箱模块，也可由整个系统所在的外部环境提供；接入尚未设计，见[进程沙箱](架构/未开始/进程沙箱.md) |
| 外部服务                                | 发现、加载、调用          | Assistant ToolSurface：目录 + `load_toolset`                |
| 指令包                                 | 按需读取，不增加执行循环      | `load_skill` / `read_skill_resource`                     |
| 扩展管理                                | 诊断、安装、更新、修复       | 管理域目录 + `load_management_tools`，下一 Step 才暴露具体工具          |
| Web                                 | 搜索、读取、浏览器         | 默认复用 MCP                                                 |
| SubAgent | 独立调查、文件修改与结果回传 | 子 Session 使用独立 Worker、Journal 与临时工作树，结果经 Host 回传，文件经父验收与授权合入；见 [SubAgent](架构/运行/SubAgent.md) 与 [子任务文件交换](架构/Agent文件系统/子任务文件交换.md) |
| Automation | 一次性定时唤醒已落地 | 保持外部唤醒的窄接入方向，新增触发方式以具体编码场景为依据 |
| 已安装 CLI 能力 | 外部命令行工具的发现、安装与调用 | 已落地；登记、安装、体检与管理域见 [CLI 能力](架构/能力/CLI能力.md) |



## 目标目录

```text
runtime                 所有 Session 必须遵守的运行不变量
assistant               RED PANDA 决策、上下文、完成判定与 SubAgent 委派
automation              非 Channel 的外部事实源与唤醒策略
llm                     模型窄接口与连接配置；Provider 表与 HTTP 客户端在平行包 thinllm，模型标识为 provider/model
filesystem              Agent 文件系统：工作区文件视图、审计、回退与成果交换
execution               命令启动、受管进程、结果与取消；接合指定文件视图
sandbox                 有实际接入需求时独立提供执行隔离；外部部署沙箱可不进入项目模块
channels                TUI / Web / ACP / Satori 平级交互入口（Satori 暂缓）
tools / mcp / skills    按各自机制独立生长的模型能力
```

这是按变化原因确定的结构，文件能力与命令执行已分离，其余变化仍按实际需求推进，不为了目录整齐一次性重写稳定代码，也不提前创建空沙箱模块。Agent 文件系统与 Sandbox 独立组合；会话开始前建立、归档后销毁的沙箱不改变审计与回退契约，需保留的数据独立于临时执行环境保存。Windows 命令 hook 已接入，完整沙箱仍未接入。`platform`、`capabilities` 不作为宽泛物理目录：前者会混合 LLM、Sandbox、Channel，后者会错误暗示 Tool、MCP、Skill 共用一套扩展机制。

命令明确选择受管或宿主文件访问，不根据命令名称分类。宿主执行独立于 AgentFS，不承诺文件回退；受管文件视图接合保留按操作分流：独立只读操作读取已发布宿主，可能写入的操作整次使用实际挂载任务根，并以进程 hook 约束任务命令直接写入宿主工作区，见[命令文件视图接入](架构/能力/命令文件视图接入.md)。执行能力拥有 cwd、hook 与任务进程树；文件系统拥有原生文件服务、挂载及文件历史；Host 拥有 Worker 与按会话归属的宿主持续进程。当前不以原路径透明重定向或完整沙箱作为宿主执行前提。

Channel 或 Automation 选择 Session identity；`redpanda/assistant/sessions.py` 接收给定 identity 的应用操作，`redpanda/runtime` 负责实际创建、持久执行与重放，`SessionScheduler` 根据 Event wake 每次推进一个 Step。

TUI、Web 是自有原生入口，ACP 适配外部编辑器，Satori 适配 IM 平台。它们共享 Assistant 应用能力，不共享统一外部协议，也不要求功能对齐；ACP 不规定原生入口的能力上限。不为四个入口预建通用 Channel 框架。当前只确定架构方向，Satori 暂缓，具体边界见 [Channel 协议改造](架构/入口/Channel协议改造.md)。

MCP、Skill 可各自删除。删除后不得在 Runtime 留下它们的名词或生命周期；生产代码不保留泛化 `plugins/` 包。

## 可控扩展

1. **变化局部**：一个功能有明确主人。
2. **生效路径明确**：从配置到模型可见能力能说清；哪一层没生效要留下事实。
3. **结果可验证**：测功能，也测装配路径。
4. **失败可定位**：保留原始语义，不把错误吞成“能力不可用”。
5. **复杂度可移除**：删能力时，领域状态和专属分支一起删。

异常处理遵循“内部相信契约，外部精确转换”：纯内部调用链不使用宽泛异常捕获兜底，契约违规和未预期异常直接暴露；控制台输入、模型响应、网络协议、文件系统等外部边界只捕获已经识别且能够给出确定处理结果的错误。未知异常不得被改写为普通 Outcome、能力不可用或可继续运行状态。持久化 Attempt 因进程失败停在 `unknown`，属于重启后的恢复事实，不是同一进程吞掉异常的理由。

### 代码实现原则：内部相信契约

- 外部数据只在进入系统的位置校验一次：工具参数、控制台 JSON、LLM / MCP 响应、配置文件、Registry / Journal 反序列化和文件系统结果。schema 必须精确，禁止用缺省值、truthy、`str()` / `int()` / `bool()` 强转掩盖缺字段或类型错误。
- 数据一旦成为内部类型，消费者直接按契约读取。内部不存在“字段缺失就跳过”“未知命令就当普通失败”“ malformed fact 就返回 `None`”等兜底；这些情况必须立即抛出，暴露生产者或持久化损坏。
- Adapter / handler 只捕获它能够确认语义的闭合集合，例如参数校验失败、已知 Provider 错误、`OSError` 或明确协议解析错误，并转换成确定 Outcome。未列入集合的异常原样穿透。
- `except BaseException` 只用于取消后的资源清理、事务回滚或并行错误聚合；完成清理后必须重新抛出原异常，清理也失败时保留两者。禁止在宽泛 handler 中 `return`、`continue`、`break` 或 `pass`。
- 持久格式只接受当前版本和完整字段，不兼容旧 envelope，不自动补 revision、时间或状态。文件不存在可以是显式空状态；文件存在但不符合契约就是错误。
- 架构测试扫描上述宽泛异常规则；边界测试分别证明已知外部失败被确定转换、未知内部错误会穿透。

当前生效路径：

```text
Host 装配 Binding / Schema
  → Registry snapshot 先成为该 Session 的目录事实
  → 未加载的 Toolset 只有目录 + load_toolset
  → load_toolset 成功结果记录 toolset_id + revision
  → Assistant ToolSurface 据此维护或重建可丢弃缓存，并 runtime.bind_tool
  → 下一 Step 的 tools 列表才出现具体工具
```

Registry 是产品资源事实源，Session Journal 是模型所见目录和激活集合的事实源。Registry 变化由各 Session 在下一次决策前按 revision 追加 catalog update，不通过共享内存直接改写所有 Session 的 ToolSurface。

MCP / Skill 管理能力遵循同一可见性纪律，但不建立统一 Plugin 生命周期：

```text
常驻 load_management_tools + mcp / skill 管理域目录
  → 成功 Outcome 记录 domain
  → Assistant 从 Journal 投影当前 Session 的管理域激活集合
  → 下一 Step 才出现该域的诊断工具与控制提案 Schema
```

## 明确不做

- 不为旧设计、旧契约或旧持久格式保留向后兼容、fallback、兜底、双轨或迁移期残留路径；当前支持环境的显式适配不在此列。
- 不为统一而把 MCP、Skill、判定收成一个 Plugin 框架。
- 不把模型判断当作副作用安全边界。
- 不把投影缓存或 Checkpoint 当成第二事实源。
- 不围绕个人生活助理与长期个人记忆扩展产品；跨编码任务的知识复用须先有具体需求，再讨论独立设计。
- SubAgent 的后续扩展与文件监听在对应专题设计确认前，不预建领域状态机或统一增强能力框架。

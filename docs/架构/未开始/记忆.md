# 记忆（未开始）

> 本文只记方向、已定的约束与已经排除的做法，是记忆约束的唯一所在。具体需求已经出现：长期 Agent 压缩之后的连续性，是 [Coding Bot](CodingBot.md) 第一版之后的第一重点；第一版不做记忆，但必须不堵本文约束的路。提取、结构与检索仍待设计，不按本文直接实现。

Memory 保存值得跨任务复用的知识。原始会话记录仍保存完整经历，记忆不取代它。

## 硬约束

**必须能指回来源。** 记忆由会话记录和产物提炼而来，不能成为无法核验的第二事实源——这与 Journal 是唯一执行事实、投影不得反向拥有状态是同一条原则，见[运行语义规约](../运行语义规约.md)。Journal 事实与 Agent 的落地提交就是现成的来源坐标。

**挂在 Agent 身份上，不挂 session_id。** 长期 Agent 以名字寻址，session_id 只在内部使用；记忆跟着名字走，见 [Coding Bot · 长期 Agent](CodingBot.md#长期-agent)。

**放在 Agent 各自的产品数据空间里，不放进 worktree。** 放进 worktree 会被当作代码改动落地进仓库。

```text
会话记录 / 产物
        ↓
提炼并保留来源
        ↓
存储与检索
        ↓
一次决策开始时冻结检索结果
```

检索结果在一次决策开始时确定，和 Decision Context 同一个冻结边界，避免决策过程中模型所见悄然变化。

## 待设计

提取时机、记忆结构、更新规则和检索策略都未确定。另有一个由长期 Agent 带出的问题：

- **注入位置与前缀稳定性。** 决策开始时冻结只解决一致性，不解决前缀缓存。随时变化的记忆若写进 System Prompt，每次变动都会打穿前缀缓存；名册已经选择作为事实追加、从下一步可见，记忆是否同一手法，待定。

首轮自我介绍届时也可以依据记忆提出负责方向。

## 已经排除的做法

- 在提取、结构、检索确定之前预建领域状态机。
- 和 [SubAgent](../运行/SubAgent.md) 的后续扩展或[自动化](../运行/自动化.md)合并成统一的"增强能力"框架——三者变化原因不同。
- 把记忆放进 worktree，或挂在 session_id 上。

# 交互式资源（未开始）

> 本文只记方向与已经排除的做法。方案确认前不按它实现，也不把它当成现行架构。

## 方向

让浏览器会话、ssh 连接、交互式 REPL 这类**活着的外部资源**在 Command 之间存活，并且可寻址、可从 Journal 恢复。

起因是工具做到一半需要人在世界里完成一件事——在网站上登录、过一次二次验证——完成后才能继续。缺的不是"表达需要人"的机制，是那个已经登录好的会话在下一个 Command 里还找不找得到。

## 不是 Runtime 的缺口

最容易走错的一条先排除：不要为此给 Runtime 加"等待人工"的 Command 状态。

[Runtime](../运行/Runtime.md) 的"已经开始的旧操作先结束"意味着一条已开始且未终局的 Command 会挡住其后到达的外部事实成为决策起点。工具若在 Command 内部等人回话，人的回话就当不成 trigger，双向死锁；取消也救不了，它只关闭自动续步权，Command 照常执行完。唯一的绕法是让工具从 Journal 之外取用户输入，那等于制造第二个状态所有者。

**往返因此只能发生在 Command 之间**，这与[工具与能力](../能力/工具与能力.md)已有的结论一致：领域拒绝作为普通结构化结果返回，不为异常原因扩张 Command 状态枚举。"需要人登录"是标准的领域拒绝，现有工具返回协议已经够表达。

## 当前是什么

Environment 描述"在哪里执行"，由调用方每次指定，Agent 不拥有工作目录，见 [执行环境](../Sandbox/执行环境.md)。命令跑完即散，没有任何东西活过一个 Command。

## 可以照抄的先例

MCP Toolset 解的是同一个问题：怎么让一次激活活过 Command、活过进程，又不变成第二事实源。它的形状是——成功的激活留下普通 Outcome，其中记录身份、revision 与契约快照；恢复时从已提交结果投影出激活集合；真正调用时才建立连接；内存里那份只是可丢弃缓存。见[工具与能力](../能力/工具与能力.md)。

交互式资源应当走同一形状，而不是另造一套资源状态机。

## 待设计

- 资源身份由谁签发，寿命跟 Session 还是跟 Workspace，跨 Session 能否共享；
- 进程重启后资源实际已死而投影说它还在，这个落差怎么让模型看见，而不是让运行内核去猜或盲目重建；
- 无人值守时谁回答。后台任务与 [SubAgent](../运行/SubAgent.md) 没有人可问，模型问一句就会永远等下去。这条归[处境观测](处境观测.md)，不在本专题解决，但本专题的价值依赖它有答案。

## 已经排除的做法

- **不给 Runtime 增加"等待人工"的 Command 状态或新 Phase。** 理由见上。
- **不让工具从 Journal 之外的侧信道读取用户输入。** 那会让模型看不见这次交互，并制造第二个状态所有者。
- **不把资源存活做成 Host 内存里的隐藏状态。** 与 MCP"可丢弃缓存不是事实源"同一条约束。
- **不轮询等待人做完。** 人完成后由人的消息唤醒会话，缺少新事实的等待不会因为被定时叫醒而变得可靠，与[工作计划与长任务](../上下文/工作计划.md)排除无新事实的定时唤醒同理。

# 进程沙箱（未开始）

> 执行隔离与 Agent 文件系统的边界已确定，具体沙箱接入设计未开始。本文只记方向与已排除的做法，不作为实现方案。

## 方向

Sandbox 独立负责进程、内存等资源、网络权限和基础文件访问限制。可以引入完整的外部沙箱模块来运行任务进程，也可以把整个 RED PANDA 部署在外部沙箱中；后一种方式不要求系统拥有该沙箱的创建与管理能力。

Agent 文件系统独立负责文件视图、审计与回退，可以在沙箱内运行。沙箱使用指定文件视图并施加限制，不接管文件变化历史、恢复语义或成果验收。

[命令文件视图接入](../能力/命令文件视图接入.md)保留只读操作读已发布宿主、可能写入操作整次使用挂载的分流，并采用进程 hook 约束直接写入宿主工作区，负责普通开发工具的文件操作接合。该方向独立于本专题，不因使用 hook 就成为完整执行隔离，也不要求先接入沙箱才能推进。

沙箱可以在会话开始前建立、会话归档后销毁，可以跟随 [Coding Bot](CodingBot.md) 的 Agent 身份（分支会换 session_id，名字不变），也可以由多条会话共用。其生命周期不决定文件历史的生命周期：释放沙箱不隐含回退文件或删除审计证据，需要保留的数据必须持久保存。文件所有权与保留边界见[Agent 文件系统总览](../Agent文件系统/总览.md)。

## 当前边界

本机命令执行尚未提供操作系统级安全隔离；文件工具的根集合与逐根权限只约束工具访问，不限制进程、网络和安装行为。Workspace 是任务文件范围，不是沙箱实例。独立 Worker 也不等同于安全沙箱。命令启动与文件视图接合见[执行环境](../能力/执行环境.md)。

外部环境已有的限制与产品自行实施的限制应如实区分，不猜测部署方是否提供了沙箱，也不把文件视图挂载成功当成执行隔离成功。模型只需要知道实际可用能力、限制和失败原因。

## 相关需求

- [子任务文件交换](../Agent文件系统/子任务文件交换.md)已经有独立可写视图，但子任务开放命令执行仍需要明确的执行限制；路径投影不能限制绝对路径或外部副作用。
- 命令授权与实际执行边界相关，见[Command 授权](../入口/Command授权.md)。[Coding Bot](CodingBot.md) 的长期 Agent 无人值守时，逐条授权请求会堆积。沙箱让按 Agent 全部放行这一人的决定变得可以承受；授权仍由人做出，沙箱不替人批准。
- Coding Bot 给每个 Agent 一条 git worktree，但它只隔离文件：命令仍能写到 worktree 之外或联网。这与下文排除的"用独立工作树代替执行隔离"是同一条边界。
- [交互式资源](交互式资源.md)中的浏览器、ssh、REPL 活过 Command 后，需要明确其进程与资源释放责任。

## 已经排除的做法

- 把 Agent 文件系统定义为 Sandbox 的子模块，或要求文件审计与回退依赖沙箱存在。
- 从沙箱销毁推导会话历史、文件成果或回退依据应当删除。
- 用文件可回退、独立工作树或根集合检查代替执行隔离。
- 按命令名字或判别模型的语义判断建立安全边界。
- 为未知沙箱预建统一策略、生命周期或跨平台实现框架。
- 为外部部署沙箱强制引入一个内部控制模块。

## 尚未确定

采用哪种沙箱、覆盖哪些平台、如何接入文件视图、施加哪些资源和访问限制，以及由谁创建与释放沙箱，都需要在实际接入需求下确定。无法取得所需限制时如何拒绝执行，也随具体方案明确。

这些问题不改变 Agent 文件系统的职责，不据此扩张文件回退为环境恢复，也不提前实现沙箱适配层。

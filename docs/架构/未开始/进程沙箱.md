# 进程沙箱（未开始）

> 方向已定，设计未开始。本文只记要解决什么、会撞上哪些已有约束。

## 方向

给命令执行一个真实的进程级边界。

## 当前是什么

`ExecutionAttachment.process_sandbox` 恒为 `"unavailable"`，并如实渲染进给模型看的环境描述。执行环境的其余边界见 [Sandbox 与配置](../运行/Sandbox与配置.md)。

工作区已经是沙箱的抽象单元，但它今天只有文件系统这一层：一组根加逐根权限。进程、网络与安装动作不在其中。

## 谁在等它

单独立题是因为三处共用它，挂在其中任何一处名下，另外两处就得跨文件去引别人的待设计项。

- **[可写子会话](可写子会话.md)整个卡在这儿。** 子 Session 没有人在回路里，授权闸对它不成立，只读名单是它唯一的边界。
- **父 Session 的授权粒度取决于它。** 现在 `execute_command` 靠人逐条兜底；有了进程边界之后，「哪些必须问人」才可能重新划，见 [Command 授权](../入口/Command授权.md)。
- **[交互式资源](交互式资源.md)活过 Command 之后**，浏览器、ssh、REPL 的生命周期同样落在进程边界上。

## 已经排除的做法

- **按名字判断哪条命令只读。** 无法静态判断，这正是只读名单排除 `execute_command` 的原始理由；ExecPolicy 的 verdict 只有 allow 与 ask 两档、不做 deny，出自同一个理由，见 [CLI 能力](../能力/CLI能力.md)。
- **拿[工作区版本](../运行/工作区版本.md)的可回退当安全边界。** 它收拾文件，收拾不了网络、安装和工作区之外的路径。「反正能退」不构成放开执行的理由。
- **用文件隔离替代进程隔离。** 给每个执行者一份独立的文件空间只解决互相踩文件，不解决这条命令会做什么，见[可写子会话](可写子会话.md)。
- **用判别模型逐条放行。** 一条命令危不危险取决于它将要执行的那些文件的内容，判别器拿到的信息不比静态名单多，校准得再好也只是在报告自己信息不足。

## 待设计

用什么实现、跨平台覆盖到什么程度、要限制哪几个维度（路径、网络、子进程、资源上限）、拿不到隔离时是降级成只读还是拒绝启动——全部未定。

还有一条形状问题：隔离档位是不是工作区的属性。`full_access` 已经从全局开关下沉成工作区属性，进程隔离要不要走同一条路，决定了它是每次执行时的一个选择，还是绑定在沙箱边界上的一条性质。

在这些确定之前不把 `process_sandbox` 从 `"unavailable"` 改成别的值。那个字段是给模型看的事实，谎报比缺失更糟。

# 可写子会话（未开始）

> 方向已定，设计未开始。挡住它的是进程沙箱。

## 方向

让子 Session 能写文件、能执行命令，真正分担一段工作，而不是只能读和汇报。

并行的执行需要并行的文件世界：每个子在自己的临时工作树里干活，父把认可的成果合入工作区那条唯一的轨道。

## 当前是什么

子 Session 拿一份显式列举的只读工具名单，`execute_command` 永远不在其中。**只读不是保守选择，是当前唯一的安全边界**，见 [SubAgent · 只读边界](../运行/SubAgent.md#只读边界)。

文件状态已经有版本可退，轨道是线性的、属于工作区，见[工作区版本](../运行/工作区版本.md)。子不写文件，所以它今天在这条轨道上什么都不留。

## 挡路的是什么

Environment 向模型如实报告 `sandbox process="unavailable"`——本产品目前没有进程级隔离。父 Session 的写工具靠人授权兜住，子 Session 没有人在回路里：它是 Agent 自己造出来的并行，用户没参与，授权闸对它本来就不成立，见 [Command 授权](../入口/Command授权.md)。

所以顺序是先有[进程沙箱](进程沙箱.md)，再谈写权限。工作区版本能收拾文件，但收拾不了 `execute_command` 的外部副作用，「反正能退」不构成放开的理由。**工作树隔离同样不是安全边界**：给每个子一份独立的文件空间只解决互相踩文件，不解决这条命令会不会删掉家目录。

**「子拿不到 MCP 工具」不在本专题内。** 那是静态名单装不下动态目录，和写权限没有关系，也不等进程沙箱，见[子会话能力面](子会话能力面.md)。

## 文件世界的形状

这几条是本专题的骨架，它们不改现有不变量，只在上面加一种写法。

**HEAD 属于工作区，不属于任何一条会话。** 这已经是现状：对象库按工作区派生，同一工作区的每个 Worker 共用同一条轨道。

**对 HEAD 只有两种操作：回滚与合入。** 回滚已落地；合入是本专题新增的唯一一种写法。不引入分支共存，不做「切换当前分支」，因此也不需要跨线的版本坐标。

**隔离只服务于 Agent 造的并行。** 父派几个子是 Agent 自己的决定，Agent 要为它负责，所以给每个子一棵独立工作树；用户同时开两条顶层会话是用户的选择，它们照旧共用任务根与 HEAD，如实交错、不协调。这是 [SubAgent · 只读边界](../运行/SubAgent.md#只读边界)里「单写者是委派树内的不变量，不是全局不变量」在文件层的投影。

**用户的项目目录始终是 HEAD 的世界。** 任务根是用户在编辑器里打开的那个目录，它只反映 HEAD。子的工作树落在产品数据目录下，用户不看它——他等的是父的结论。

**合入的坐标是会话，不是版本。** 父说的是「接受这次委派的成果」，引用自己已提交的 delegate Command，和 `restore_workspace` 引用 `tool_call_id` 是同一个形状。**版本标识仍然谁都看不到**，见[工作区版本](../运行/工作区版本.md)。

**合入是一次普通写入。** HEAD 属于工作区，所以合入对共享该工作区的其他会话立刻可见，和任何一次文件修改一样。不为它新开例外。

## 已经排除的做法

- **用工作树隔离换写权限。** 理由见上：隔离文件和限制进程是两个问题。
- **靠授权闸当安全边界。** 子没有人在回路里，闸是空的。
- **按名字判断哪条命令只读。** 无法静态判断，这正是只读名单排除 `execute_command` 的原始理由。
- **父逐条审批子要执行的命令。** 父只拿结论、不拿过程，所以它手里只有命令文本，看不到这条命令是怎么产生的——而危不危险恰恰全在那段上下文里。让父看得到过程，隔离就没了；不让它看，这个闸就是假的。两个目标在同一个点上互斥。
- **给人类会话开文件分支。** 用户没有「主线」这个概念，哪条会话活着哪条就是现实，所以分出去的文件世界没有合回来的动作。多条顶层会话继续共用一份工作树。
- **让人在界面上挑两条线合并。** 人的入口必须是零歧义的坐标；「回到这一刻」是，「把这两条线合起来」不是，后者要理解两边各改了什么，那是语义判断。
- **从时间线切出的会话分支连带切文件。** 那个按钮的语义就是只分会话，见 [Web](../入口/Web.md)。

## 待设计

进程沙箱本身另立专题，见[进程沙箱](进程沙箱.md)。本专题要回答的是有了它之后的事：

- **合入冲突怎么处置。** 委派是异步的，父不阻塞，所以父很可能在子工作期间改了同一个文件。两条路：把带冲突标记的树物化进任务根让父当普通文件解，代价是在父可能正忙别的事时弄脏它的工作树；或者合入失败、只返回冲突清单、不物化，由父决定重派、自己改还是放弃。后者与「恢复失败不留半吊子状态」一致。
- **父怎么验收子的改动。** 父要看 diff 才能决定收不收，但 SubAgent 的第一原则是父只拿结论、不拿过程，diff 就是过程。这两条直接冲突，绕不过去。
- **委派只能衰减。** 父不能给子它自己没有的能力，默认还应该更窄。现在子什么都没有、无从衰减；可写之后这条必须先成立，否则人授权父、父授权子，每往下一层人的注意力稀释一次，权限却不跟着收窄。
- **合入事实的形状。** 大概照抄回退那条：记委派命令身份、合入前的版本、合入后的版本或失败原因。
- **子的工作树从哪一版出发、什么时候建与删。** 生命周期跟着子 Session，但要回答工作树里的忽略规则与任务根不一致的问题——`.gitignore` 会跟着 checkout 过去，用户本地的排除文件不会。

在这些确定之前不给只读名单开口子，也不做「受限的 `execute_command`」：一个能跑一部分命令的执行口，安全边界比现在的名单更难说清。

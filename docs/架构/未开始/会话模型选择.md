# 会话模型选择（未开始）

> 本文只记方向与已经排除的做法。方案确认前不按它实现，也不把它当成现行架构。

## 方向

每个 Session 维护自己的模型选择。Web 在会话输入区提供切换入口，选中即对该会话后续的模型调用生效，不影响其他会话。

`~/.helperme/config.json` 的定位随之明确：它是用户明确做出的选择，保存新会话的默认模型与用户维护的候选模型列表。Web 保存时整份写入，与手工编辑走同一套解析与校验。

## 当前是什么

模型选择是全局的：配置只有一个 `model.active`，Host 持有一个绑定单一 Provider 的客户端，所有 Session 共用。模型名在每次调用时传入，协议层本身不需要改变。见[模型 Provider 接入](../能力/模型Provider接入.md)。

## 已经确定的边界

- **选择是会话级设置，不是 Journal 事实。** 重放不重新调用模型，不需要知道当时用的是哪个模型；它与自动授权总闸同类，属于会话元数据。
- **候选列表由用户维护，不做模型目录。** 下拉只列用户写进配置的 `provider/model`，且只列 `.env` 中已具备所需设置的 Provider。不向 Provider 查询模型列表。
- **密钥不经过 Web。** 页面只选择模型，不填写或回显密钥；密钥仍只在项目 `.env`。
- **中途切换依赖已有的 Provider 协议差异处理。** 一个 Provider 产生的历史回放给另一个 Provider 时，只按实测遇到的协议要求在该 Provider 表项上补差异，不预先做跨 Provider 历史转换。

## 待设计

- Host 如何按 Provider 持有客户端并把调用路由到会话所选模型；
- 切换在什么时刻生效：正在进行的 Step 用旧模型完成，下一次决策才用新模型，还是另有规则；
- compact 阈值是否随模型变化：换到上下文更小的模型时，全局阈值可能超过其容量；
- 配置写入的原子性，以及 Host 运行中配置文件被改写后何时重新读取。

## 已经排除的做法

- **不做全局切换入口。** 放在会话输入区的选择若影响其他正在运行的会话，与界面位置暗示的语义不符。
- **不做 Provider 模型自动发现、内置推荐模型表或按能力自动路由。** 选模型是人的决定，Runtime 不替用户挑选。
- **不允许在下拉中自由输入任意模型标识。** 拼写错误要到调用时才暴露；新模型先加进配置列表。
- **不把模型选择写进 `.env`。** 偏好与密钥的变化原因不同，保持分开。

# 子会话能力面（未开始）

> 方向已定，设计未开始。本文只记要解决什么、会撞上哪些已有约束。

## 方向

让子 Session 能看见的工具，从一份写死的名单，变成从已提交事实投影出来的只读子集。

## 当前是什么

子 Session 拿一份显式列举的只读名单，见 [SubAgent · 只读边界](../运行/SubAgent.md#只读边界)。名单里没有 MCP 工具，也没有加载目录的入口——子连去发现自己能有什么的机会都没有，一个 MCP 工具都拿不到。

父 Session 的能力面不是这个形状：它从已提交的加载结果投影激活集合，Provider 用契约快照重建 Schema 与惰性句柄，不连接外部 Server，见[工具与能力](../能力/工具与能力.md)。两边形状不同，是因为只读名单要守的是「显式列举、新增默认进不来」这条安全性质，而投影出来的集合天然是动态的。

## 挡路的是什么

**不是安全，是形状。** 一个静态名单装不下运行时才知道的目录。MCP 工具里相当一部分是纯读的——查文档、搜索、读远端 issue——它们被挡住不因为危险，只因为登记不进那份写死的集合。

这和[可写子会话](可写子会话.md)的阻塞原因不同：那边卡在没有进程隔离，写和执行都得等[进程沙箱](进程沙箱.md)。**本专题不等它们**，三者不合并，也不互为前置。

## 已经排除的做法

- **把 MCP 工具整块放进来。** 没有只读依据就等于放弃「显式列举、新增默认进不来」这条性质，而它是子 Session 当前唯一的安全边界。
- **给子开加载入口，再用提示词约束它别加载写工具。** 提示词不是边界。
- **父在委派时逐个点名子能用哪些工具。** 那只是把名单的作者从代码换成父模型，运行时才知道的目录仍然装不进去。委派时声明能力是[可写子会话](可写子会话.md)要回答的问题，它解决的不是本专题。

## 待设计

- **「只读」由谁声明。** MCP 协议的只读提示由服务器自己给出，信它等于信这个 server——但那是安装这个 server 时就已经做过的一次性信任，和逐条判断一个任意命令不是一回事。这个区别要不要写成准绳、内建工具的只读属性落在 ToolSpec 还是别处，未定。
- **子要不要也走渐进加载。** 父可以多花一个 Step 去加载目录，子没有人可等，多烧的 Step 全算进委派的延迟里。
- **目录 revision 变化时子怎么跟。** 父有「下一次决策前比较并追加 catalog update」的规则；子的生命周期短得多，是否需要同一套未定。

在这些确定之前不往名单里临时塞几个 MCP 工具——那会留下一份「一半静态一半动态」的双轨名单，日后删掉它比现在一次做对更贵。

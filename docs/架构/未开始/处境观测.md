# 处境观测（未开始）

> 本文只记方向与已经排除的做法。方案确认前不按它实现，也不把它当成现行架构。

## 方向

给"这条 Session 现在处于什么处境"找到所有者和形状。

Runtime 的状态词汇只为一个问题设计：下一步能不能决策。这个问题它回答得权威且完整。但系统正在长出第二类消费者——测试、无人值守的监督、以后的运维视图——它们问的是另一个问题，目前没有地方回答，于是只能拿为"能否决策"设计的标量去推断处境。

## 已经撞上的两例

**可决策不等于已静默。** `RUNNABLE` 只表示存在尚未消费的决策事实，与"命令是否全部终局"是两根独立的轴。消费者若按决策观测位置去切一个静默边界，会间歇性地切在同一个 Step 的两条命令结果之间。这一例已经收敛，结论是消费者该直接查在途命令而不是从状态推断静默，它不欠 Runtime 改动——但它暴露了这类误用的形状。

**无人值守时没有人可问。** 一条答完话在等人的会话，和一条卡住等人去世界里完成登录的会话，从 Runtime 状态上看一模一样。后台任务与 [SubAgent](../运行/SubAgent.md) 根本没有人可问，它需要的是升级而不是干等。起因见[交互式资源](交互式资源.md)。

## 边界：处境不是 Runtime 状态的扩展

Runtime 只做确定性的事实归约、调度与不变量，见 [Runtime · 职责与边界](../运行/Runtime.md#职责与边界)。"在等人登录"是领域含义，把它做成一类新的等待理由就是把语义判断搬进内核，而且会一路加下去。

**升级需要的信息已经在 Journal 里，只是不在 Runtime 状态里。** 工具的 Outcome 带着领域 code，模型的 deliver 也已入账。处境视图应当是 Journal 的又一个投影——和 ToolSurface 从已提交 Outcome 重建激活集合是同一个手法——投影可丢弃可重建，但不能反向成为状态所有者，见 [Runtime · 投影边界](../运行/Runtime.md#投影边界)。

## Runtime 侧已经改掉的一笔

等待理由原先用"用户消息"兜底，名不副实：能成为 trigger 的外部事实不止人的发言，还包括要求决策的领域事实，SubAgent 回传与[自动化](../运行/自动化.md)触发都走这条共用窄入口，对无人值守的 Session 断言它在等 user 是在说一件不成立的事。现已改为"等外部事实"，见 [Runtime · 状态](../运行/Runtime.md#状态)。

这笔属于确定性事实的更正，不涉及语义判断，所以它能落在 Runtime。**本专题剩下的部分都不能。** Runtime 只知道那条外部事实还没来，不知道它为什么不来——那是处境，得另找所有者。

## 升级的第二种触发：跑偏

上面两例都是"停住了"。还有一种处境是**在跑，但方向不对**：反复在同类失败上打转，或者动作已经滑出任务描述的范围。它和"卡住了"要的是同一个动作——无人值守的 Session 怎么惊动人——所以不另立专题。

对 [SubAgent](../运行/SubAgent.md) 这尤其要紧。父对一个跑偏的子只有两个选项：让它跑完，或者 `reclaim` 杀掉；中间没有纠偏这一档，整段工作只能作废重来。子的能力越强，这一档越贵。

几条已经清楚的形状：

- **汇报不是授权。** 它异步、事后，而授权必须在副作用发生之前阻塞。指望进度汇报兼任安全闸，只会做出一个半阻塞的东西，两头都不成立。
- **不定时，由子自己判断何时上报。** 固定间隔是脚手架在做机械判断，而"现在这个进展值不值得打扰人"是语义判断。定期汇报里绝大多数是"还在跑，一切正常"。
- **进度给人看，不进父的 Journal。** 它走 SubAgent 那条活动指示的线：读进程内缓存、异步发出、只管显示、可丢可过期、不进执行闭环。灌进父的 Journal 就是把过程塞回父的上下文，正好吃掉 SubAgent 存在的主要理由。
- **判据的结论只走向人，不回喂给被观察的那条 Session。** 回喂就要像 [LoopGuard](../上下文/LoopGuard.md) 那样把结论冻进事实并记下判据版本——概率判断不可复现，重放时算不出当初那个数。

**这不和"不靠时长自动判定卡住"冲突。** 那条排除的是运行内核按时长下结论；这里的判据是执行轨迹本身，判断发生在内核之外，而且只驱动显示、不挡执行。

## 待设计

- 处境视图归谁：Assistant 的投影，还是[入口与授权](../入口/入口与授权.md)的升级面，两者需要的粒度是否相同；
- 升级由谁判定。"等太久了"是语义判断，运行内核不能按时长自己下结论；
- 无人值守的 Session 怎么声明自己没有人，升级又投给谁——这和 SubAgent 的中断回传是不是同一条窄协议；
- 观察本身要不要留下事实。看一眼处境不应改变 Session，但升级动作大概要。
- **跑偏怎么定义。** 这等于在问该拿哪几个问题去问一条轨迹——是不是在重复同类失败、动作还落不落在任务描述范围内、产出相比前面是不是在变差。这份清单本身就是升级判据，比怎么接线重要。[LoopGuard](../上下文/LoopGuard.md) 那份"后续可增加"的策略清单越往后越需要语义判断，两边是同一个缺口。
- **判据拿什么当输入。** 一条执行轨迹里可能含工作区内的私人内容，送给外部服务是一次数据出境。这是产品决策，不是实现细节。
- **允许多次上报之后，终局怎么保持唯一。** SubAgent 的"最多回收一次"靠投递身份从子 Session 身份确定性派生、第二条被 Journal 幂等吞掉；放宽成多条上报，就必须让"哪条是终局"能从已提交事实判定，否则父会拿着一个永远清不空的待回收集合干等。
- **人要不要能向子插指令。** 那会推翻子"对话另一端没有人"的前提，也要求子先能被看见——它现在不进顶层列表、`deliver` 是空操作。这是把子从"没有人的函数"改成"可监督的后台任务"，是形态转变，不是加一个功能。

## 已经排除的做法

- **不给 Runtime 增加语义化的等待理由**（例如"等人工操作"）。同理不增加 Goal / Criteria 状态，见[工作计划与长任务](../上下文/工作计划.md)。
- **不靠时长自动判定卡住。** 缺少新事实的等待不会因为超时而获得新含义；无新事实的定时唤醒已在[工作计划与长任务](../上下文/工作计划.md)排除。
- **不让处境视图成为第二事实源。** 它是投影，不是 Runtime 状态的一部分。
- **不为"可决策不等于已静默"补 Runtime 字段。** 在途命令的事实已经准确，欠的是消费者查对字段。
- **不把进度汇报做成父子双向对话。** 子的"一次性"是投递幂等的性质，父没有追问通道所以任务描述必须自包含；开一条双向通道会让父的上下文被子反复打断，隔离随之失效，见 [SubAgent](../运行/SubAgent.md)。

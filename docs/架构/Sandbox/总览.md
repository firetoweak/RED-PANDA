# Sandbox

Sandbox 统一承载助手与任务环境交互时的执行边界。当前文件管理能力已落地；完整的进程与网络隔离尚未实现。长期目标见[Sandbox 设计目标](../../Sandbox设计目标.md)。

## 职责与依赖

| 层 | 拥有的职责 |
|---|---|
| Assistant / Host | 委派、回收、结果验收、授权与回退意图，以及业务事实和文件操作的关联 |
| Sandbox 文件管理系统 | 文件视图、受控操作与历史、发布与恢复、子任务基准及成果交换 |
| 原生文件管理服务 | 候选文件执行、变化证据、接受与恢复执行 |
| 底层 VFS 库 | 文件系统语义、存储事务、写时复制、冻结制品与挂载适配 |

上层通过文件管理系统使用完整的文件能力。原生控制协议、对象存储和 Git 比较合并属于其内部实现，不由 Assistant、Host 或 Tools 分别编排。文件管理系统可以由 Python 和 Rust 协作实现，职责归属由变化原因决定。

文件管理系统基于原生能力构建；原生服务使用底层 VFS 库。底层库不认识 Session、Step、委派或验收，不维护另一套产品回退历史。这里的“VFS 库”专指文件系统机制；早期讨论将整个文件管理系统简称为 VFS，不据此扩大底层库的职责。

工作区登记、路径范围与执行环境绑定属于 Sandbox 的环境边界；用户可选择的工作区与临时文件视图有不同的生命周期。进程与网络控制按真实需求独立推进，不预建空模块或统一策略框架。

## 当前契约

| 文档 | 唯一负责的主题 |
|---|---|
| [执行环境](执行环境.md) | 任务根、材料根、命令启动环境与产品环境的边界 |

文件视图隔离不代表进程访问已经受到操作系统约束。挂载外文件写入、安装、系统配置与网络副作用不属于文件回退范围。进程安全边界仍见[进程沙箱](../未开始/进程沙箱.md)。

模型只接触逻辑文件位置、可观察结果、使用限制与下一步动作。内部锁、候选、发布阶段和版本坐标不能成为要求模型理解的前提。

# 后续方向

本文只列尚待解决或验证的问题，不记录已完成切片与实施分工。当前架构见[多智能体总览](总览.md)，产品取舍见[产品定位](../../产品定位.md)。

## 用真实任务证明协作价值

在讨论、检索、内容生成和简单编码等日常任务中，观察 Bot 能否交付可用结果，持续交流是否减少背景重述，需要多人协作时能否减少人工协调。

外部接入先走通一次「原生 Codex 交付明确版本 → 长期团队独立验证 → 原聊天取得反馈并修复 → 新版本复验」。观察有效问题是否补足自测遗漏、证据是否支撑修复，以及每轮还需多少人工转交、催促与协调；不能把接口接通、CI 通过或报告发出当作价值已验证。

长期职责的保持也需在持续工作中验证。真实 PR 测试团队是一个具体场景：协调者按例行任务观察版本，由成员独立取证并汇报。重点看漏派与重复派单、报告到达人的时间、压缩后是否保留职责与约定。验证方法和派单规则留在对话与项目 Skill，不建设系统内测试执行器或任务状态机。

多个原生聊天之间更深入的讨论、交接和群参与，等实际并行工作证明需要后再扩展。通用通信与客户端适配继续分开，其他客户端按真实需求适配和验证，不预建通用执行器或外部长期成员框架。

## 按实际阻力扩展

| 问题 | 接入方向与边界 |
|---|---|
| 没有远端的项目怎样发现新版本 | 可由例行任务按 Skill 观察本地集成分支，不先增加事件源 |
| 例行检查大多无事可做，调用成本明显 | 经测量后再考虑可选前置命令，以输出变化决定是否唤醒；当前先不做 |
| 只有远程仓库地址，尚未准备本地目录 | 再设计获取与登记；当前挂载只接受已准备好的本地 Git 仓库 |
| 长期工作何时需要主动向人升级 | 见[处境观测](../未开始/处境观测.md)，卡住或跑偏的含义由模型判断 |
| 怎样提供可依赖的执行隔离 | 见[进程沙箱](../未开始/进程沙箱.md)，授权仍由人决定 |
| 浏览器、SSH、REPL 怎样保持交互资源 | 见[交互式资源](../未开始/交互式资源.md)，不把资源会话混入 Runtime 状态 |

这些方向尚不是实施设计。只有需求和边界明确、能独立验证时才推进，不为目录完整提前建框架。

## 回退仍未设计

当前撤销文件成果依靠 Git，不提供对话回退或任意步骤的文件版本。以后若重提回退，必须解释对话与实际 Git 提交如何关联，并保证不越过已被同事使用的输出；不能连带回退其他 Bot，也不能靠系统自动补提交制造逐步版本。

Agent 文件系统的去留与代价见[取舍记录](../../历史/AgentFS取舍.md)。只有新的真实需求使现有前提不再成立，才重新讨论，不因追求完整撤销而恢复旧层。

## 继续坚持的取舍

系统提供身份、通信、执行、定时与授权原语；谁负责、怎样交接、何时报告和如何验收由人、模型与 Skill 约定。群聊不需要主持人模型，协作不要求共同项目，项目也不决定同事关系。

不包装或托管外部编码工具，不新增普通 Web 会话模型，不监听 GitHub webhook，不让系统判断任务状态或依赖。新增功能应减少真实任务中的人工协调，并能局部接入、明确生效、独立验证。

# 入口与授权

各类 Channel 共用的 identity、投递幂等、并发输入与输出路由约束见 [Channel 接入契约](Channel接入契约.md)。本页记录当前 TUI 与 Telegram 的入口行为，以及控制提案的事实形状。

## TUI

```text
python console_chat.py [--workspace <path>]
```

`--workspace` 显式登记或复用该路径，缺省使用启动目录。TUI 每次启动生成新的 Session 并绑到这个工作区。

**输入读取与 Agent 推进并行。** 单个后台任务独占标准输入，编辑行在空闲和运行期间都可用；运行期间新输入的每一行仍是普通 `UserMessageReceived`，不是 Interrupt。所有后台输出写到编辑行上方再恢复输入内容与光标，Agent 执行不直接操作键盘或编辑行。Channel 不维护运行中输入的特殊协议。

模型正文 delta 直接续写同一次输出，提交后的 `deliver` 只结束该行、不重复全文，异常结束则标出中止。底部一栏展示最近一次模型返回的实际输入用量、compact 绝对触发阈值与 compact 次数、相位；用量包含缓存命中，不显示请求前估算。Journal、Step、授权事实这些说明留在文档里，不进启动横幅。

`/resume <session_id>` 只选择用户明确指定且已持久创建的 Session，包括尚无 Event 的空 Session，**不猜测"最近一个"**。选择成功后 Host 才替换该 owner 的旧映射，失败时旧选择不变。

TUI 只处理能够确认来源的输入错误和控制信号。内部契约违规或未预期异常必须穿透 Assistant 与 Channel，在进程入口直接暴露，不能打印后继续运行，也不能降级成业务失败。

模型错误逃逸后台 Step 后，Scheduler 立即唤醒 Channel 的失败等待；入口展示已识别的模型错误并停止当前进程，未知异常保持原样穿透。失败的模型决策没有提交 Step，Session 仍是可恢复的 `RUNNABLE`。若 Tool 异常逃逸，已经持久开始但没有 Outcome 的 Attempt 保持 `unknown`；`/resume` 只重建投影和唤醒合法状态，不重试或伪造未知副作用的结果。

## Telegram

入口访问边界由配置的 allowed chat id 决定。该值为空时**只启动配对模式**：仅回显来源 chat id，不装配 Assistant、不创建 Session、不接收任务。

正常模式以 bot + chat 作为对话 identity，token 只是凭证。工作区只接受显式指定；没给时回退到最近一次聊天的工作区，完全没有则报错退出，**不从进程启动目录隐式登记**。

所有文本按 update 投递顺序接纳为 UserMessage。模型首个正文 delta 创建消息，后续 delta 按时间窗合并编辑，最终 `deliver` 刷新为已提交正文；明确的临时网络、服务端和限流错误在 Channel 内重试。

## 输入到事实

| 输入 | 事实 |
|---|---|
| 任意普通文本 | `UserMessageReceived` → wake Session |
| `/new` | Channel 生成 identity，Assistant 交给 Runtime 创建新 Session |
| `/resume <session_id>` | Channel 选择已有 Session；Assistant 重建能力并按当前 State 唤醒 |
| `/mcp` `/skill` | TUI 控制面，不进 Journal 当用户任务 |
| 待授权时的 yes / no | `CommandAuthorized` / `CommandRejected` |
| 待授权时的其他句子 | 仍是 `UserMessage`，下一步模型判断 |

## 两条边界

**副作用安全**：产品装配的 Tool Spec / Binding 显式声明是否需要授权，签发 Command 时冻结该要求。需要授权的 Command 没有授权事实就不能 dispatch，**模型不能批准自己**。Runtime 不根据工具名、参数或模型措辞推断风险。

**意图**：这句话是什么意思，由下一步 Step 判断。Runtime / Assistant 不得因为"正在等授权"就丢掉用户的话。

yes / no 在等待授权时由 Channel 映射为授权事实，因为**那是人在回答产品的批准问题，不是模型该投的票**。

用户工作区的普通写入与子成果合入需要授权；子在独立工作树内写入不需要授权，见[可写子会话](../运行/可写子会话.md)。Web 提供 Session 总闸的设置入口，TUI 不提供总闸 UI，在总闸关闭时拦截并用 yes/no 一次性处理当前全部待授权命令。owner 切换不改变这条 Session 已设置的总闸。这只是产品装配当前的声明，不是 Runtime 的内置白名单；以后调整某个工具的策略只改其 Spec / Binding，已签发 Command 的授权要求不会随配置变化。见 [Command 授权](Command授权.md)。

## 安装

安装、恢复、更新、删除或启用 MCP / Skill / CLI 有两种入口：直接用 `/mcp`、`/skill`，或在普通对话中先按需加载对应管理域，再由模型提交提案。管理域成功加载后，诊断与提案 Schema 从下一 Step 才可见。提案必须单独调用，用户确认前不执行变更。

## 控制提案

Control Approval 有自己的窄协议，但必须服从与 Runtime Command 相同的**"事实先于副作用"**原则。它不复用 Runtime Command Authorization，也不能让普通工具结果进入授权等待态。

一次请求使用稳定 `request_id`。**冻结输入存在已提交 Step 中**，Worker 内存中的暂存只允许作为缓存；若 Step 已提交而候选尚未形成，恢复时从 Step 重建同一请求。

候选准备不得改变 Registry、已安装包或其他产品状态。它可以原子写入由内容 hash 标识的不可变候选产物；该产物是提案所引用的持久执行输入，不是可随时清理的 staging。准备只能产生三种持久结果：

| 事实 | 何时 | 是否请求决策 |
|---|---|---|
| `proposed` | 冻结确定候选、summary、risk 与 revision，等待人裁决 | 否 |
| `concluded` | 只读准备已经得到无需执行的已知结论 | 是 |
| `preparation_failed` | 准备边界返回语义明确的已知外部失败 | 是 |

未知异常不得写成 `preparation_failed`，必须原样结束 Worker。因为准备契约禁止产品状态变更，恢复可以从已提交 Step 重新准备；**一旦 `proposed` 已提交，就始终使用其中冻结的候选**，不重新探测或静默升级。执行时若候选已不存在，属于语义明确的已知失败；候选内容与 hash 不一致则是持久化损坏，必须原样暴露。

用户裁决和外部执行分开记录：

```text
proposed
  ├─ rejected
  └─ approved
       → execution_started
       → succeeded | failed
```

`approved` / `rejected` 只表达人的决定。批准后必须先提交 `execution_started`（其 id 由 `request_id` 确定性派生），Handler 随后才能改变外部世界。`execution_started` 之后没有终态时投影为 `unknown`，恢复不自动重试——需要查询、补偿或重新提案时由对应管理域提供窄协议，**不能把异常或时间经过写成失败**。

`rejected`、`succeeded`、`failed` 会请求下一次模型决策；`approved` 和 `execution_started` 不单独唤醒模型。unknown 只作为持久投影暴露给人和后续 Decision Context。

每个事实使用 `{request_id}:{phase}` 作为投递身份。重复 yes/no、重复 IPC 或恢复投递只能命中同一事实。

Channel 从投影出示 summary / risk。提案本身不走 `deliver`，不进对话时间线；执行说明只能从同一 `request_id` 的 Journal 事实投影，不另存一份结果。有待裁决项时不再向模型提供控制工具 Schema。

进程退出或 Worker 静止不丢待确认项。`proposed` 未裁决时绝不执行，`approved` 尚未 `execution_started` 时可以继续确定性派发，已 `execution_started` 而无终态时保持 unknown。

# 交互与响应

RED PANDA 是以编码为主的泛用 Bot：讨论想法、分析资料与推敲方案也是完整的协作场景。本文围绕长期 Bot 的交互职责组织，输入优先、保持响应和回复去向适用于这些场景。Bot 的身份、个人目录和交流已独立于代码项目，项目是执行编码与集成成果时使用的可选资源；当前边界见[总览](总览.md#项目归属与执行目录)，后续演进见[方向](方向.md)。

长期 Agent 同时接收人的要求、同事私信、群里的回应请求和执行结果。它需要在长时间工作期间继续接待新的请求，让人的更正及时进入判断，并把回答交给明确的听众。

这三件事分别决定输入何时进入决策、命令是否占着当前处理、输出交给谁。它们不能互相代替：收到输入不等于已经处理，命令转后台不等于工作完成，普通回复也不等于已经回复同事或群。

## 人的要求优先进入下一次决策

人设定目标、给出授权，也会修正之前的要求。系统已经接纳更正后，不应只把较早的旧指令交给模型，或让更正排在同事消息之后，继续依据不完整的要求行动。

因此，下一次决策优先处理当时已经接纳、尚未处理的全部人的输入。每条消息保留身份、原文和顺序，模型判断它们之间的关系；系统只按输入类型选择，不读正文判断哪条是更正，也不沿来源链把同事报告算成人的输入。人的输入优先是一项产品政策，与操作是否获得授权相互独立。接受的代价是人持续追加消息时，其他来源可能持续等待。

新消息不改写正在进行的模型调用，也不撤销已开始的操作。整批输入若需要等待旧操作产生结果，就一起等待，不能先交付更正之前的旧指令。旧结果与新输入共同进入后续判断；没有人的输入时，其他要求决策的事实仍逐条处理。完整的可见性、消费、失败与取消契约见 [Runtime · 用户输入与后到消息](../运行/Runtime.md#用户输入与后到消息)。

一次决策处理过这批输入，只表示模型已经得到共同判断的机会，不表示逐条答复或任务完成。显式取消也只取消当前决策批次，不能由系统解释成整项任务已经取消。

## 长命令释放 Agent，结果可靠回来

耗时脚本、资料处理，以及编码中的构建、测试和长验证，都不应让 Agent 在几分钟里无法回应人或同事。命令只在前台等待有限时间；尚未结束就转后台，也可以直接在后台运行。Agent 可以继续做别的，或结束当前处理、等结果回来，不需要占着一次模型调用或反复查询来保住后续工作。

「已转后台」承诺的是：命令可以继续寻址、查看输出和停止；结束后，结果作为一条新的、要求决策的事实回到原 Agent。自然结束和被停止都恰好接纳一条完成通知。它不承诺命令成功、必然结束或服务已经就绪，也不表示 Agent 已经向人或同事汇报。

后台执行只释放等待，不创建另一个 Agent 或独立任务上下文。完成通知进入同一条长期会话，模型结合届时可见的要求决定结果意味着什么、继续做什么、向谁汇报。通知标明它来自此前的后台命令，不能伪装成人的新要求，也不注入已经进行中的决策。

命令没有默认总运行期限：开发服务器本来就可能一直运行。担心进展时，模型可以安排一次性提醒，回来查看输出并决定是否停止；系统不按静默时长或输出内容判断卡住、就绪或工作完成。

后台命令不因切换会话或打断当前轮而停止。前台打断与停止后台命令是不同动作，均不能撤销已经发生的副作用。应用重启后，系统补报已保存的退出结果；没有结束记录就报告结果未知，不声称必然被终止，也不自动重跑。命令执行与恢复的完整保证、平台范围见[执行环境](../能力/执行环境.md#命令生命周期与后台执行)，进程恢复见[多活跃会话](../运行/多活跃会话.md#worker-生命周期)，前台终止见[打断](../运行/打断.md)。

## 普通回复给人，协作消息显式发送

长期 Agent 的普通回复直接给人看，包括由同事私信、群回应请求、例行任务或后台命令完成开始的工作。模型按普通对话协议表达结论，不需要另用消息工具才能回答人；实时输出、历史与恢复后的展示遵守同一规则。接受自主工作的收尾也给人看，不再区分「工作记录」与「给人的消息」。

表达形式由模型按任务选择：日常交流保持简短，复杂内容适合时采用非像素的图形表达，结论与关键依据保持可见。Web 可接收的表达入口直接告诉模型，不维护格式或图型清单，也不增加格式配额或强制模板。

对同事说话用 `send_message`，在群里说话用 `send_group_message`。普通回复不会自动发给唤醒者，不会因此叫醒其他 Agent。群发言用 `reply_to` 表达在回应哪条消息；回复引用只表示回应关系，不表示工作已经完成，具体规则见[总览 · 群聊](总览.md#群聊)。

需要人下载文件时，用 `send_file` 交付工作区文件的副本并附说明；同事之间仍直接读取工作目录。例行任务的无人查看判断依据实际交付给人的回复与文件，不能依赖某个回答工具是否被调用。

不按「这一轮由什么开始」决定输出去向。一次决策可以照顾多项往来，触发来源不能代表每句话的听众。系统负责固定的普通回复展示和显式消息投递，汇报内容与协作对象由模型判断。

曾经要求给人回答也使用 `message_user`，但普通 assistant 回复的协议形态与人的实际可见性不一致。实测中，模型会漏发；积累纯文字回答后，追加说明也不能稳定纠正。当前选择让普通回复与人的可见性一致，不让 Runtime 猜正文并补发，也不继续叠加提醒。关键对照及实验限制见[回复交付实验](../../实验/回复交付1020.md)。

Runtime 的「一次决策必须有产出」不变。普通会话仍直接回复人，SubAgent 的普通回复直接给父 Agent，回合收口不结束协作，由父验收并明确结束，后台压缩不向人交付回复；这些边界不由长期 Agent 的展示规则扩展。

## 系统提示从长期处境出发

长期 Bot 与单次会话共用执行、证据、工具结果与表达约定，区别只在系统提示开头的处境。单次会话默认后续消息延续当前任务；长期 Bot 的时间线由人、同事、群、例行任务和后台结果交错组成，延续当前任务的默认在这里会把别人的消息并进错误的事。因此长期 Bot 的处境先说明它是团队中的一员、来源交错需要先分清归属，以及人与同事的角色：同事的请求以不超出人给的授权、不与人的要求冲突为界，可以直接接手，需要授权或决定的回到人；答应过谁、在等谁由模型自己记住。

模型可见文字统一把人称作「用户」，与工具返回一致；同事不是用户。名字、负责方向和所在的群仍由事实给出，不写进系统提示；处境只说被拉进群时会收到记录，不暗示 Bot 已经在某个群里。

协作约定只针对实测出现的失败：只做人交代的、同事请求的和自己的例行任务，同事加入或声明方向不触发打招呼与分工讨论；回复同事回答所问，不发纯确认；谁接了人的事由谁汇报，同一问题只问人一次；普通回复不复述刚发给同事或群的内容。给同事的内容仍由 `send_message`、`send_group_message` 显式发出，约定只是强调普通回复不会转给他们，不改变去向，也不另设回答人的通道。

这些约定只能缩短由同事、群或例行任务开始的那一轮写给人的回复，不能省掉它：一次决策必须有产出，被叫到群里却不发言的成员也会给人留下一句话。允许长期 Bot 以无回复结束一轮已试过：模型能判断该沉默，却不能可靠地产出空结尾，因此保持现状，接受每一轮留下一两句话。对照数据见[协作约定实验](../../实验/协作约定1021.md)。

## 模型只需理解可观察行为

人的输入、后台完成通知和协作消息必须明确呈现来源及必要的引用关系。工具说明与返回只告诉模型可以选择什么、实际发生了什么、接下来能做什么。后台执行说明应让模型知道命令仍在运行、结束会收到通知，以及可以查看输出或停止；不能要求模型理解内部调度、进程归属或持久化机制才能正确使用。

系统保证输入与结果可靠进入判断、输出遵守明确的去向，不能保证模型据此采取正确行动。是否完成、是否需要重跑、是否向某位同事汇报仍由模型或人决定，不从回复中的承诺反推任务状态。

# Coding Bot

长期 Bot 及编码场景的当前边界。产品方向与尚未落地的部分见[后续方向](方向.md)，人的输入优先、后台工作期间的响应和回复去向见[交互与响应](交互与响应.md)，可替换的任务方法与协作流程见[编码与工作流](编码与工作流.md)，常驻工作约束见[共同记忆](../上下文/共同记忆.md)与[个人记忆](../上下文/个人记忆.md)。

## 稳定身份与名册

一个 Bot 以全局唯一的名字寻址，身份独立于代码项目，指向一条长期 Session。名字区分大小写，不带首尾空白，可以使用中文；人可以修改名字，会话、工作目录与群成员关系继续保留。同事会收到改名事实，新私信与点名使用当前名字；旧消息与进行中的群回应仍对应原来的 Bot。曾用名只属于原身份，不分配给其他 Bot，避免历史通信指向另一个人。Session 身份只用于内部定位，不作为模型寻址同事的地址。

Host 拥有创建与名册查询。固定的身份关系随创建事实写入该 Session，先持久化，再允许启动 Worker；名册从这些事实重建，不独立保存另一份身份清单：Host 在第一次用到时读一遍 Journal 建出内存索引，之后随创建、改名与项目变化更新，重启时重新建。每个源头已驱动的 Agent 消息同样只在内存里按消息身份记账，重复投递不重复计数。发送、群调度与收件箱因此不再随历史长度变慢。并发创建也必须守住全局名字唯一。项目继续使用工作区登记，不另建项目清单。

分工来自用户要求和实际协作约定，不维护独立的「负责方向」资料，也不将一句长期角色描述反复带入模型上下文。真实协作中方向为空仍能正常分派和执行，预先填写反而可能牵引当前任务。持续适用的工作约束由个人记忆承接，协作经历通过历史回查，知识成果按需检索；不以角色标签替代任务记录或扩大授权。

名册对模型的呈现分两部分：查询给出当前快照，事实给出之后的变化。Agent 可以用工具查询所有同事的名字和工作目录，不包括自己；查询结果不带内部 Session、项目坐标或分支名。查询同时给出每位同事当前在工作、空闲还是等人授权，以及最近一次活动的时间，与 Web 名册归约自同一组已有事实；是否卡住、要不要改派由模型判断，系统不设停滞超时。同事加入时，Host 把对应事实投递进其他 Bot 的时间线，不请求决策，从下一步可见并可重放；同事离线时为此拉起它的 Worker。名册不写入 System Prompt。

创建在持久化身份后，先向同事投递加入事实，再重新投递创建事实拉起新 Agent 的 Worker；这样同事总是先知道它加入，再看到它做的任何事。Agent 不等人开口即作出第一次决策：问候用户并简短介绍能一起做什么。konden 本身能做什么、入口在哪里，写在所有 Bot 都能加载的内置使用指南 Skill 里，不由某位特殊 Bot 独占，也不写进 System Prompt。创建前不要求填写角色，之后按用户目标与具体协作约定工作。

上下文压缩之后，早期的创建与入群事实不再出现在模型视图里。新窗口在交接之前重新给出 Agent 自己的名字、所在的群及成员和它的例行任务，见 [Compact](../上下文/Compact.md)；同事的当前状态仍靠查询。

人可以在 Web 删除 Bot。删除使这个身份永久退出运行与协作：停止它的执行、子任务、命令与定时唤醒，不再接受新任务或消息，也不再作为群里的有效成员。聊天事实、个人目录、项目工作树与分支保留；删除不丢弃或自动落地成果。名字继续属于原身份，历史通信不会指向后来创建的 Bot。删除事实是重启后仍不续跑的依据，已有历史可以只读查看，不提供恢复入口。

## 项目归属与执行目录

每位 Bot 创建时自动获得一个普通的持久目录，用于文件、资料和笔记；没有代码项目也能对话、协作、读写文件与执行经人授权的命令。个人目录跟随身份，不因 Worker、Host 重启或上下文压缩而改变，它始终是 Bot 的任务根。不为普通目录初始化 Git；Host 只管理其中挂载项目用的 `projects` 子目录。

项目是可挂载的执行资源，偏向编码靠默认设置（创建时可选关联、内置编码 Skill、挂载提示），不靠 Runtime 里的编码分支。一位 Bot 可以同时挂多个项目，也可以在对话中途挂上或解除。挂上一个项目，就是在 Bot 个人目录的 `projects/<项目名>` 下为它准备一份独立 worktree，在它自己的分支上；任务根不切换，系统提示不变，挂载以事实进入时间线，告诉模型项目名与工作树目录。项目名在同一位 Bot 的挂载中唯一，重名时加序号。项目继续使用工作区登记，不把每份 worktree 再登记成项目。

选择任务根不动而不是切到 worktree，是因为切换要换系统提示、只能挂一个项目，中途挂载还要重新装配会话。代价是 Bot 在项目里工作时要写工作树下的路径、给命令设 cwd；真实模型对照中两种方式都能正确改代码、提交和落地，任务根不动时没有出现写错目录，见[项目挂载实测](../../实验/项目挂载1021.md)。

项目以本地仓库目录识别，名字直接取目录名，不单独命名或改名。同一目录可被多位 Bot 复用，不因已经登记而拒绝关联。人在创建 Bot 或之后关联时直接选择目录，不必先创建项目；选择尚未确认时不登记。Bot 用 `link_project`，可以给已登记的项目名，也可以给一个本地 Git 仓库根目录，后者原地登记为项目。授权看谁发起：人在 Web 上操作不需要确认；模型给出的路径要人批准，给已登记项目的名字不需要。原地登记的仓库就是这个项目的「人的检出」，集成分支从它当时的 HEAD 建立，之后它怎么变都与集成分支无关；它被删除后项目登记失效，相关操作明确报错。

解除只影响那一位 Bot：移除它在这个项目里的工作树和分支，不动项目本身和其他 Bot。工作树里有未提交的改动、分支上有未落地的提交、有进行中的合并，或还有委派到这个项目尚未交回的子任务时，解除不执行，结果列出原因；系统不替 Bot 丢弃任何改动。重新挂上时从集成分支开新分支。

文件工具直接作用于真实目录，自己的目录可写，同事的目录只读；开放其他宿主机路径也不改变同事目录的只读边界。同事挂载的项目在其个人目录里，只读讨论直接用现有的只读权限查看；要一起测或一起改，各自挂上同一个项目、各开一个 worktree。命令不按路径区分读写，仍走命令授权。所有 Bot 都装配挂载、落地、同步与分支委派的工具，没有挂项目时这些工具返回可观察的已知结果。所有 Bot 使用通用交互底座，编码与 Git 工作流按需加载；工作目录约定和自定义 Skill 不以 Git 项目为前提，见[编码与工作流](编码与工作流.md)。

Host 为挂载准备分支和 worktree，不接纳调用方指定执行目录或分支。项目登记路径必须是 Git 工作树根；裸仓库、未初始化的目录和没有首个提交的仓库不能挂载，登记前先校验，不留下无效登记。

每个项目有一条本地集成分支与 Host 持有的集成 worktree，首次挂载时从项目当时的 HEAD 建立，只取已提交内容。之后的挂载都以集成分支为起点，不跟随人检出或移动的分支，不重置已有挂载的工作树。人的暂存区、未提交与未跟踪文件不进入这个起点，也不要求人先清理它们。

集成工作树位于应用数据目录，Bot 的工作树位于它的个人目录，都必须在人的项目工作树之外。它们与项目共享 Git 对象和分支，不另建仓库副本；不同数据根各自拥有集成分支，不能争用同一条。Git 元数据承载这些关系，不再另存一份项目分支清单。已存在但与所属项目或分支不一致的集成工作树必须暴露错误，不自动覆盖或重建。

创建时关联项目与之后挂载走同一份准备逻辑，只是挂载事实随身份一并写入，第一次决策就能看到。事实写入失败时撤销本次新建的个人目录、Bot 工作树与分支，项目集成工作树继续保留；请求取消也必须等待本次创建或挂载收口，不能提前释放。创建 Git 工作树时不执行仓库钩子，宿主进程继承的 Git 路径覆盖也不能改变项目归属。

挂载请求的确认丢失不能视为挂载事实未接纳。请求收口后先核对原身份对应的事实：已经接纳的挂载保留工作树，并从事实校准名册；确未接纳才撤销本次准备的工作树。核对与清理不能遮蔽原错误，核对失败时不删除结果不明的资源。这只确定挂载是否已发生，不替模型判断任务是否继续。挂载和解除在物理操作之前保留原请求与资源身份，进程退出后先核对并收口原操作，再让 Bot 使用项目；已删除的工作树与已接纳的事实都不能当作一次新操作重做。

TUI 的普通会话同样直接作用于真实目录，但没有 Bot 身份带来的挂载、落地与同步和分支委派。Web 从名册按名字创建 Bot，代码项目可选；Bot 资料里列出已挂的项目，可关联或解除。不接受调用方指定的工作树或分支，不向用户提供手填内部工作树路径的入口。Web 不再提供输入区的文件改动摘要与会话差异审阅，代码成果通过项目自己的 Git 工具查看。

当前 Agent 不提供文件回退或历史分叉，撤销靠 Git。

## Git 文件历史

以下是关联项目时内置 Git 协作 Skill 提供的工作约定，用户指定的流程优先；实际分支与合并边界由工具保证。

Agent 主动管理自己的工作分支：在修改代码的任务中判断何时暂存、提交哪些修改、如何说明，以及需要哪些验证，通过现有命令能力执行 Git。只读任务和用户要求不提交的任务遵守各自范围。Git 操作沿用命令授权，负责提交不等于可以替人批准命令，也不等于获准推送远端、修改他人分支或重写既有历史。

修改任务收尾时，Agent 应核对相关修改已经提交；存在阻塞时说明未完成的部分。Bot 命令使用自己的 Git 作者与提交者身份，不继承启动者的提交身份，不改写用户或项目的 Git 配置。提供执行身份不意味着系统代替 Agent 发起提交。

系统不在 Step 收口、回复结束、上下文压缩或重启时自动暂存和提交，不为 Step 创建或补齐文件版本。真实执行与结果随普通命令留在时间线，文件历史以实际 Git 提交为准，不另建一份版本映射。未提交、已暂存与已提交修改分别用对应的 Git 差异核对；未提交差异为空不能证明任务没有修改。

不承诺每个对话步骤都有文件回退位置；未来回退需要单独明确对话与 Git 提交的关联。被忽略的文件不强制加入历史，现有提交不由系统压缩或重写。Git 命令失败由 Agent 根据实际结果判断下一步，系统不替它判断冲突解决或成果已经完成。

## 落地与同步

何时落地、何时同步是 Agent 的语义判断，由模型调用工具发起并指明项目；合并本身由 Host 确定性执行。内部 Git 进程复用既有进程托管，不能在所属进程退出后继续写项目。已开始的集成合并保留原目标和源提交；重启后只有暂存树仍等于 Git 对原提交的自动合并结果时，才能完成原合并提交。冲突或外部修改不由恢复猜测处理。两个工具都必须单独调用，不与同一步的其他工具并行。Git 提交仍由 Agent 自己决定，落地与同步只移动已提交的内容。

落地把 Agent 分支上已提交的工作合入项目集成分支，未提交的修改不随之带走：能快进则快进，否则产生一个作者为该 Agent 的合并提交。同一项目的落地由 Host 串行执行，取消请求也要等本次合并收口才释放。冲突时放弃这次合并，集成分支保持不变，结果列出冲突文件，由 Agent 同步、解决后再落地。落地不经人审批；每次落地都是一个可单独撤销的 Git 动作。集成工作树里有会被覆盖的文件时落地不执行，结果列出这些文件，由 Agent 告诉人去清理，不替人清理。

同步把集成分支合进 Agent 自己的分支，只拿到同事已落地的工作。冲突时合并停在冲突状态，交给 Agent 用普通 Git 命令解决并提交，或放弃。工作区里会被覆盖的未提交文件让同步不执行，不替 Agent 丢弃改动。Git 是否以退出码区分「冲突」与「拒绝合并」随合并方式而变，判断依据是合并是否留在进行中。

落地与同步时，Git 的其他失败（残留的 `index.lock`、文件被占用等）作为这次工具调用的失败结果，带着 Git 原文交给 Agent，不终止 Agent，也不改写成「文件会被覆盖」。只有 Git 明确说会覆盖文件才归为挡路；其余失败的含义交给 Agent 和人判断，结果也不声称工作树没有变化。

落地的合并结果作为该工具调用的结果留在 Agent 的 Journal 里，是之后判断外泄点的事实来源；集成分支的名字与位置不进入模型上下文；Git 失败原文里带出的路径例外，它原样交给 Agent，好让人找到出错的位置。

## 委派

Agent 的 [SubAgent](../运行/SubAgent.md) 与父共享个人目录和项目文件，能看到未提交内容并运行命令。父决定工作目录、修改范围、并行顺序及是否使用 Git 分支；系统不为子建立工作树、提交或合入成果。无项目时同样具备基础执行能力。

子保留独立上下文，普通回复直接给父，后台结果由子继续处理。父验收实际文件与证据，完成、取消或不再需要时必须显式回收；回收收口子执行和受管命令，保留共享文件与历史。解除项目之前先回收共享这些目录的子协作。

## 通信事实

创建、改名、私信、群发言、群消息回应请求分别表达确定的事实，复用 Runtime 的领域事实接纳，不新增执行循环或通用消息框架。事实重放必须遵守当前完整契约；损坏和未知错误不能被忽略或补成默认值。

私信按全局同事名字寻址，只接受收件人、正文与可选的回复引用。名字不存在、发给自己和引用不属于这两位同事的私信，都返回已知结果。发送成功只确认已进入对方时间线，不等待回复；收件人离线时拉起 Worker，正在工作时沿现有外部事实路径接纳。

人的打断只取消当前轮，不冻结 Agent 与协作环境。后续私信正常接纳并触发处理，不要求人再次允许继续。

回复引用由 Host 校验，继承被引用消息的交流链，每回复一次增加一跳。超过上限拒绝发送，在发送方留下不触发决策的上报事实，并在与人的聊天中呈现。上限只约束显式引用的链，不判断正文是否属于同一话题。

另起新链不能绕过总量：每条 Agent 消息（私信与群发言）都带一个源头，即最终驱动它的那条非 Agent 外部事实，例如人的一条消息或一次定时触发。Host 从发送方 Journal 确定性推出源头：发送命令由哪一步发出、那一步由什么触发；触发者是续跑结果时沿命令回溯，是同事消息或群回应请求时继承那条消息的源头。同一源头驱动的 Agent 消息有总量上限，超限同样上报给人。按源头而非“上次收到人消息以来”计数，同事交来的新任务不会占用另一件事的额度。上限数值是起步值，按实际协作调整。

私信身份由发送方 Command 确定性派生，收件方幂等接纳。发送方接管时，对未知发送使用窄恢复：按原身份核对收件方 Journal，已经送达就补交确定结果，尚未送达就按原身份投递；不能把未知结果直接留给模型再发一条新消息。双方同时恢复时可以先接纳事实，但模型决策须等待自身的发送恢复完成。损坏与身份冲突原样暴露，不降级成普通发送失败。

## 结尾文字的去向

普通回复直接给人看；对同事或群说话仍用显式消息工具，不自动回复唤醒者。完整规则、文件交付与取舍集中在[交互与响应](交互与响应.md#普通回复给人协作消息显式发送)。

## 群聊

群是 Host 持有的公共记录：每个群一份事实日志，放在会话目录之外，不是会运行模型的会话，也不进入名册、收件箱或启动时的会话遍历。群按全局唯一的名字寻址，成员是 2 到 6 个 Bot，项目归属不限制成员；创建时向每个成员投递不触发决策的入群事实，第一版不改成员。

发言先写入群记录，再作为不触发决策的事实投递给其他成员；发言者自己的时间线里已有这次工具调用。是否轮到某个成员回应由单独的回应请求表达，它请求一次决策。被叫醒时，之前到达的群发言都已在上下文里，一次决策就能看到全部；因此不需要改变 Runtime“一条外部事实一次决策”的规则。Agent 在群里只能用工具显式发言；每轮结尾的普通回复给人看，不自动发进群，见上文「结尾文字的去向」。

调度由 Host 确定性执行，不设主持人模型，不靠提示词让 Agent 闭嘴：

- 点名的消息只叫被点名的成员，不点名叫全体，发言者本人除外；按点名或成员顺序投递回应请求。
- 回应请求投递后即继续通知其他成员，不等待成员发言、工具执行或整段工作结束。各成员可以并行工作，忙碌成员在自己的时间线中接续处理。成员是否先回执、何时报告由模型决定，不能成为其他成员启动的前置条件；一次派活之后的新消息也不能被某位成员的长时间工作挡住。
- 一条发言算不算回应，由模型显式表达：它用 `reply_to` 引用自己被叫来回应的那条消息，且这次叫尚未被回应过，才算回应，延续那次讨论；同一次叫只认一次。系统只校验引用与待回应状态，不从这一步由什么触发、成员当时忙不忙去推断归属——同一步里模型可以照顾好几件事，只有它知道每条发言在回应谁。`reply_to` 只表示回应哪条消息，不表示那件事已经做完；一条发言只引用一条，同时回应几条就分开发。一轮里各条回应叫到的成员合起来是下一轮，整轮无人发言即停。
- 其他发言——没被叫时发的、回应之后继续工作再发的（例如先回执、跑完验证再报告）、引用了没有待回应请求的消息的，或忘了带 `reply_to` 的——各自开启一次新的讨论，有自己的轮数与回复额度，叫的人并入待叫队列，不取代正在进行的讨论，也不丢掉已在排队的人。
- 硬上限：每次讨论最多的轮数与回复总数。超限的回应返回已知结果与下一步，不写入群；轮数用完的发言照常写入，但不再叫人。新讨论不断开启也受每条源头的消息总量约束，见上文「私信」；漏带 `reply_to` 能绕开一次讨论的轮数，绕不开这条总量上限，因此轮数是让一次讨论早收住的软约束，互叫终止由总量上限保证。数值是起步值，按实际效果调整。
- 人的新发言取代群里正在进行的全部讨论，从它重新开始；这是转移话题，不打断成员手头的工作。
- 不提供群级的强制停止。它要判断成员事后的发言是否属于被停止的讨论，这只能从发言的来源推断；群聊靠每条源头的消息总量上限收住互叫，人发言可以转移话题；用户插话只打断当前处理，不把成员永久排除在后续协作之外。

群记录同时保留已接受发言的投递与调度进度。重启后按原身份补齐未送达的副本和回应请求，保留待叫顺序、已回应关系与讨论额度；已完成的叫人不从聊天历史重新生成。人的新发言仍取代旧讨论，重试同一次发送不算新发言。群发言身份由发送方 Command 派生，人的发言由入口保留稳定请求身份，复用已有幂等接纳能力。恢复只推进已记录的动作，发言回应谁仍由模型显式表达。

通信要保留明确的发言者、消息引用、线程与因果来源。消息身份、发送者和跳数由 Host 根据真实来源确定，不由模型工具参数自报。授权只能来自人的入口；同事转述的同意不构成授权。私信、群发言和同事查询只装配给有长期身份的 Agent，普通会话、SubAgent 与后台压缩不因此取得同事通信能力。

模型只看到自己的名字、发言者、群、正文、可引用的消息以及需要回应的提示。内部 Session、项目索引、分支、线程计数和投递坐标不直接进入模型上下文。真实任务目录由执行环境说明；名册变化不能作为可变内容直接写入 System Prompt。

人可以在 Web 解散群聊。解散后不再接受发言或叫成员回应，重启也不恢复未完成的讨论；群历史仍可只读查看，成员 Bot 的其他工作继续。群名保留给原群，避免旧消息中的群名指向另一个群。删除某位 Bot 只让它退出群的有效成员，不连带解散群；其余成员仍能交流。

## 不做

- 为身份增加独立的持久名册、通用注册框架或第二份项目清单。
- 替别的 Bot 挂载或解除项目，或在解除时替 Bot 丢弃未落地的工作。
- 让 Runtime 解释角色、人的同意或消息正文。
- 系统代 Agent 暂存或提交，或为每个 Step 追补文件版本。
- 在工作树与落地中加入协作工具、群调度或记忆。
- 落地时自动压缩提交、经人审批，或合并进人当前检出的分支。
- 给废弃的普通 Web 会话模型预建迁移与兼容路径。

# Coding Bot 后续方向

> 方向已确认，身份骨架与 A 线（工作区与落地）已接入，当前边界见[总览](总览.md)。本文只记尚未落地的方向、取舍与落地顺序，不是现行行为；每个切片完成后，把已落地的结论写进对应架构文档，本文只留后续部分。

## 方向

RED PANDA 从「开一个会话、做完一个任务」转向**几个长期在线的 Bot 自由交互协作**。侧边栏列的是同事，不是历史会话：每个 Agent 有名字、与人共同维护的负责方向和一条持续的时间线；人可以直接找任何一个说话，Agent 之间自己交接、讨论，需要人判断时再来找人。

系统只提供原语，不预设工作流。谁做什么、何时交接、谁来协调，由人在对话里交代、由模型当场决定；任何 Agent 都可以被交代成临时协调者，协调者不是一种特殊类型。**群聊是核心玩法。**

编码是优先做好的主要协作场景，但不是必须场景。人可以只创建几个 Bot，让它们讨论想法、分析资料或推敲方案，不必准备代码项目。长期职责由 Agent 自己的例行任务承担：到点叫醒自己，按保存的意图做事，GitHub 的 PR 与 CI 是编码场景中的例子，见[例行任务与验证闭环](#例行任务与验证闭环)。

### 项目资源继续解耦

Bot 的长期身份、负责方向与时间线独立于代码项目；创建、私信与建群不以登记工作区、Git 仓库或共同的项目归属为前提。项目是执行编码与集成成果时使用的资源，不承担同事关系与通信边界。需要编码时再关联项目并准备独立工作树，代码修改仍遵守分支隔离、授权与成果审阅的约束。

Bot 身份、个人目录、全局通信与前端入口已解耦，编码方法与 Git 协作也已收敛为独立加载的 Skill，当前边界见[总览](总览.md)和[编码与工作流](编码与工作流.md)。用户可以自定义协作流程，文件交接无需以 Git 为前提；Git 执行、授权与分支隔离仍由相应的底层能力承担，Skill 不替代这些边界。

项目已可在创建时关联、对话中途挂上或解除，一位 Bot 可挂多个，见[总览](总览.md#项目归属与执行目录)。尚未实现的是给远程地址由 Host 拉取再登记；不预建通用场景框架。

## 阶段

| 阶段 | 目标 | 状态 |
|---|---|---|
| 一：长期 Coding Bot 基础 | 身份与名册、独立 worktree 与分支、私信、主动 Git 历史、落地与同步、变化查看；移除 Agent 文件系统 | 已完成，见[总览](总览.md) |
| 二：单群协作（当前 MVP） | 群聊中自由讨论与委派、并行修改不同分支、交换成果与问题、向人汇报 | 已完成，见[总览](总览.md)与 [Web](../入口/Web.md) |
| 三：例行任务与跨群闭环 | Agent 的例行任务定时观察 CI 等外部状态，测试问题回到开发，修复进入再次验证；Agent 参与多个群 | 例行任务、Web 控制、回复展示、防空转、GitHub PR 观察与文件交付已落地；剩验收，见[落地顺序 D 线](#并行线) |
| 四：异构专业 Agent | 外部编码端与长期 Bot 交换任务及反馈；长期 Agent 也可委派外部执行者 | MCP 主动协作入口已接入，见[外部协作](../入口/外部协作.md)；命令委派与自动唤醒继续按需验证 |

阶段四的约束：外部执行者不共享 Runtime，编码成果以 Git 提交回到协作。外部编码端主动通过 MCP 联系内部 Bot 的窄入口已落地，不成为名册成员；RED PANDA 主动启动外部 CLI 仍可先以普通命令形式验证，经命令授权，在 Bot 自己的工作目录内运行。不预建执行器协议，长期成员与客户端自动唤醒等真实需求出现后再议。

命令接入几乎不需要新代码，所以不等阶段三做完，放进阶段三的验收一起验证。理由：RED PANDA 若只是更窄、更可靠的长期 bot，人仍可以继续用通用 bot 加外部 Coding Agent；它站得住，要么靠原生 Agent 的编码能力，要么靠把专业执行者接进闭环。原有实践里自动化恰好止于「人把测试问题手动交给外部 Coding Agent」，这一步是最先值得自动化的。

## 长期 Agent

Web 的基本单位从会话换成 **Agent 名册**，不保留普通会话列表与名册两套并行。即开即用的单次会话由 TUI 承担。

- **回退不能越过最近一次外泄点**：A 在第 10 步发给 B 的消息，B 已经据此行动；把 A 退回第 8 步，B 的时间线里就留着一条 A 从未发过的消息，世界不再自洽。出问题的是越过了「已经被别人用过的输出」。未来回退不能越过给同事发私信、在群里发言或落地到集成分支的最近边界；外泄点由 Host 从它经手的事实确定性判断。文件历史以 Agent 实际保留的 Git 提交为依据，对话步骤与文件提交如何对应仍须设计，不再承诺任意 Step 都有文件版本，也不为实现回退让系统后台补提交。不另设普通会话入口。
- **第一版不做回退**，Web 现有的编辑消息开分支、从某一步重开随旧会话模型一起去掉。第一版保留 Agent 主动创建的 Git 历史，不由系统压掉（落地时可以收拢成一个提交进集成分支）；私信、群发言、落地都作为事实留下。
- **一条时间线**：一个 Agent 一条长期 Session。人的私聊、同事的私信、各个群的发言按到达顺序排在同一条时间线里，靠 Compact 延续；不为每个群另开上下文。
- **创建与归属**：由人在 Web 创建，长期身份不以项目为前提；每位 Bot 自动获得持久的个人工作目录；代码项目按需关联。Agent 不创建同事；需要临时帮手时用 [SubAgent](../运行/SubAgent.md)，委派能力保留。
- **首轮自我介绍与负责方向**已落地，见[总览](总览.md)。不设创建时必填的角色表单，不让人写 System Prompt；名册展示人和 Agent 共同维护的当前方向。

## 编码场景的工作区：每个 Agent 独立分支

多个 Agent 在同一个代码项目上协作时，每个参与编码的 Agent 有自己的 git worktree 与分支，不碰人自己检出的工作目录。这是编码场景的执行约束，不是创建 Bot 或交流的前提。做法参考 Claude Code「每个会话一个 worktree，改动不在主分支」。

**为什么不让所有人直接写同一棵活的工作树。** 同一文件的写写冲突还算显眼；兜不住的是「工作区常处于别人改到一半的状态」：A 改三个文件才能对上接口，改到第一个时 B 跑测试失败，B 无从知道原因不在自己。命令还会动到 `.git`、依赖目录、运行中的服务等没有按文件合并语义的共享状态。纯共享工作树只能把这些交给模型自觉协调，系统给不出确定保证。

- **集成分支**：项目有一条本地集成分支，由 Host 在自己持有的 worktree 中合并。人自己的工作目录不被触碰，何时把集成分支合进自己的分支或推到远端由人决定。
- **落地与同步**：已落地，见[总览](总览.md#落地与同步)。**落地不经人审批**：鼓励的小步频繁落地与逐次审批相互矛盾。同事尚未落地的改动可以直接去读，协作不必等落地，见[总览 · 项目归属与执行目录](总览.md#项目归属与执行目录)。
- **文件历史由 Agent 主动管理**：暂存什么、何时提交、提交说明与验证是否充分，由 Agent 根据任务判断并通过现有命令能力执行。系统不在 Step 收口时暂存、提交或补记文件版本，不为每一步创建空提交。历史按实际 Git 提交组织，审阅使用未提交差异与提交差异。worktree 是真实目录与真实路径，普通工具链原生可用。**不另建系统内的文件历史层**，原因见 [AgentFS 演进回顾](../../讨论/AgentFS演进回顾1018.md)。
- **主动 Git 操作的成本仍须实测**：当年 Git 方案卡在「每步整树哈希、多会话串行」上，见[版本操作分层](../../讨论/版本操作分层1009.md)。现在提交频率由 Agent 决定，每个 Agent 有独立的 worktree 与 index；仍须验证大仓库、Windows 和未跟踪文件扫描的实际耗时，慢了先查清原因，不先加一层。
- **SubAgent 挂在 Agent 的 worktree 上**：已落地，见[总览](总览.md#委派)。
- **编码项目要求是 git 仓库**；不是的先初始化。单纯讨论无需创建仓库。
- **已知代价**：每个 worktree 缺少被忽略的依赖与构建目录，需要各自准备；SubAgent 每次委派也要付一次检出成本。先接受，实测太痛再单独讨论。
- **文件之外的共享资源**（端口、测试数据库、开发服务器）没有合并语义，由 Agent 协商；后台命令按会话持有，各自在自己的 worktree 里起。

## Agent 文件系统的去留

Agent 文件系统（候选执行、发布、操作历史与文件回退）已于 2026-10-18 从主仓库整体移除，TUI 也不再使用它：所有会话直接作用于真实目录，文件改动不提供系统内回退，撤销交给 Git。代码保存在主仓库标签 `agentfs-final`（提交 174dcb6）与私有存档仓库 `firetoweak/agentfs`（带历史），演进与去留见 [AgentFS 演进回顾](../../讨论/AgentFS演进回顾1018.md)。

git 覆盖不到、可能让人重新考虑系统内文件历史的信号：

- 命令改动被忽略的文件（依赖目录、构建产物、本地配置），不进 git 历史；
- 未跟踪文件被删除，git 里没有记录；
- Windows 隐藏/只读属性与 POSIX 权限；
- Agent 重新需要直接修改人检出的工作目录；
- 每个 worktree 各自准备环境的代价无法接受。

遇到这些时，先问能不能改前提——例如明确被忽略文件不在撤销承诺之内，或把保护交给[进程沙箱](../未开始/进程沙箱.md)——再考虑从存档取回。直接接回等于重新爬一遍演进回顾里那架梯子。

## Agent 之间的私信

由子会话回传推广而来：任意 Agent 可以给任意同事定向发消息。

- 发送是一条 Command；Host 把消息作为外部事实写进收件人时间线，标明发送者并请求一次决策，收件人不在线就拉起它。投递身份由发送方 Command 派生，重复投递被吞掉。
- 结果只确认「已进入对方日志」，发送方不等回复；回复只是对方的另一次发送，没有请求/响应配对。
- **跳数上限**：消息按线程计跳，回复一次加一；超过上限时发送返回已知结果并上报人。这是确定性计数，不按内容或时间判断「是不是在闲聊」。
- **转述不等于同意**：授权事实只能由人在 Channel 中产生，Agent 无法替人批准。模型语义上仍可能把「对方说用户已经同意」当真，因此私信与群发言必须标明发送者，提示词明确其他 Agent 转述的同意不算数。

## 群聊（核心玩法）

群聊后端与 Web 入口已落地：Host 持有的群记录、显式发言工具、Host 确定性调度、按源头的硬上限，「一串发言怎么决策」的结论（发言送达不触发决策，只有回应请求触发），以及建群、人发言与点名、群记录的界面，见[总览](总览.md)与 [Web](../入口/Web.md)。仍需留意：

- **不进群的内容**：命令授权请求与需要人判断的事项只出现在该 Agent 与人的私聊，名册在对应 Bot 旁提示，界面不把它们搬进群。
- **上限数值以实测校准**：轮数、回复总数、每人每轮发言条数与每个源头的消息总量都是起步值。

## 例行任务与验证闭环

依据是一套已经实际运行的 PR 测试团队（Grok Bot，一名统筹加三名测试 Bot）：人与外部 Coding Agent 写代码、推 PR；CI 完成后统筹在群里点名派单，测试 Bot 回应接单，把 PR 合到最新主线上做端到端实测，在群里贴报告，统筹私信汇总给人，合入仍由人决定。从中得到的结论：

- **CI 只是信号，不是验证。** CI 完成说明「有新版本可以测了」；测什么、怎么测、结论是否成立，由测试 Agent 按项目自己的验证 skill 判断与执行。系统不提供测试执行器，不判定验证结论。
- **隔离靠约定，不靠平台。** 测试 Agent 各自的 worktree、端口段、验证实例与证据目录，由协调者在对话里约定。端口、测试数据等共享资源照旧由 Agent 协商。
- **规矩随对话变化。** 何时打回、哪些推送不重测、合入后是否补测、哪些消息只私信人，都是人在对话里随时调整的约定，不进入系统。

由此落地的原语：**例行任务**，参照 Grok Bot 的 Routine（[官方文档](https://docs.x.ai/grok-bot/skills-routines-and-automations)、[0.18 逆向重建](https://github.com/b-nnett/grok-bot-0.18-reconstructed)）。它是 Agent 自己的长期安排，由 Agent 创建、改写、暂停与删除，不经人确认；人在 Web 上可以暂停或删除。定义、调度、恢复与压缩后重述见[自动化](../运行/自动化.md)。

- **GitHub 观察是 Skill，不是系统能力。** 观察哪个仓库、哪些 PR 事件、可信推送者、合入后要不要补测，都写在项目 Skill `.claude/skills/watch-pull-requests/` 的脚本与规则里，由协调者登记例行任务按它定时检查；规则由模型总结、和人推敲后修改。系统不监听 GitHub，不暴露 GitHub webhook。
- **投递确定，判断归模型。** 每次触发是新的源头，闭环不会被上一条源头的消息总量卡住；「这次推送只是解决冲突，要不要重测」这类判断归模型。测试结果对应的代码版本由 Skill 输出的 head 提交给出，系统不判定派单或任务状态。
- **同事的运行状态可查询**，见[总览 · 稳定身份与名册](总览.md#稳定身份与名册)。是否算卡住、要不要改派由模型判断，系统不设停滞超时，也不自动终止或重派。
- **长时间任务先回应。** 被点名做长时间工作的成员，先在群里回应再开始工作，群的这一轮就不会被它挡住；以群聊提示中的可观察行为指引表达，不改调度。
- **推送与合入的分界。** Agent 可以推送自己的分支、开 PR，走普通命令授权。合入 main 或人指定的分支只能由人来做。这条边界交给远端仓库的分支保护与凭据权限，系统不解析命令来拦截合并：按 Agent 全部放行之后，命令文本拦不住，远端的保护拦得住。

实践里的半小时巡检在补三件事：群通知会漏、后台任务重复交接、卡住的成员没人发现。前两件由确定性投递与单一时间线消除，不需要巡检；第三件可以由协调者派单时安排一次性唤醒，也可以是一个例行任务，由协调者按职责选择。系统不内置巡检；Overstory 为卡住检测叠了机械存活、AI 分诊、巡逻 Agent 三层，最终归档，不走这条路。

**按「有没有人在看」防止空转。** 每次触发都是新源头，源头上限管不住例行任务。参照 Grok Bot：人长时间没有回到 Web、Agent 的未读汇报与触发次数累积到门槛时，先在该 Agent 的对话里问人要不要继续；仍无回应则暂停这个 Agent 的全部例行任务并告知，人恢复时只恢复被它暂停的那些。判据是确定性的计数与时间，人的选择由 Host 执行，模型只得知结果。

Agent 向人交付文件已落地：`send_file` 交付工作区内一个文件的副本，人在对话里下载；同事之间仍直接读工作目录。以后若要在 Agent 之间传递，也是按内容复制进对方的会话，不另建存储。

后续再定：

- **本地版本事件。** 没有远端的项目，以集成分支前进为版本；可以是例行任务按 Skill 检查集成分支，不另设事件源。需求普遍，排在 GitHub 之后。
- **触发前置条件。** 如果实测发现绝大多数触发都无事可做、成本明显，再给例行任务加一条可选的前置命令：输出不变就不叫醒模型，相当于本地的事件触发。先不做。

## 对谁说话：结尾文字的去向

规则已落地，人的输入、后台执行与回复去向的关系见[交互与响应](交互与响应.md)：长期 Agent 的普通回复直接给人看，对同事和群说话仍用显式工具；普通回复不自动交给唤醒者，文件用 `send_file` 交付。

**观察点。** 验收场景里观察普通回复在实时和刷新后是否都能直接看到，以及同事、群和例行任务开始的工作是否只通过显式协作工具影响其他 Agent。

## 人在环内

- **名册中的介入提示**：有命令授权、控制提案或交流超限等事项时，在对应 Bot 旁提示，人进入它的对话处理。
- **命令仍需授权**：worktree 只隔离文件，命令仍可能联网或写到工作区之外。保留按 Agent 的「全部放行」开关，由人逐个决定。[进程沙箱](../未开始/进程沙箱.md)让按 Agent 全部放行这一人的决定变得可以承受；授权仍由人做出，沙箱不替人批准。无人值守时授权请求堆积的程度，以实测为准。
- **停止**：单个 Agent 打断；群里不设强制停止，人对单个 Agent 的停止即是刹车。重启也不让团队停下，见[总览 · 群聊](总览.md#群聊)与[多活跃会话](../运行/多活跃会话.md)。
- **成本**：硬上限与跳数上限兜住通信失控，「有没有人在看」防护兜住例行任务空转；先在界面展示各 Agent 用量，不做金额预算。

## 记忆（之后的第一重点）

压缩之后的连续性决定长期 Agent 有没有用。团队共同维护的短笔记已落地，见[共同记忆](../上下文/共同记忆.md)；个人记忆与自动提炼仍未开始，约束见[记忆](../未开始/记忆.md)。

最具体的第一个需求来自协调者：派单记录（哪个 PR、哪个提交、派给谁）与一天里多次调整的规矩，跨天必然被压缩。实践中协调者的误判都源于记录没写清楚。它更接近 Agent 自己维护、放在 worktree 之外的笔记，而不是系统提炼的记忆。同类项目都有这一层：CCCC 在会话之外保存任务、决策、交接与每个成员的工作状态，新会话启动时先取回；Claude Code Agent Teams 有共享任务列表，任务状态同样由模型维护，常见问题是忘记标记完成。系统只提供持久位置与压缩后的取回入口，内容与状态由 Agent 维护，系统不判定。先在验收场景里观察压缩后的实际损失，再定形态。

## 落地顺序

第一版（MVP，阶段二）的范围是长期 Agent、工作区、私信、群聊与人在环内，不含回退与记忆；外部事件属于阶段三。下面的切分让多个 agent 可以并行实施。

### 协作规则

- **一个切片一个 PR，直接以 main 为 base**，不叠加 PR。
- **每个切片自带验证并删除它取代的旧路径**，不留双轨；涉及模型可见文字的，按 AGENTS.md「模型交互边界」只写可观察行为。
- **三处热点**会被多条线同时改动：Host 的请求路由、Worker 的装配、Web 后端。同一热点同时只放一个进行中的切片，或者小步合入、频繁同步 main。
- **文件夹就是进度**：Coding Bot 已有自己的架构目录；每个切片完成后，把已落地的结论写进对应架构文档，本文只留尚未落地的部分。

### 并行线

身份骨架与 A 线（工作树创建、主动 Git 历史、落地与同步、基于分支的委派、Git 变化查看）已经完成，结论见[总览](总览.md)。其余两条线内部按序号依次进行，跨线依赖在括号里注明。

**B 线：消息与身份**

B1 私信、B2 名册对模型可见与首轮自我介绍、B3 群聊后端已全部完成，当前契约见[总览](总览.md)。

**C 线：Web**

C1 去掉旧会话模型、C2 名册取代会话列表与 git 差异审阅已落地，结论见 [Web](../入口/Web.md) 与 [总览](总览.md)。

C3 通信上限上报、停止 Agent 执行 的未处理消息，与 D2 的无人查看询问由名册提示并在对应对话处理，见 [Web](../入口/Web.md)。

C4 群聊界面已落地，见 [Web](../入口/Web.md)。

**D 线：例行任务与验证闭环**（阶段三）

例行任务原语、普通回复直接给人、GitHub PR 观察 Skill、名册附带同事运行状态、例行任务的 Web 控制、「有没有人在看」和向人交付工作区文件已经落地。剩下的是阶段三验收场景，见下文。

本地版本事件与触发前置条件放在 D 线之后，见[例行任务与验证闭环](#例行任务与验证闭环)。

**E 线：转向后的修正**（依据[转向 Coding Bot 的系统审视](../../讨论/转向CodingBot审视1019.md)）

文档定位、旧目标残留删除、长期身份延续、重启与停止执行语义、项目 Skill、外部事实边界、同事工作目录只读、扩展登记跨进程安全、名册索引和协作验证地图已经落地，结论写在各自的架构文档和 verify-redpanda 里。

### 验收场景

| 阶段 | 场景 | 可以验证什么 |
|---|---|---|
| 二 | 两三个 Agent 在一个群里讨论、分工、各自落地 | 群聊这一核心玩法；人的工作目录始终不被触碰 |
| 三 | 把上文的 PR 测试团队迁到 RED PANDA：一名协调者加三名测试 Agent，协调者关注仓库 PR 事件，跑真实 PR | 与原团队对比：每轮人工介入次数、漏派与重复派单、报告到达人的时间；压缩后协调者是否还记得派单与规矩 |
| 三（含四的起点） | 在上一场景上加一名开发 Agent：它从群里接到测试问题，在自己的 worktree 里以命令调用外部 Coding Agent 实现修复，自己核对后推送到 PR，测试 Agent 再验证；合入由人决定 | 测试问题到修复推送之间是否不再需要人转发；外部执行者长时间运行时的授权、后台接管与输出回读是否可用 |

每个场景按 [verify-redpanda](../../../.claude/skills/verify-redpanda/SKILL.md) 在真实应用里验证，并同步更新它的功能地图。

## 已经排除的做法

- **所有 Agent 直接写同一棵活的工作树。** 半成品状态会干扰同事，命令对 `.git`、依赖与服务的副作用没有合并语义。
- **在系统内文件层里自造草稿层、三方合并与落地，或把 Agent 建在这样的文件层上。** 前者是在文件系统层重写 git 的分支与合并；后者的挂载、路径命名空间与进程介入，在物理 worktree 下都失去了理由。
- **回退越过外泄点，或「连带回退同事」的机制。**
- **为标准 coding agent 体验另开一条 Web 会话入口。** 它是从没与同事交流过的 Agent 的特例。
- **落地经人审批。** 与小步频繁落地矛盾；git 已提供逐次撤销。
- **合并进人当前检出的分支或工作目录。** 会撞上人未提交的改动。
- **每个群一个独立上下文。** Agent 会在不同群里分裂成不同的人，前缀也不稳定。
- **主持人模型调度发言，或靠提示词限制回复数量。**
- **按时长、内容判断 Agent 之间是否在闲聊。** 只做确定性计数。
- **对外暴露的 webhook，或由系统监听 GitHub。** GitHub 由 Agent 的例行任务按 Skill 定时检查；外部协作入口只接纳明确身份的协作者消息。
- **结尾文字自动回给唤醒者，或放宽「决策必须有产出」作为解决噪音的手段。** 理由见[对谁说话](#对谁说话结尾文字的去向)。
- **例行任务的创建与修改经人确认。** 例行任务只是到点叫醒自己；人用 Web 上的暂停与删除兜底，副作用由命令授权兜底。
- **系统内的测试执行器或验证结论判定。** CI 只是信号，验证由 Agent 按项目 skill 执行与判断。
- **系统判定任务状态或依赖。** 谁接了什么活、做完没有属于语义，由 Agent 在对话与笔记里维护；系统可以保存，不解释。
- **Agent 自行创建同事。**
- **创建时必填角色或由人编写 System Prompt。** 负责方向由人和 Agent 共同维护，Agent 可自行调整，人随时能查看与修改。
- **普通会话列表与 Agent 名册并存。**
- **把随时变化的名册直接写进 System Prompt。**

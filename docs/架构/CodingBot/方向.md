# Coding Bot 后续方向

> 方向已确认，身份骨架与工作树创建已完成，当前边界见[总览](总览.md)。本文只记尚未落地的方向、取舍与落地顺序，不是现行行为；每个切片完成后，把已落地的结论写进对应架构文档，本文只留后续部分。

## 方向

RED PANDA 从「开一个会话、做完一个任务」转向**几个长期在线的 coding Agent 在同一个项目上自由交互协作**。侧边栏列的是同事，不是历史会话：每个 Agent 有名字、自己声明的负责方向和一条持续的时间线；人可以直接找任何一个说话，Agent 之间自己交接、讨论，需要人判断时再来找人。

系统只提供原语，不预设工作流。谁做什么、何时交接、谁来协调，由人在对话里交代、由模型当场决定；任何 Agent 都可以被交代成临时协调者，协调者不是一种特殊类型。**群聊是核心玩法。**

只做 coding 场景。定时与事件驱动的长期职责（Routine）不在方向内，现有一次性定时保持原样。

## 长期 Agent

Web 的基本单位从会话换成 **Agent 名册**，不保留普通会话列表与名册两套并行。即开即用的单次会话由 TUI 承担。

- **回退只到最近一次外泄点之后**：A 在第 10 步发给 B 的消息，B 已经据此行动；把 A 退回第 8 步，B 的时间线里就留着一条 A 从未发过的消息，世界不再自洽。出问题的不是回退，而是越过了「已经被别人用过的输出」——和 git「没推送的历史可以改、推送过的不能改」同理。因此 Agent 可以把对话与文件一起回退到**最近一次外泄点**（给同事发私信、在群里发言、落地到集成分支）之后的任意一步；外泄点由 Host 从它经手的事实确定性判断，文件回退就是让 Agent 分支回到那一步的自动提交。从没和同事交流过的 Agent 可以完整回退任意一步，标准 coding agent 的会话体验就是它的特例，不另设会话入口。
- **第一版不做回退**，Web 现有的编辑消息开分支、从某一步重开随旧会话模型一起去掉，之后按上一条恢复。第一版只须守住两个前提：Agent 分支上的逐步自动提交不被压掉（落地时可以收拢成一个提交进集成分支）；私信、群发言、落地都作为事实留下。
- **一条时间线**：一个 Agent 一条长期 Session。人的私聊、同事的私信、各个群的发言按到达顺序排在同一条时间线里，靠 Compact 延续；不为每个群另开上下文。
- **创建与归属**：由人在 Web 创建，一个 Agent 属于一个项目。Agent 不创建同事；需要临时帮手时用 [SubAgent](../运行/SubAgent.md)，委派能力保留。
- **首轮自我介绍**：创建写入一条创建事实并请求一次决策，Agent 不等人开口即醒来，依据自己的名字、当前空间（只读浏览项目）与名册里已有同事的方向，向人提议自己打算负责什么。系统只写事实、触发决策；方向判断属于模型。
- **负责方向由 Agent 声明**：人在对话里认可或修正提议后，Agent 用工具记下自己的负责方向，之后也由它在对话中更新。名册展示的「负责什么」就是这份声明。不设角色表单，不让人写 System Prompt。
- **名册对模型可见的方式**：名册变化作为事实追加，从下一步可见并可重放，与能力目录同一手法；不把随时变化的名册直接写进 System Prompt，以免每次变动打穿前缀缓存。

## 工作区：每个 Agent 一条分支

多个 Agent 共用一个项目，但每个 Agent 有自己的 git worktree 与分支，不碰人自己检出的工作目录。做法参考 Claude Code「每个会话一个 worktree，改动不在主分支」。

**为什么不让所有人直接写同一棵活的工作树。** 写写冲突文件工具和受管命令大体兜得住；兜不住的是「工作区常处于别人改到一半的状态」：A 改三个文件才能对上接口，改到第一个时 B 跑测试失败，B 无从知道原因不在自己。命令还会动到 `.git`、依赖目录、运行中的服务等没有按文件合并语义的共享状态。纯共享工作树只能把这些交给模型自觉协调，系统给不出确定保证。

- **集成分支**：项目有一条本地集成分支，由 Host 在自己持有的 worktree 中合并。人自己的工作目录不被触碰，何时把集成分支合进自己的分支或推到远端由人决定。
- **落地**：何时落地是 Agent 的语义判断；落地本身由 Host 确定性执行——串行合并，能快进则快进，否则产生一个作者为该 Agent 的合并提交。合不进去时返回已知结果，由 Agent 同步、解决冲突后再落地。**落地不经人审批**：落地进的是 git，每次落地可单独撤销；鼓励的小步频繁落地与逐次审批相互矛盾。
- **同步**：Agent 想拿到同事已落地的工作时，主动把集成分支合进自己的分支，时机由它决定。同事尚未落地的改动可以直接去读，协作不必等落地。
- **Agent 内部的文件历史也用 git**：Host 在每个 Step 收口时，在该 Agent 的分支上自动提交一次。这是确定性动作，不做语义判断；审阅就是看提交差异，撤销就是退回某个提交，落地时可以把逐步提交收拢。worktree 是真实目录与真实路径，隔离是物理的，普通工具链原生可用，不需要挂载、路径命名空间或进程 hook。**第一版不建在 Agent 文件系统上**，原因见 [AgentFS 演进回顾](../../讨论/AgentFS演进回顾1018.md)。
- **每步自动提交的成本须实测**：当年 Git 方案正是卡在「每步整树哈希、多会话串行」上，见[版本操作分层](../../讨论/版本操作分层1009.md)。现在每个 Agent 有独立的 worktree 与 index，git 只重新哈希变过的文件，串行也不复存在；但大仓库、Windows 与未跟踪文件扫描下的实际耗时，第一版必须测出来。慢了先查清慢在哪里，不先加一层。
- **SubAgent 挂在 Agent 的 worktree 上**：子任务的临时工作树基于父 Agent 的分支，成果合入的是父 Agent 的分支而不是人的工作目录，因此这一步不再需要人授权。
- **要求项目是 git 仓库**；不是的先初始化。
- **已知代价**：每个 worktree 缺少被忽略的依赖与构建目录，需要各自准备；SubAgent 每次委派也要付一次检出成本。先接受，实测太痛再单独讨论。
- **文件之外的共享资源**（端口、测试数据库、开发服务器）没有合并语义，由 Agent 协商；持续进程本来按会话持有，各自在自己的 worktree 里起。

## Agent 文件系统的去留

Web 上的 Agent 第一版不使用 Agent 文件系统。它由 TUI 长期使用：TUI 是标准的单会话 coding agent，直接修改人检出的真实目录，正是 Agent 文件系统要解决的前提——改动可回退、不覆盖人的修改。TUI 目前只有模型调用的回退工具，人用的回退命令以后再补。Web 现有的文件审阅、回退与分支在被 Agent 名册替换之前仍依赖它。

git 覆盖不到、可能让 Web 上的 Agent 也需要它的信号：

- 命令改动被忽略的文件（依赖目录、构建产物、本地配置），不进 git 历史；
- 未跟踪文件被删除，git 里没有记录；
- Windows 隐藏/只读属性与 POSIX 权限；
- Agent 重新需要直接修改人检出的工作目录；
- 每个 worktree 各自准备环境的代价无法接受。

遇到这些时，先问能不能改前提——例如明确被忽略文件不在撤销承诺之内，或把保护交给[进程沙箱](../未开始/进程沙箱.md)——再考虑把 TUI 里的 Agent 文件系统接过来。直接接回等于重新爬一遍演进回顾里那架梯子。

## Agent 之间的私信

由子会话回传推广而来：任意 Agent 可以给任意同事定向发消息。

- 发送是一条 Command；Host 把消息作为外部事实写进收件人时间线，标明发送者并请求一次决策，收件人不在线就拉起它。投递身份由发送方 Command 派生，重复投递被吞掉。
- 结果只确认「已进入对方日志」，发送方不等回复；回复只是对方的另一次发送，没有请求/响应配对。
- **跳数上限**：消息按线程计跳，回复一次加一；超过上限时发送返回已知结果并上报人。这是确定性计数，不按内容或时间判断「是不是在闲聊」。
- **转述不等于同意**：授权事实只能由人在 Channel 中产生，Agent 无法替人批准。模型语义上仍可能把「对方说用户已经同意」当真，因此私信与群发言必须标明发送者，提示词明确其他 Agent 转述的同意不算数。

## 群聊（核心玩法）

- **公共记录归 Host**：群记录是群里发言的事实源，人与 Agent 的发言都先写入它，再作为外部事实投递进每个成员的时间线，标明群与发言者。成员仍只有一条时间线。
- **发言必须显式**：Agent 用工具在群里发言；它每轮结尾的普通回复留在自己时间线，不进群。发群里还是发私信由 Agent 自己判断，系统不替它选。
- **调度由 Host 确定性执行**：有 @ 只叫被点名的成员，无 @ 或 @所有人叫全体；成员依次被叫醒，后发言者能看到前面的发言。
- **发言按顺序，干活并行**：成员在群里发了言，或本轮结束没有发言（视为跳过），即算完成本轮发言，Host 接着叫下一个；发言者可以继续在自己的 worktree 里干活，干完再发言就是一条新发言。coding 的一轮可能很长，不能让整个群等它做完。
- **硬上限只在 Host 代码里**：成员数、一条人消息最多驱动的轮数与公开回复总数、每个成员每轮的发言条数、整轮无人发言即停。起步参考 Grok Bot 的数值（6 人；3 轮共 10 条；每人每轮 2 条），以实测校准。不靠提示词让 Agent 闭嘴，不设主持人模型。
- **不进群的内容**：命令授权请求与需要人判断的事项只出现在该 Agent 与人的私聊及待处理收件箱。
- **群级停止**：一键打断所有成员当前这一轮，并不再调度新轮次。停止不撤销已经完成的动作。
- **待定：一串发言怎么决策**。成员被叫醒时，时间线里往往已经排着一串群发言与私信；当前外部事实按接纳顺序一条一次决策，是否合并、怎么合并仍待定，先前的推敲与「先告诉模型还有几条未处理」的探针见[外部事实合并](../../讨论/外部事实合并0918.md)。

## 人在环内

- **跨 Agent 待处理收件箱**：汇集命令授权请求、控制提案与跳数超限上报，人不必挨个打开 Agent 查看。
- **命令仍需授权**：worktree 只隔离文件，命令仍可能联网或写到工作区之外。保留按 Agent 的「全部放行」开关，由人逐个决定。[进程沙箱](../未开始/进程沙箱.md)让按 Agent 全部放行这一人的决定变得可以承受；授权仍由人做出，沙箱不替人批准。无人值守时授权请求堆积的程度，以实测为准。
- **停止**：单个 Agent 打断与群级停止。
- **成本**：硬上限与跳数上限兜住失控；先在界面展示各 Agent 用量，不做预算。

## 记忆（之后的第一重点）

压缩之后的连续性决定长期 Agent 有没有用。记忆不进第一版，但第一版必须不堵它的路，约束只在[记忆](../未开始/记忆.md)。

## 落地顺序

第一版（MVP）的范围是上文除「回退」「记忆」之外的全部内容；TUI 的人用回退命令也不在第一版。下面的切分让多个 agent 可以并行实施。

### 协作规则

- **一个切片一个 PR，直接以 main 为 base**，不叠加 PR。
- **每个切片自带验证并删除它取代的旧路径**，不留双轨；涉及模型可见文字的，按 AGENTS.md「模型交互边界」只写可观察行为。
- **三处热点**会被多条线同时改动：Host 的请求路由、Worker 的装配、Web 后端。阶段 0 合入之前不开并行线；之后同一热点同时只放一个进行中的切片，或者小步合入、频繁同步 main。
- **文件夹就是进度**：Coding Bot 已有自己的架构目录；每个切片完成后，把已落地的结论写进对应架构文档，本文只留尚未落地的部分。

### 并行线

身份骨架与 A1 工作树创建的结论见[总览](总览.md)。骨架切片合入后，三条线可以同时开工。每条线内部按序号依次进行，跨线依赖在括号里注明。

**A 线：工作区与落地**

2. **每步自动提交**：用 Agent 分支上的 git 提交，取代现有「每个 Step 记录一次版本」在 Web Agent 下的实现；逐步提交不被压掉。必须附带大仓库、Windows 下的耗时实测。
3. **落地与同步**：模型可调用的落地与同步；Host 串行合并进集成分支，合不进去返回已知结果。
4. **SubAgent 改用 git worktree**：子工作树基于父 Agent 的分支，合入父分支不需要人授权；TUI 保留现有实现。
5. **Agent 变化查看**：会话范围的变化查询在 Web Agent 下改由 git 差异提供。

**B 线：消息与身份**

1. **私信**：发送工具 → Host 路由 → 按名字解析 → 作为外部事实写入收件人时间线，复用子会话回传那条投递路径；收件人不在线就拉起；投递身份由发送方 Command 派生；跳数上限与超限上报。
2. **名册对模型可见与首轮自我介绍**：名册变化作为事实追加；创建事实触发首次决策、只读浏览项目、提议方向；负责方向声明工具。（只依赖阶段 0，可与 B1 并行。）
3. **群聊后端**：Host 持有的群记录、群发言工具、投递进成员时间线、Host 调度（@ 选人、依次叫醒、发言或本轮结束即算完成、硬上限）、群级停止。（依赖 B1。）

**C 线：Web**

1. **删除时间旅行**：编辑消息开分支、从某一步重开，以及会话顶替关系、相关端点与界面。纯删除，不依赖阶段 0，可与它并行，但要和阶段 0 协调热点。
2. **文件审阅改为 git 差异视图**。（依赖 A5。名册已取代会话列表：选择项目创建 Agent，并用现成的运行、授权与等待事实显示状态。结论见 [Web](../入口/Web.md) 与 [总览](总览.md)。）
3. **跨 Agent 收件箱**：汇集命令授权、控制提案与跳数超限上报；批准沿用现有授权与控制入口。（跳数上报部分依赖 B1。）
4. **群聊界面**。（依赖 B3。）

## 已经排除的做法

- **所有 Agent 直接写同一棵活的工作树。** 半成品状态会干扰同事，命令对 `.git`、依赖与服务的副作用没有合并语义。
- **在 Agent 文件系统里自造草稿层、三方合并与落地，或第一版建在 Agent 文件系统上。** 前者是在文件系统层重写 git 的分支与合并；后者的挂载、路径命名空间与进程介入，在物理 worktree 下都失去了理由。
- **回退越过外泄点，或「连带回退同事」的机制。**
- **为标准 coding agent 体验另开一条 Web 会话入口。** 它是从没与同事交流过的 Agent 的特例。
- **落地经人审批。** 与小步频繁落地矛盾；git 已提供逐次撤销。
- **合并进人当前检出的分支或工作目录。** 会撞上人未提交的改动。
- **每个群一个独立上下文。** Agent 会在不同群里分裂成不同的人，前缀也不稳定。
- **主持人模型调度发言，或靠提示词限制回复数量。**
- **按时长、内容判断 Agent 之间是否在闲聊。** 只做确定性计数。
- **Routine、周期定时与 webhook 事件触发。** 不在方向内；没有鉴权也不对外暴露服务。
- **Agent 自行创建同事。**
- **角色表单或由人编写 System Prompt。** 负责方向由 Agent 提议、人认可、Agent 声明。
- **普通会话列表与 Agent 名册并存。**
- **把随时变化的名册直接写进 System Prompt。**

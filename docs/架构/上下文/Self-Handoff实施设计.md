# Self-Handoff 实施设计

为什么 Compact 是现在这个形状。当前契约与运行规则读 [Compact](Compact.md)，本文只保留设计论证，不复述规则。

## 三层与所有权

```text
完整 Journal：执行事实，持续追加
    ↓
已接纳 Handoff：不可变、有来源的语义材料
    ↓
Current ContextWindow：由切换事实重建的当前阅读视图
```

业务 Session identity、Journal、工具激活、委派关系及待处理输入保持连续。Runtime 从完整 Journal 归约执行状态，Assistant 仅改变下一次模型请求的阅读范围。压缩移出模型视图的事件不退出 Runtime 归约，不重新签发历史 Command，也不重新消费旧触发。

ContextWindow 属于 Assistant 投影，用现有的窄领域事实入口记录接纳与切换，**不增加 compact 专用的 Runtime Event 类型或语义分支**。

"某次生成了这份 handoff"是持久事实。摘要内容可能有误，但接纳后不能重新生成并覆盖原节点——可以重建窗口指向和消息组装，不能假定模型能重建字节相同或语义相同的摘要。

## 为什么要 P 和 Q 两个位置

后台生成期间 B 不停机，新事实照常写入。P 是冻结点，Q 是发布点，`(P,Q]` 期间新增的事实必须完整进入新视图，一条都不能少。

P 前的内容交给 handoff 承接，并保留原文回读入口；不再用本地 token 预算选取重叠的旧历史尾部。`(P,Q]` 完整保留是正确性要求，不受压缩触发阈值裁剪。

H 复用 Worker／执行机制，但拥有独立执行记录与决策游标。它的读取过程不作为 B 的业务对话逐轮注入，不竞争 B 的正常触发，也不拥有 B 的业务命令执行权。

## 为什么冻结整个前缀

H 的首次请求原样继承 P 处实际模型输入的 SYS、工具定义与消息，不根据随后变化的目录重新组装，也不从 Raw Journal 展开成更长的全文，后续轮次也不对冻结前缀重新做年龄脱水。

保留原生工具定义，不临时换成仅 `submit_handoff`，也不为交接新增前置 Schema。缓存复用取决于实际请求前缀和服务端条件，不因 Session identity 相同就保证命中。

**工具定义可见不等于允许执行。** 执行边界只开放交接所需的只读能力，禁止工作区修改、业务委派、控制操作和用户消息投递。回读能力必须在源会话已有的基础工具面中设计，不为此次交接临时修改冻结 `tools`，也不把只读权限判断交给提示词。

历史读取的授权范围截至 P；P 之后的业务事实由新窗口尾部承接，不偷渡进摘要覆盖范围。读取外部文件或服务不等于读取 P 时刻快照——必须保留实际来源和时间语义，不能把后来的观察写成 P 前已经发生的事实。

## 为什么不设调用上限

Harness 不设模型调用次数上限或后台任务总超时。取而代之的是 Session 级 [LoopGuard](LoopGuard.md)：从 H 自身的 Journal 检测重复行为并追加提醒，由模型自行判断下一步，命中不强制收尾或失败。

Compact 由真实输入用量达到绝对阈值触发，阈值为后续增长留余量；不另设本地输入总上限或百分比预算。内部契约违规和未知异常原样暴露，不包装成正常交接成功。

## 为什么"还差谁"要读时投影，摘要要保原证据强度

删除"上一任所有行动一律据称、接班后统一后验"的协议。统一后验把已经付出代价取得的证据全部作废，重新跑一遍才算数，成本不可接受。

改为保持原有证据强度：计划不能变成已执行，完成声明不能变成已验证，未知事项仍标为未知。遇到矛盾或关键疑点再回读，后续尾部事实可以更新或推翻摘要中的结论。

工具激活、委派与执行状态由完整 Journal 及运行对象维护，不依赖模型摘要恢复。压缩后无需重新加载已有工具，也不重置运行状态。

## 多次压缩的来源链

多次压缩读取的是"上一份 handoff + 压缩期间新增消息 + 新事实"，不声称模型重新读过全部原始历史。来源窗口及冻结材料用于说明实际阅读范围，来源链最终可以追溯到 Raw Journal 和原始 Artifact。

模型可以为关键结论附可见的来源引用，但不能猜测未展示的 Step ID。引用是回查入口，不是结论正确性的证明。Event ID 与 Step ID 保持各自身份，回读接口明确自己接收哪种位置，不混用编号。

## 已知局限

工具 Schema 本身仍占用模型上下文。历史压缩解决不了工具定义独占模型容量的问题，本轮接受这条边界，不另建卸载机制。

脚本模型与进程测试只验证机械边界，不代表真实模型的交接质量或缓存命中率已经评测完成。

# 架构总览

当前架构准绳。完整运行规则见 [Runtime](运行/Runtime.md)，跨层状态所有权见[运行语义规约](运行语义规约.md)，按变化原因分组的文档索引见 [README](../README.md)。文档与实现不一致时按实现缺陷处理，不保留双轨。

HelperMe 的运行事实在 Journal 里。模型看到的对话、人看到的一轮问答，都是投影。

> **Event 是唯一持久执行事实，State 是事件归约结果，Step 是决策推进单元，Command 是外部副作用闭环。**

## 分层

```text
console_chat.py
      │
helperme/channels/                TUI / Web / ACP / Telegram 输入、会话选择、控制命令
      │
helperme/assistant/               决策、上下文、完成判定、驱动、装配
      │
┌─────┴─────────────┬───────────────────────┐
│                   │                       │
helperme/runtime       helperme/llm + helperme/sandbox     helperme/mcp + helperme/skills + helperme/tools + helperme/cli
执行内核            模型接口 + 执行环境                 MCP / Skill / 文件命令
```

每个活跃 Session 在独立 Worker 进程中拥有自己的 Runtime、工具与 MCP 客户端、调度器和 Journal；模型调用经 Host 级 LLM Port 复用同一个 Ferro 客户端。同一 Session 的 Step 保持线性提交。详见[多活跃会话](运行/多活跃会话.md)。

下表的禁止列由 `tests/architecture/` 强制验证，是这套分层唯一能自动守住的部分。

| 包 | 职责 | 禁止 |
|---|---|---|
| `helperme/runtime` | Event、State、Step、Command、Decision 取消 | import 其他 helperme 模块 / host / plugins / tools |
| `helperme/assistant` | 模型决策、Context、Completion、Artifact、Host Supervisor、Worker 调度、产品装配 | 控制台输入输出 |
| `helperme/channels` | TUI / ACP / IM 输入输出、会话 identity、投递幂等、控制命令 | 实现模型决策或 Runtime 推进循环 |
| `helperme/llm` | 模型契约、Gateway 客户端与连接配置 | import Assistant / Runtime / Sandbox / MCP / Skills |
| `helperme/sandbox` | Workspace View、权限绑定、本地环境与进程执行 | import Assistant / Runtime / Tools / MCP / Skills |
| `helperme/mcp` | MCP Registry、Client、控制面 | 把 MCP 名词写入 Runtime；遮蔽第三方 `mcp` SDK |
| `helperme/skills` | Skill 包、安装、管理与两个普通工具 | 做成第三种执行循环 |
| `helperme/tools` | ToolSpec、参数契约、执行器、管理控制请求与环境工具 | 反向依赖 Assistant / Runtime / MCP / Skills；把控制请求当 Runtime 授权 |
| `helperme/cli` | CLI 登记、安装、体检与管理域 | 拥有执行循环；新建 subprocess 执行器 |

当前按职责分片迁移，不为了目录整齐一次性搬动稳定模块。最终目录方向见[项目架构方向](../项目架构方向.md)。

## 测试分层

按成本分层，不按目录再搬一次。默认反馈环只跑契约和进程内语义，真实进程与真模型不进日常循环；直接点名某个 process 文件时仍会跑它。

| 层 | 命令 | 守什么 |
|---|---|---|
| default | `python -m pytest` | 架构边界、类型契约、Runtime 切片、进程内 Assistant / MCP / Skill |
| process | `python -m pytest -m process` | Host Worker、Compact 后台进程、真 shell、MCP stdio/HTTP |
| all | `python -m pytest --all` | default + process |
| live | `HELPERME_RUN_LIVE_TESTS=1 python -m pytest tests/live` | 真实模型 |

新测试只守一条能说清的契约并放对层，不要为了覆盖再开一整份装配故事。存量测试不按这个标准回改。

## 一次推进

```text
UserMessageReceived
  → RUNNABLE
  → Step：模型决策 + 发出 Command
  → Dispatcher 执行工具（可并行）
  → CommandOutcomeReceived
  → 需要再决策则再开 Step
  → content-only deliver → WAITING(external_fact)
```

工具还在跑或模型还在想时，后到的文本仍是 `UserMessageReceived`，不另建 Interrupt 类型。见 [Runtime 的"用户输入与后到消息"](运行/Runtime.md#用户输入与后到消息)。

Session 是持续追加的 Event 流，没有绝对终态。一次回答结束后进入 `WAITING(external_fact)`；人继续打字只是向同一 Session 追加下一条外部事实，SubAgent 回传与自动化触发走的也是这条。任务完成属于模型、Judge 或 Host 的业务判断，不封闭 Runtime Session；归档、删除与 Worker 退出也不写成 Runtime 终态。

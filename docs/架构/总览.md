# 架构总览

当前架构准绳。完整运行规则见 [Runtime](运行/Runtime.md)，跨层状态所有权见[运行语义规约](运行语义规约.md)，按变化原因分组的文档索引见 [README](../README.md)。文档与实现不一致时按实现缺陷处理，不保留双轨。

RED PANDA 的运行事实在 Journal 里。模型看到的对话、人看到的一轮问答，都是投影。

> **Event 是唯一持久执行事实，State 是事件归约结果，Step 是决策推进单元，Command 是外部副作用闭环。**

## 分层

Channel 提供交互入口，Assistant 负责模型决策与产品装配。Runtime、模型接口、Agent 文件系统、命令执行及外部能力按各自变化原因独立组织。

| 模块 | 拥有的职责 | 边界 |
|---|---|---|
| Runtime | Event、State、Step、Command、Decision 取消 | 不依赖其他产品模块，不认识文件版本或沙箱 |
| Assistant / Host | 模型决策、上下文、完成核验、Worker 调度、产品装配与业务引用 | 不在 Runtime 中隐藏语义判断 |
| Channel | TUI / Web / ACP 输入输出、会话选择、投递幂等、控制命令 | 不实现模型决策或 Runtime 推进循环 |
| 模型接口 | 模型调用窄契约、协议编码与连接配置 | 不依赖执行与业务模块；Provider 客户端保持独立 |
| Agent 文件系统 | 文件视图、操作证据、审阅、发布与回退、子任务成果交换 | 不拥有命令进程、网络权限或沙箱生命周期，不依赖 Assistant / Runtime / Tools |
| 命令与进程执行 | 根据明确目录与环境执行命令、收集结果、取消与终止受管进程 | 消费指定文件视图，不接管文件变化历史，不替模型选择项目环境 |
| Sandbox | 进程、内存等资源、网络权限与基础文件访问限制 | 独立的执行隔离能力，可由外部模块或整个系统所在的外部环境提供 |
| MCP | Registry、Client、控制面 | 不把 MCP 名词写入 Runtime，不遮蔽第三方 SDK |
| Skills | 指令包、安装、管理与读取工具 | 不引入第三种执行循环 |
| Tools | ToolSpec、参数契约、执行器、管理控制请求与模型入口 | 消费窄契约，不反向依赖 Assistant / Runtime / MCP / Skills，不把控制请求当 Runtime 授权 |
| CLI | 登记、安装、体检与管理域 | 复用命令执行，不拥有执行循环或另建进程执行器 |

每个活跃 Session 在独立 Worker 进程中拥有自己的 Runtime、工具与 MCP 客户端、调度器和 Journal；模型调用经 Host 级 LLM Port 按 Provider 复用模型客户端，见[模型 Provider 接入](能力/模型Provider接入.md)。同一 Session 的 Step 保持线性提交。独立 Worker 是运行边界，不代表操作系统安全隔离。详见[多活跃会话](运行/多活跃会话.md)。

Agent 文件系统独立拥有文件视图、变化证据与回退语义，原生文件管理服务依赖底层 VFS 库；业务意图与会话引用归 Assistant / Host，见[Agent 文件系统总览](Agent文件系统/总览.md)。命令执行与文件视图的接合见[执行环境](能力/执行环境.md)。

Agent 文件系统可以在本机或沙箱内运行。沙箱可以只包住任务进程，也可以在系统外包住整个 Agent；其创建、重建或销毁不决定文件成果和审计历史的保留。会话、Worker、沙箱与文件历史不要求共享生命周期。

当前文件审计、回退与本机执行已落地，文件能力与命令执行已独立组织。文件工具直接消费文件范围和文件能力，不经命令执行附件访问文件系统；命令工具分别消费文件访问与命令执行能力，由 Assistant 装配。两类底层能力互不依赖，代码依赖约束以架构测试为事实源。完整执行隔离和沙箱接入仍在[未开始](未开始/进程沙箱.md)，后续方向见[项目架构方向](../项目架构方向.md)。

命令保留按操作分流：独立只读操作读已发布宿主，可能写入的操作整次使用挂载视图。Windows 受管任务通过进程 hook 拒绝直接写入宿主工作区，必要接入失败即阻止执行，先回收任务进程再结束文件操作；支持范围与其他平台边界见[命令文件视图接入](能力/命令文件视图接入.md)。

## 测试分层

按成本分层，不按目录再搬一次。默认反馈环只跑契约和进程内语义，真实进程与真模型不进日常循环；直接点名某个 process 文件时仍会跑它。

| 层 | 命令 | 守什么 |
|---|---|---|
| default | `python -m pytest` | 架构边界、类型契约、Runtime 切片、进程内 Assistant / MCP / Skill |
| process | `python -m pytest -m process` | Host Worker、Compact 后台进程、真 shell、MCP stdio/HTTP |
| all | `python -m pytest --all` | default + process |
| live | `REDPANDA_RUN_LIVE_TESTS=1 python -m pytest tests/live` | 真实模型 |

新测试只守一条能说清的契约并放对层，不要为了覆盖再开一整份装配故事。存量测试不按这个标准回改。

## 一次推进

```text
UserMessageReceived
  → RUNNABLE
  → Step：模型决策 + 发出 Command
  → Dispatcher 执行工具（可并行）
  → CommandOutcomeReceived
  → 需要再决策则再开 Step
  → content-only deliver → WAITING(external_fact)
```

工具还在跑或模型还在想时，后到的文本仍是 `UserMessageReceived`，不另建 Interrupt 类型。见 [Runtime 的"用户输入与后到消息"](运行/Runtime.md#用户输入与后到消息)。

Session 是持续追加的 Event 流，没有绝对终态。一次回答结束后进入 `WAITING(external_fact)`；人继续打字只是向同一 Session 追加下一条外部事实，SubAgent 回传与自动化触发走的也是这条。任务完成属于模型、Judge 或 Host 的业务判断，不封闭 Runtime Session；归档、删除与 Worker 退出也不写成 Runtime 终态。

## 产品规则（判定）

[工作计划](上下文/工作计划.md)由模型按需维护，成功工具结果是进度事实，模型上下文与 Channel 读取同一投影。计划不参与 Runtime 调度，也不作为完成证明；收尾由模型依据最新要求与工具证据核验。当前没有独立 Goal / Criteria 状态，也不从 Host 内存向 Decision Context 注入可变判定标准。人的目标和后续修正都以有序 `UserMessageReceived` 表达。未来引入 Judge 时再单独定义事实、identity 与所有者。

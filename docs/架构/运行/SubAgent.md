# SubAgent

> SubAgent 是一次性的异步函数式 Session：父 Agent 传入任务，子 Agent 独立执行并通过 `report` 返回结果；父也可以主动 `reclaim` 收回还在工作的子。之后不能继续交互。

父子 Session 在独立进程与独立 Journal 中推进，实现边界见[多活跃会话](多活跃会话.md)。

子 Session 是普通独立 Session：同一套创建、推进、恢复，自己的 Journal 与判定。父子关系只存在于 Assistant 侧，用因果事实表达，**Runtime 不增加 `parent_session_id` 或 `agent_type`**。

子 Session 的上下文也按普通 Session 压缩；后台交接只读它自身的冻结来源。交回或收回是窗口发布的截止边界，交接失败且容量耗尽则带原始原因交回父 Agent。具体窗口规则见 [Compact](../上下文/Compact.md)。

## 为什么要有它

**上下文隔离是主要理由，并行是次要理由。** 整个上下文模块都在一条 Session 内部跟上下文膨胀作战——预算、保护窗、体积外置、脱水，见 [上下文](../上下文/上下文投影.md)；摘要则走独立的 [Compact](../上下文/Compact.md) 后台换会话机制。SubAgent 从另一个方向解同一个问题：让中间过程根本不发生在父的 Journal 里。

所以全部设计围绕一件事——**父只拿结论，不拿过程**。任何一处冒泡都会漏掉隔离，这也是下面那些"不外露"约束的共同来源。

## 类比在哪里会失准

上面那句是准确的接口描述，但「函数」这个类比有三处不覆盖，而这三处正是实现里最容易出错的地方。

**返回值有四种，不是一种。** 父拿到的永远是同一条 report 事实，但它表达四件不同的事：子成功交回结论；子没跑完（带 failure）；子静止了但从没调用 `report`；父主动收回。前三种是子自己的终局，第四种是父已经做过的判断。**取消不是失败**，父不应按「要不要重派这次失败」去读它。

failure 有三种来源，形状相同：已识别的模型失败装原文；未知异常装类型、消息和 traceback，**不改写成友好句**；恢复发现未完成 Attempt 时记录执行中断、结果未知及相关 Command，不虚构异常原因。父是 Judge，重派、换做法还是如实告诉用户，由它读了原因再定。

未知异常仍会结束子 Worker，并由 Host 把同一份原始失败亮给 Channel；report 只是补一条父能看见的机械终局，不是把异常降级成普通 Outcome，也不自动重试。

**「一次性」是投递幂等的性质，不是生命周期的性质。** 子 Session 不会被关闭，正常交回结论后停在 `WAITING(external_fact)`。真正保证「最多回收一次」的是回收事实使用由子 Session 身份确定性派生的投递 id：同一个子第二次回收会被 Journal 的投递幂等吞掉。代价是失败的子即使又被推进并再次静止，第二条终局也不会被看见。

**「传入任务」不是参数传递，是一条事实。** 任务以独立的任务事实进入子自己的 Journal，**不伪装成用户消息**。子因此知道另一端没有人，`report` 是唯一出口。父没有追问的通道，所以任务描述必须自包含——`delegate` 的参数说明里写明「它看不到当前对话，所需背景必须写在这里」。父要停掉一个还在工作的子，用的是收回，不是追问。

## 委派与回收

```text
父 Step: delegate(task)
  → delegate Command 随 Step 提交（同一步的全部委派此时已经可见）
  → 子 id 由 command id 确定性派生
  → handler 幂等确保子 Journal 与任务事实原子存在
  → 启动子 Worker
  → Outcome 只确认「子 Session 已存在」
  → 父继续，不阻塞

子独立推进 …
  → report、已识别失败，或未知异常
  → 子 Journal 先写入回传
  → Host 投递 report 进父 Journal（请求决策）
  → 唤醒父

父 Step: reclaim(child_session_id)
  → Host 停掉子 Worker，不等它自己静止
  → 子 Journal 在无 Writer 时写入取消终局（已有终局则沿用先写入的那条）
  → 同一条 report 进父 Journal（取消时不请求决策）
  → 待回收集合少一个
```

用户插话之后父决定停，和父看了别的结果后觉得这个子参数不对、已经不需要，是同一种 `reclaim`。**Runtime 不从文本推断「停」。**

取消这条 report 不单独要 Step：判断已经在发出 `reclaim` 的那次决策里做完了。子自己交回的结论仍要唤醒父。已经回收过的再 `reclaim` 返回明确的"已回收"结果。同一 Step 里收回旧的、再委派新的，合法；新子 id 绑在新的 command id 上。

Host 停子是 Worker 回收，不改变 Session 状态。子的写只落在自己的临时工作树里，没被合入就等于没发生，所以半途停下也没有外部副作用要补偿。与子自己 `report` 的竞态交给投递幂等：同一个投递 id 只接纳一次，先写入的终局胜出。

**委派必须异步。** `delegate` 的 Outcome 只是「子 Session 已存在」，结论经外部事实入口回到父。同步版本会把一条可能活很久的独立生命线塞进一个 Attempt 的生命周期。

### 为什么子 id 从 command id 派生

子 id 派生自委派命令（`{parent}/sub-{command_id}`），重放同一条命令不会造出第二个子 Session。父侧的"已委派"从**已提交的 delegate Command** 投影，不等待 Outcome；Outcome 只证明物化结果。

这保证父 Worker 在创建子之后、Outcome 入账之前崩溃时，恢复仍能从自己的 Journal 找到准确的 child id。

这是对 unknown Attempt 提供窄恢复协议的领域特例，不改变 Runtime 通则：任务事实精确记录任务、父身份与委派命令，其 Session identity 必须等于派生值。恢复只检查这个确定的 child id——匹配则补交已知"存在"结果，原子确认不存在则幂等创建，身份或内容冲突直接失败。它不按时间猜测、不扫描无关 Session，也不重新执行一个身份不明的外部操作。

### 回收挂点

调度器的静止与已识别失败、Worker 在未知异常退出前的回收、新 Worker 接管后的中断回传，以及父发出的 `reclaim`。

**未知异常不进调度器的失败回调**——那会把它降级成普通失败。子 Worker 的外层异常边界覆盖配置、装配、客户端进入及运行阶段：先写入回传，再单向交给 Host 投递，不依赖 Worker 的 IPC 接收循环，也不在异常路径等待回复。租约丢失是接管，不是这条生命线失败，不回收。

漏接这些终局，父会拿着一个永远清不空的待回收集合干等。通知父「这条路断了」不是把未知异常变成 Runtime Outcome，也不是自动重试：已开始的 Attempt 仍是 unknown，Worker 照死，Host 照亮原始失败。

### 子什么时候算做完

子 Session 是**没有人的 Session**：父落到 `WAITING(external_fact)` 时真的有人会再说话，子落到同样状态则没人会来。等待理由只说"在等一条外部事实"，不说那头是谁——判断有没有人是这里的事，不是 Runtime 的事。

由此得到纯机械的判据，不问模型做完没有，只看它还有没有事做：只等用户消息 = 本轮产出完毕，可以回收；卡在等授权不是完成；还在等命令结果就继续等。

## 结论不齐时的约束

一个 Step 里可以发多次 `delegate`，每个子只写自己的工作树、互不感知，并行不会踩到父或兄弟的文件。但结论不是一次性交付的：每个子静止就单独回收一次，父被逐条唤醒。Runtime 的批次约束只覆盖同一 Step 的工具调用组，跨 Session 回灌的事实不在其中；System Prompt 里也没有任何一句让父等齐子。没有别的机制会替父攒齐。

所以父在决策时从自己已冻结的事实里投影出待回收集合（已提交的 delegate Command − 已确定创建失败 − 已回收）。unknown 创建 Attempt 仍保留在集合中，由稳定 child id 的窄恢复协议核对。

集合非空就往 System Prompt 追加一句约束，只说结论还没齐、不要把已回来的部分当成全部，以及不再需要时收回它；**不说「还差几个」**，也不要求必须等齐才能作答。带上计数会让 System Prompt 每收到一条结论就变一次，整段 prefix 缓存跟着失效。

**「还差谁」是派生值，不冻进事实。** 回收事实只记这个子自己的终局。若把计数算好写进事实，两个并行的子就必须在父维度串行读写才算得对：它们几乎同时静止，各自读父 Journal 再写入，无锁时都读到对方写入前的状态，双双报「还差一个」，父永远等不到 0。改成读时投影，事实只述自己、聚合留给读方，这个约束和那把锁一起消失。

读时投影还保证口径与决策一致：它读的是决策冻结位置的那份事实，和 Decision Context 同一个边界。重放一次早先的决策，那次子还没回来，约束照旧出现。

漏人由提交边界消除，而不是靠调度时序避免。一个 Step 的全部 delegate Command 原子提交后，父侧投影已经能看见所有 child id；子 Worker 只能在各自 Command 已提交后启动。极快的子即使在兄弟 Outcome 之前回收，父投影仍知道全部兄弟。测试应覆盖这个交错，但**测试让出控制权不是正确性的前提**。

## 能力边界

子 Session 能看见哪些内建工具，由一份**显式列举**的名单决定，而不是排除危险工具：新增任何工具默认进不来，要进必须有人明确加。

`execute_command` 永远不在其中——一条命令会做什么无法静态判断，名单之外的边界要等[进程沙箱](../未开始/进程沙箱.md)。`delegate` 和 `reclaim` 也不在其中，递归委派和收回兄弟因此被同一份名单挡住。

**写文件在其中，但它写的不是用户的世界。** 子的任务根是自己的临时工作树，改动必须经父验收并合入才出得来，见[可写子会话](可写子会话.md)。子的写因此不需要授权——那个盒子里没有东西值得问人；该被问的是父的合入，那一下才改变用户打开的目录。

子也能回退自己的文件，沿用普通 Session 的版本记录与调用坐标。回退只推进自己的轨道，不改动父的文件或工作区 HEAD。

**名单只管内建与控制工具，管不了 MCP**，运行时才知道的目录装不进一份写死的集合。这两半用两套机制，不强行并成一套：内建工具的效果与路径边界是我们自己写的代码，本来就是已知契约，继续显式列举；MCP 工具的只读性是安装那个 Server 时记下的决定，边界靠**子 Session 的目录里只有只读 Server** 来守，见[工具与能力 · 只读是安装时的声明](../能力/工具与能力.md#只读是安装时的声明)。加载成功的 MCP 工具不再经过内建名单过滤。两套机制的共同性质没变：谁都不默认进来，要进必须有人明确加。

子 Session 因此也走渐进加载，和父同一条路——开工只看见目录和 `load_toolset`，点名后下一个 Step 才拿到具体工具。这多烧子一个 Step，而子没有人可等，成本全算进委派延迟。**接受它，不为子另造一套「委派时由父冻结能力面」**：那是第二套能力面机制，一致性比省一个 Step 值钱，而且父点名给什么会让名单的作者从代码变成父模型，安全边界不能这么建。目录 revision 变化对子也不特殊处理，父那套规则照用。

**名单不是授权闸的替代品，两者守的不是同一件事。** 名单守「子能不能看见这个工具」，授权守「这次调用要不要问人」。父 Session 的写工具标了需要授权，见 [Command 授权](../入口/Command授权.md)；子没有人在回路里，所以它的能力面必须在看见这一层就是安全的，不能指望调用时有人拦。**委派只能衰减**：父不能给子自己没有的能力，能出盒子的路径只有一条，而且窄于父自己那条。

**单写者是委派树内的不变量，不是全局不变量。** 分界在于并行由谁制造：父决定开几个子，这个并行是 Agent 造的，用户没参与，Agent 必须为它负责；用户同时开两条顶层 Session 是在开两个完整任务，写冲突是用户的选择，Agent 不替他兜底。`get_changes` 的契约因此不需要改——它本就只报告工作区快照、明确不做变更归因；要约束的是子写在哪里，不是它报告什么。

这道边界是**安全性质**，所以进程内的父子缓存必须能从 Journal 认回来，否则重启后子 Session 就拿到父的能力面和父的工作树了。**两个方向都要认**：恢复父时从它已提交的 delegate Command 找出子，并经 Host 请求恢复未回收的那些；恢复子时从它自己的任务事实找回父。只做前者的话，直接 `/resume` 一个子 Session 就绕过了整道边界。

子 Session 换用独立的 System Prompt：它不碰管理面，那份 catalog 不拼；Toolset 目录要拼，但只含只读 Server。

## 对外不可见

子 Session 的 `deliver` 变成空操作，正文留在子自己的 Journal 里。失败提示同样不外露：子 Session 的失败信号被吞掉。用户该看到的是父转述后的判断，而不是一条不知来处的裸错误。父自己失败仍照常送达——**拦的是子，不是所有失败**。

唯一外露的是一个活动指示，供 Channel 显示「子 Agent 工作中」。它读的是进程内缓存而不是 Journal 投影，且异步发出——**这条线只管显示，不进入委派与回收的执行闭环**。执行判断始终从 Journal 投影。两者不混用：显示可以丢、可以过期，执行判断不行。

## 不做

- 让子 Session 再委派（递归）
- 让用户看到子的过程正文（只给一个「工作中」的布尔指示），或让子访问父的上下文与 Journal
- 把父子关系写进 Runtime State
- 给 Session 增加绝对终态来表达「子做完了」或「子被收回了」
- 把「还差几个」冻进回收事实
- 把父收回做成 Runtime 通用 Cancel，或从用户文本推断该停哪些子
- 为子另造一套委派时冻结的能力面，或让父点名子能用哪些工具

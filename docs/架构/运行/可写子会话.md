# 可写子会话

> 子 Session 在自己的临时工作树里改文件，父验收后显式合入工作区。文件工具和命令使用同一任务文件视图；进程安全隔离另见[进程沙箱](../未开始/进程沙箱.md)。

## 为什么把文件状态与进程隔离拆开

独立文件视图给并行改动提供一个不污染父工作区的地方，文件工具和视图内的命令写入都能捕获实际结果。它不限制进程访问宿主机：命令仍继承真实开发环境，绝对路径和外部副作用不会因为 cwd 投影而被隔离。文件状态回退可以先落地，不能因此宣称进程安全隔离已经完成。

**写文件缺的从来不是隔离，是一个能装下并行改动、又不污染用户目录的地方。**

## 文件世界的形状

**日常文件历史与成果比较分开。** 父子各自按任务根使用文件视图与操作历史；Git 引用只保存委派基准和成果比较坐标，不参与日常 Step 快照。

**回退与合入都由显式调用发起。** 回退见[工作区版本](工作区版本.md)；合入接受一次委派的成果，之后仍在普通 Step 边界记录。不提供切换子轨道的入口，因此也不需要向模型暴露跨线的版本坐标。

**子借工作区的身份，换自己的工作树。** 对象库由工作区身份决定，任务根是另一回事。子沿用父的工作区身份，两边的对象天然在同一个库里，三方合并不必跨库搬运；子的任务根指向自己的临时工作树，写工具因此被今天约束父的**同一套**路径边界关住，不新增任何安全机制。

子使用的是该委派的临时文件视图，不登记成用户可选择的新工作区。父子共享成果比较对象库，各自的文件视图存储独立；共享比较存储不意味着共享当前文件状态。

**子永远不继承 `full_access`。** 这是上一条能成立的前提，不是保守配置。工作区开了整机访问时，Workspace View 会把宿主机的所有根挂进来并授予读写；子若继承，「关在临时工作树里」当场作废，它能写到任何地方。父开没开整机访问，都不改变子只有一个根这件事——这正是「委派只能衰减」在文件层的具体形态。

**子也在 Step 边界记自己的操作位置。** 它是普通 Session，走同一套记录规则，没有特例，能回退自己的文件。成果比较只在已交回的子工作树上显式建立，不把每一步的文件视图位置当成 Git 提交。

初次委派冻结父的文件基准，再从基准物化子工作树。重放与恢复沿用这个基准和已经存在的工作树，不把子的改动重置成恢复时父的状态。成果复制与比较遵守工作区忽略规则，包括父任务根的本地排除规则；日常回退仍捕获所有视图内的助手变化。这两项能力的范围不能混为一谈。

**独立子工作树只服务于 Agent 造的并行。** 父派几个子是 Agent 自己的决定，Agent 要为它负责，所以给每个子一棵独立工作树；用户同时开两条顶层会话是用户的选择，它们共用任务根及其操作历史，助手的接受与发布按任务根串行。这是 [SubAgent · 能力边界](SubAgent.md#能力边界)里「单写者是委派树内的不变量，不是全局不变量」在文件层的投影；它不把用户直接修改纳入助手串行锁。

**用户的项目目录反映已发布的变化及用户直接修改。** 候选尚未接受和发布时不改用户任务根。子的工作树落在产品数据目录下，用户不看它——他等的是父的结论。

**合入的坐标是会话，不是版本。** 父说的是「接受这次委派的成果」，引用自己已提交的 delegate Command，和回滚引用 `tool_call_id` 是同一个形状。**版本标识仍然谁都看不到。**

**合入是一次普通写入。** HEAD 属于工作区，所以合入对共享该工作区的其他会话立刻可见，和任何一次文件修改一样。它在 Step 边界正常留下新的一版，不为它新开例外。

## 子的写不需要授权，父的合入需要

父的写工具靠人逐条授权兜住；子没有人在回路里，这曾经是「子不能写」的理由，见 [Command 授权](../入口/Command授权.md)。

但**子写进一个用户看不见、且必须经父与人批准才能出来的盒子，没有东西需要被授权**。闸没有被拆掉，它挪到了效果真正发生的那一刻：父的合入，那一下改变的是用户打开的目录。从每次写一问收敛成每次委派一问，人的注意力反而省了。

这同时让「委派只能衰减」成立：子的写比父的写更窄，不是更宽，父没法让子越过自己去改用户的世界。

## 父怎么验收

**父按会话坐标主动拉取，diff 不由子交付。** 子的 report 只装自然语言结论和 failure，不夹带任何机器坐标——父本来就知道自己派了谁。

这解掉了「父只拿结论、不拿过程」和「父要看 diff 才能决定收不收」的冲突。冲突来自「过程」一词指了两件事：子的推理与探索绝不能给父，那是上下文隔离的全部意义；而 diff 不是子怎么想出来的记录，是两个坐标之间的现场比较，**在父要它之前根本不存在**。子甚至不需要知道 diff 是什么。

**验收是多轮的。** 一次把全部改动塞进 report 必然出问题：大小完全由子的行为决定，父对它没有控制权，而父在收到结论的那一刻还没决定要不要看。拉取把控制权还给父——先看动了哪些文件，再挑着看，再决定收不收。

比较用单独的工具，不给 `get_changes` 加参数。那个工具的契约是「代码基线到当前工作区」，连变更归因都特意不做，见[工具与能力 · 变更证据的职责边界](../能力/工具与能力.md#变更证据的职责边界)。

验收与合入只接受当前父已经提交、子已经交回的委派。文件取自显式记录的子工作树成果，不凭 report 的正文决定；记录失败明确暴露，不换到另一个坐标。合入在父的文件视图中执行，其文件效果与普通文件修改一样封存、发布并可回退。合入独占一个调用批次，避免同批普通写入与合入相互交错。

## 合入冲突

委派是异步的，父不阻塞，所以父很可能在子工作期间改了同一个文件。

**合入失败时不把冲突标记物化进父的工作树。** 父可能正忙别的事，在它没准备好的时候塞一个烂摊子过去，和「恢复失败不留半吊子状态」也相悖。失败只返回冲突清单。

父拿到清单后有三条路，都不需要新机制：自己改；放弃；**再派一个子去解冲突**——给那个子一棵带冲突标记的工作树，它和任何一个可写子会话没有区别。第三条是这套设计自己长出来的，不是为它开的特例。

## 子工作树的生命周期

从合入基准那一版 checkout 出来，落在产品数据目录下。

**不跟子 Session 走**：子 report 之后父还要比较和合入，那时子已经结束了。跟父 Session 走，父归档时一起清。代价是长期活着的父会攒下副本，占用等于委派次数乘以仓库大小——先接受，真的疼了再谈回收。

归档先停止父与仍在工作的子，等待文件操作静止，再清理子工作树。清理的是临时副本，不回收共享对象库里的历史。

## 不做

- 用工作树隔离换执行权限。隔离文件和限制进程是两个问题，`execute_command` 仍然等[进程沙箱](../未开始/进程沙箱.md)。
- 做「受限的 `execute_command`」。一个能跑一部分命令的执行口，安全边界比只读名单更难说清。
- 让子 report 带上分支、版本或任何机器坐标。
- 引入用户可切换的工作区分支。
- 给人类会话开文件分支。用户没有「主线」这个概念，哪条会话活着哪条就是现实，所以分出去的文件世界没有合回来的动作。
- 让人在界面上挑两条线合并。人的入口必须是零歧义的坐标；「回到这一刻」是，「把这两条线合起来」不是，后者要理解两边各改了什么。
- 从顶层会话分支自动派生独立工作树。会话重开与文件回退仍遵守[工作区版本](工作区版本.md)。

# 多活跃会话

## 决策

Session 是执行隔离单元，也是持久化隔离单元。每个活跃 Session 在独立操作系统进程中装配一套完整实例：Runtime、事件循环、工具与 MCP 客户端、Session 投影缓存，以及只属于它的 Journal。模型客户端不在 Worker 内，Worker 通过 Host 级 LLM Port 调用按 Provider 复用的模型客户端。一个 Worker 不承载第二条 Session。

```text
Channel / SubAgent 回传
          │
          ▼
Host Supervisor
  Shared LLM Client (selected Provider)
  ├─ Session A Worker ─ Runtime ─ Journal A
  ├─ Session B Worker ─ Runtime ─ Journal B
  └─ Session C Worker ─ Runtime ─ Journal C
```

**Runtime 是否静止与 Worker 是否驻留是两件事。** Channel 用稳定 owner identity 显式选择当前 Session，Host 据此决定空闲 Worker 的驻留。没有 owner 选择的 Session 不占用空闲进程，Journal 始终保留生命线。

进程边界保证一个 Session 内的同步阻塞、事件循环停顿和未预期异常不会暂停其他 Session。Session 内部仍按 Runtime 契约推进：Step 线性提交，同一 Step 的 Command 可以并行。这次改造不把每次工具调用再拆成独立进程。

## Host 与 Worker

Host Supervisor 只负责机械职责：定位持久目录、保证同一时刻至多一个对应 Worker、把外部事实与唤醒请求送到 Worker、接收输出与失败信号、在父子 Session 之间路由带稳定投递身份的回传，以及维护 owner 选择与不进 Journal 的 Session 元数据（暂停、总闸）。

**Host 不读取事实含义，不归约 Runtime State，也不决定任务是否完成。** 可否继续推进、一次 Step 看见哪些事实、Command 是否已经终结，仍由目标 Session 的 Runtime 和 Journal 决定。对外的 `session_activity` 只跟调度器是否真正在推进，不因 `select` / `view` 这类应用请求报运行中。

## 进程身份

Host 拉起 Worker，给的不只是「又一个进程」，而是「这个进程在这台电脑上按谁的日常环境干活」。

两件事不要混：

- **你是谁**：本地启动就沿用当前操作系统用户。谁有权读写文件、跑命令，跟这个用户走。
- **用哪套环境**：标准输入输出、环境变量，以及靠环境变量找程序（最常见是 `PATH` 里找 PowerShell、git）。这一套必须是你平时在这台电脑上开终端时用的，不能是 Obsidian、编辑器或其他 Channel 客户端自己带着的。

Channel 只负责传话。以前 TUI 没踩坑，是因为它碰巧从你的终端里起来，进程环境和日常终端差不多。编辑器拉起 ACP 之后这个巧合不在了：管道是给协议用的，环境变量也可能是编辑器的。

因此：

- Worker 的标准输入输出不能接着 Channel 的管道。协议帧会写乱；在 Windows 上，没有控制台时子进程甚至起不来。
- Worker 的环境变量必须是本机用户平时那一份。Channel 配置里多出来的变量可以叠加上去，但不能拿客户端的环境当底座。
- ACP、TUI、Web，以及 SubAgent、后台压缩，都走同一套启动，不为某一种入口单独开例外。
- Sandbox 继续假定「当前进程就是本机环境」。环境不对，应在 Host 启动进程时报出来，不要到更里面才说「这台机器没有 PowerShell」。

Windows 上 Host 启动时用当前用户的会话环境补全进程环境：已有变量留下，`PATH` 以当前为前缀再补上用户会话里缺的目录，构造失败按外部操作系统错误暴露。POSIX 暂不另造一份 login 环境，等那边有实测再补。

## Worker 生命周期

Worker 启动后只处理一个 Session：打开它的 Journal，重建 Runtime 与 Assistant 投影，接纳本次请求并推进到静止。

存在未结束的模型调用或 Command 时 Worker 保持存活；静止后只要仍被任一 owner 选择就继续驻留并复用 MCP 客户端。待确认的管理提案活在 Journal 里，**不要求 Worker 为了保住内存态而拒绝 idle**。

未预期异常直接结束 Worker 并由 Host 暴露。Host 不把它转换为普通失败，也不因 Session 仍被选择而自动重启；下一次真实请求才从 Journal 恢复，待裁决提案也从同一份事件重放得出。恢复不会自动重试已经开始但没有 Outcome 的 Attempt。

Worker 异常退出时 Host 还要做一轮**展示清理**：终结旧 generation 的对外活动、中止活动 preview、清除精确的 live activity 并通知 Channel 重拉 Journal。这些都是展示清理，不能补写 Command Outcome。

停止采用静止通知与确认握手：Host 有尚未确认的应用请求时不批准停止，Worker 确认期间若又有活动会拒绝停止。多 Channel 使用各自 owner identity，一个 Session 只要仍被任一 owner 选择就继续驻留。Windows 下 Worker 纳入 Host 持有的 Job Object，Host 退出时其 Worker 一起结束，避免重启后遗留旧写入者。

Host 重启后**只恢复显式选中的 Session**，不扫描并自动恢复全部历史 Session。

## IPC 边界

IPC 只承载应用请求和生命周期信号，不复制 Runtime 内部状态。**事实必须先由目标 Worker 可靠写入自己的 Journal，Host 才能确认投递成功。**

父主动收回是例外：Host 先停掉该子 Worker，再在没有 Writer 时写入取消终局，然后把同一条 report 投递给父。

出入口保持窄而明确：Host 向 Worker 发送新建、投递、授权、取消或无新事实的恢复唤醒；Worker 向 Host 返回投递已接纳、对外输出、静止或失败，并经同一条 pipe 发出模型调用。失败信号保留异常类型、消息和 traceback，**不把异常改写成 Runtime Outcome**。Worker 启动中或退出中到达的投递由 Host 等待该次状态转换后送入同一个 Session，未写入 Journal 前不向调用方确认。

## 每 Session 一个 Journal

```text
~/.helperme/runtime_sessions/<session-key>/journal.sqlite
```

`session-key` 是 Session identity 的稳定、文件系统安全映射，Journal 内仍保存并校验原始 identity。目录存在即表示这条生命线存在，不另建全局 Journal 或第二份事实目录。

每个 Journal 只保存一条 Session，因而不同 Session 不再竞争同一个写锁，Checkpoint、claim 和恢复也不会扫描无关会话。

配置、Skill 和 MCP Registry 仍是产品级资源。Workspace 是会话级绑定的沙箱边界：一条会话只属于一个工作区，Worker 装配时按该会话的绑定读取根集合。多个顶层 Session 对同一 Workspace 的写入来自用户选择，不由 Agent 增加跨 Session 协调。

## 父子 Session

SubAgent 仍是普通 Session，使用相同的 Worker 和 Journal 边界。父子关系由 Assistant 事实表达，不进入 Runtime State。

```text
父提交 delegate Command（child id 已确定，父侧委派关系已经可投影）
  → Host 按该 id 幂等确保子 Session 与任务事实存在并启动
  → delegate Outcome 只确认子 Session 已存在
  → 父静止，父 Worker 可以退出
  → 子静止并形成 report
  → Host 启动父 Worker（如果尚未运行）
  → 父 Worker 将 report 可靠写入父 Journal 并继续推进
```

**父进程不等待或持有子进程。** 结论是否收齐由父模型根据已提交事实判断，父也可以主动收回还在工作的子。Host 只用稳定投递身份保证每个子结论最多回收一次。

子回传内容先保存在子 Journal，再通过 Host 投递到父 Journal；恢复子 Session 时重投同一份内容，父按稳定投递身份去重。恢复父 Session 时，Assistant 从已提交的 delegate Command 与回收事实找出未回收的子，分别请求恢复，**不扫描无关 Session**。

## 租约与接管

租约用于 Worker 崩溃后的接管，**不把正常但暂时停顿的 owner 判成失败**：

- 到期只表示新的 Worker 可以竞争接管；
- 成功接管必须产生更高的 generation；
- 续租和提交以当前身份（token + owner + generation）为准；
- 没有发生接管时，原 Worker 在到期后恢复，仍可续租或提交；
- 原 Worker 提交与新 Worker 接管由同一 Journal 事务决定先后，只有一个能成为有效写入者。

Attempt 已经开始而 Worker 在 Outcome 入账前退出时仍保持 unknown。**时间经过本身不能制造 unknown，恢复也不能据此盲目重试外部副作用。**

### SubAgent 中断回传

新 Worker 独占接管后，如果子 Session 尚无回传、但存在已开始且未记录 Outcome 的 Command，就在子 Journal 追加中断回传：说明执行结果未知、未自动重试，并列出相关 Command。原 Attempt、已完成结果和其他事件全部保留，不删除、不回退，也不伪造 Outcome。

回传复用普通的回传通道，父侧接纳后请求模型决策。已有回传优先，恢复只按原投递身份幂等重投，子会话不再调用模型或执行工具。

本阶段只保证父 Session 知道中断，由父模型决定后续行动，**不设计子会话续跑或通用恢复协议**。

### 子 Session 的未知异常

子 Worker 在未知异常退出前先把回传写入自己的 Journal，单向通知 Host 负责投递，并暴露原始失败。Worker 不等待投递回复；Host 先释放死掉的 Worker，再完成回传。这不是把异常改写成 Runtime Outcome，也不自动重试。

异常回传**不要求完整 Assistant 已装配**：新建子 Session 时任务事实与 Journal 一起原子建立，保证首次初始化失败也能找回父身份；持久化完成后才允许 Host 启动子 Worker。Journal 无法读取或写入时不伪造回传事实；回传本身再失败则同时保留原异常与回传异常。

进程被直接杀掉、没走到这段回收时，父侧待回收集合仍在，要显式 `/resume` 才按上面的中断规则重建。

## 不负责

- 协调用户主动创建的多个顶层 Session 对同一 Workspace 的写入；
- 隔离操作系统、磁盘、网络或外部服务自身的容量限制；
- 让多个 Host 或多台机器共同竞争同一条 Session；
- 为旧的全局 Journal 保留双轨、fallback 或长期兼容层。

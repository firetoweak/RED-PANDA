# 外部事实要不要合并成一次决策（2026-09-18）

> 状态：**未决策，当前选择不做。** 准绳仍以 [Runtime](../架构/运行/Runtime.md) 的「决策一致性」和「用户输入与后到消息」为准：外部事实按 Journal 的接纳顺序逐条消费。本篇记录一次推敲，不是第二份准绳。
>
> 2026-10-20 后续：人的待处理输入已落地为成批进入下一次决策，见 [人的输入成批](人的输入成批1020.md)。其他来源之间仍按本篇结论逐条消费。

这次没有改代码。议题从一个已经修掉的 bug 里剥出来：修的是判据，剥出来的是「一条外部事实一次决策」这条调度规则本身。

## 由何引起

`a7f69810` 那个会话里，父 Agent 在一个 Step 中派了四个 `delegate`。子智能体的报告成串回来，三份挤在 seq37/38/39 连着到达，父一次消费一条：

```text
seq=37/38/39  三份 subagent.report 连着到
seq=40  STEP  trigger=seq37  observed=37
seq=41..46      它的 glob 全部 attempt + outcome
seq=47  STEP  trigger=seq38  observed=46
seq=48..50      它的 read_file attempt + outcome
```

直接症状是投影缺口（Step47 的 `tool_calls` 可见、结果被剪掉，DeepSeek 400），根因是 `_is_waited_follow_up` 用 Journal 顺序判新旧、`apply_step` 用因果顺序判可见，两套规则在成串到达时分叉。**这个缺口已经修掉**，改判据即可，不需要合并。

剥出来的是另一件事：报告一条一条消费，每个 Step 之间 Journal 都在长，观测位置一路往后漂。上面那段里父先去 `glob`、再去 `read_file`，看着像在原地转。合并的设想是：装配时把当前所有待消费的外部事实一次交给模型，一个 Step 消费完。

## 关键事实：合并已经存在，只是不对称

讨论到一半才看清的一点，它改变了问题的形状。

`_requires_decision` 里对 Outcome 有这条：

```python
observed = issuing_observed[command_state.issued_by_event_id]
if any(
    _is_external_decision_fact(item.payload)
    and item.sequence > observed
    for item in events
):
    return False
```

只要有任何外部事实落在「发起该命令的 Step 的观测位置」之后，这条 Outcome 就不会成为触发事件；它的结果会经 `_include_waited_follow_up_events` 进入那条外部事实的帧，由那一次决策一并处理。这正是 [Runtime](../架构/运行/Runtime.md) 「用户输入与后到消息」第 2 条写的行为，只是代码里把它推广到了所有 `requests_decision` 的外部事实，不限于用户消息。

所以**续跑与新到外部事实早就是合并的**，今天不合并的只有外部事实彼此之间。议题因此不是「要不要引入合并」，而是「已有的合并规则要不要推广到外部事实之间」。这个问法下合并的正当性高不少：现在的规则更像是只覆盖了一半。

## `_blocked_by_in_flight`：不用改，已经兼容

本以为这是最大障碍，不是。判据对事实 F 的参与集合是「发起 Step 的观测位置 < F.sequence」的命令中有 attempt 且未终局者。F 越靠后集合越大，于是：

> F1 被阻塞 ⟹ 任何晚于 F1 的 F2 也被阻塞。

未阻塞的外部事实天然构成一个前缀。而现行循环碰到第一条被阻塞的事实就 `break`，`break` 的位置正是这个前缀的边界。合并只需把「取第一条」改成「取到 break 为止」，判据一个字不动。

这条不对称是刻意的（见 `_blocked_by_in_flight` 的 docstring：它问「这条事实该不该等」所以比 Journal 位置，`_is_waited_follow_up` 问「冻结帧必须显示什么」所以走因果序），合并不触碰这个不对称。

## 决策游标：合并会逼它说清自己是什么

现行校验是 `expected_cursor = len(consumed) + 1`，而 `consumed` 装的是 trigger 的 event_id。游标同时承担「第几次决策」和「消费了几条事实」两个含义——今天这两个数相等，纯粹因为一对一。

合并会把它们拆开：游标继续数**决策**，`consumed` 继续数**事实**。`basis_state_version` 与回放判定用的是前一个含义。这不算成本，算澄清。

## 用户消息夹在两条报告中间：真正的代价

早先把它记成「合并会改变语义」，太笼统。精确讲，合并丢掉的不是**信息**，是**中间的反馈回路**。

报告#1(seq37) → 用户说「停」(seq38) → 报告#2(seq39) 这个序列里，三条事实在决策发生时都已在 Journal 中。串行消费并没有让父在 seq39 到达之前先处理 seq38——那个「之前」已经过去了。串行真正保住的是：父可以为「停」签发命令、拿到结果，**带着这些结果**再去看报告#2。合并之后，回应「停」和处理报告#2 必须用同一份信息一次决定完。

但反方向也有一条，而且指向同一个场景：父在处理报告#1 时**不知道报告#2 和#3 已经到了**。循环在第一条待消费事实处就 `break`，后两条不进 `decision`。四次决策各自盲人摸象，这恰恰是前面那段「先 glob 再 read_file」的来源。

所以这不是「串行更安全 vs 合并更快」，是两种残缺的取舍：

| | 串行（现状） | 合并 |
|---|---|---|
| 决策次数 | 每条事实一次 | 未阻塞前缀一次 |
| 看得见队列里还有什么 | 看不见 | 看得见 |
| 中间命令的结果可依赖 | 可以 | 不可以 |
| 观测位置漂移 | 会跨过未消费 trigger | 不会 |

若要保住用户消息，规则会是「合并前缀在遇到 `UserMessageReceived` 时断开」。**这条规则是 Runtime 在编码「用户消息比子智能体报告重要」这个判断**，按[项目原则](../../AGENTS.md)第 4 条（Runtime 不做语义判断）它是可疑的：它确定、可回放，但它替模型定了优先级。真要做合并，这是最该被质疑的一处，不是实现细节。

## 阻塞成本：这是一次核心 schema 改动

「一个 Step 消费一个 trigger」扎在三处，不止事件载荷：

| 位置 | 现状 | 合并后 |
|---|---|---|
| `Step.trigger_event_id` | 必填单值 | 变成元组 |
| `step_claims.trigger_event_id` | `NOT NULL UNIQUE` | N 条 trigger 要原子认领 |
| `decision_consumptions.step_id` | `UNIQUE` | 同 step_id 要插 N 行，约束须去掉 |

也就是又一次 `EVENT_SCHEMA_VERSION` 升版，外加认领协议的并发语义重做（N 条 trigger 整体成功或整体失败）。这比 2026-09-18 那轮 `StepState` 重——那轮只动投影，可以靠 `STATE_PROJECTION_VERSION` 重建缓存了事；这轮动的是持久化与并发边界。

## 为什么当前骨架下可以先不做

同日引入的 `StepState` 把「一个回合」做成了归约结果的一等公民，投影层不再靠扫事件拼装。这解决的是**表达**问题，没有解决**调度**问题，但它让调度问题不再紧迫：缺口已经从构造上消失，合并剩下的收益只是效率与模型稳定性。

顺带留下两个边界问题，它们和合并是同一件事的两面，真要做分组或合并时会重新撞上：

1. 触发事件是 `DomainFactCommitted`（外部事实）而非 Outcome 时，这个 Step 算新回合的开始还是上一回合的延续？子智能体汇报回来就是这个形状。按因果链它是新根，按用户视角多半仍是同一回合。
2. `canonical_outcome_event_id` 只记第一条 Outcome。重试产生的后续 Outcome 不是 canonical；若某次 `next_trigger` 落在非 canonical 的那条上，「Outcome → 命令 → 发起 Step」的反查会落空。尚未确认 `canonical_outcome_event_ids` 是否已把它们排除在触发候选之外。

## 更便宜的探针

合并要解决的痛点是「模型原地打转」，而上面拆出来，打转的直接原因是**决策时看不见队列里还有什么**，不是「分了四次决」。这两件事被绑在一起讨论，但可以分开。

探针：把「还有 N 条已到达但未消费的外部事实」作为事实放进帧里。不改 schema、不改认领、不动消费语义，一次决策仍只消费一条。

- 若模型知道「后面还有两份报告」之后不再乱开工，合并的主要收益已经拿到，剩下的只是省几次 round trip——撑不起一次核心 schema 改动。
- 若照样打转，说明问题真在「必须一条一条决」，合并才值得做，而且届时手上有证据。

需要注意它本身也踩边界：告诉模型「队列里还有东西」是给事实，不是替它决定；但若进一步写成「建议你先别动手」，就越界了。

## 明确不必回到的方向

- 不要为了消除投影缺口而做合并。缺口已由判据修复，两件事不再耦合。
- 不要把 `_blocked_by_in_flight` 和 `_is_waited_follow_up` 统一。它们的不对称是刻意的，统一会让新事实死锁在一个它从未等待过的 Step 后面。
- 不要在没有证据的情况下先改 schema。三处约束一旦放开，回退成本高于这次讨论涉及的任何收益。

## 还没决定的问题

1. **「一条事实一次决策」是不变量还是默认值？**
   代码里它已经对续跑破例了。如果它只是默认值，推广到外部事实之间就不需要特别理由；如果它是不变量，那续跑那条破例才是需要解释的。
2. **合并前缀该不该在用户消息处断开？**
   这是本议题唯一会让 Runtime 编码优先级判断的地方。
3. **打转的真因是决策次数还是队列不可见？**
   探针可以在不动 schema 的前提下分辨，应先做这一步。
4. **N 条 trigger 的原子认领怎么定？**
   `step_claims` 现在是每 Session 一行、每 trigger 唯一。多 trigger 认领的失败与续租语义没有想过。
5. **`_blocked_by_in_flight` 的「已开始执行」代理要不要换掉？**
   判据现在用「有没有 attempt 事件」当代理，于是存在一个窗口：命令已提交、已 eligible、`DispatchAttemptStarted` 尚未落盘，此时新外部事实不被拦。而 [Runtime](../架构/运行/Runtime.md)「用户输入与后到消息」第 1 条排除的是「仍在等待授权」，不是「等待调度」。换成「PENDING 且 `dispatch_eligible_by_event_id` 为 None 才跳过」即可对齐原意。目前没有已知危害：同日那个预览竞态曾经走过这个窗口，但它同时也能经由 `deliver` 的 `decision_on_outcome=false` 触发，已从预览侧修掉。

## 附：Compact 尾部问题的后续决议

本议题之外的 `recent` 悬置已在 [Compact](../架构/上下文/Compact.md) 收口：不再保留没有稳定边界、大小也不受控的“最后一个完整回合”。近期尾部改为按 Event sequence / Step identity 选取预算内最大的完整单元后缀，不能拆开工具调用与结果；最后一个单元仍放不下时允许为空，优先保证 handoff 与 `(P,Q]` 新事实。本文此前的折中推测不再作为候选设计。

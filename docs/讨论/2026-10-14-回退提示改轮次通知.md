# 2026-10-14 回退提示改为轮次通知

状态：代码已落地，工作区未提交；`docs/架构/Sandbox/文件操作与回退.md` 已同步；自动化回归全绿（后端 869 passed / 7 skipped，前端 157 passed，`tsc --noEmit` 通过）；真实 UI 流程未复跑。

依据：用户在使用中报告「会话已回退 · 文件处理结果」卡片在点击关闭、切换会话再回来后重复显示；逐层核对后确认根因是严重度错配与生命周期缺失，不是关闭状态丢失。本次同时修订 2026-10-12 契约 B 中关于该提示持久呈现的部分。

## 一、问题

提示卡的数据来自 `ConversationView.workspace_file_result`，由 journal 里的救援事实投影而成，永不失效。原组件的 `dismissed` 是本地 `useState`，而会话组件按 `sessionId` 渲染，切会话即重挂载，关闭记忆丢失，卡片反复出现。

进一步核对发现真正让人不适的地方：这张卡是警告形状的组件，却被用在一切结果上。`unchanged`（文件本来就一致，什么都没动）也带着「机械回退不保证符合你的意图。请核对文件」的措辞呈现为整幅警示，纯会话回退没有异常却像出了大事。

## 二、确定的契约

**文件处理结果提示与控制操作提示同一套钩子。** 两者都是 journal 事实投影出的当前轮次提示：用户提交下一条消息后不再呈现，也不提供手动关闭按钮。到期规则收敛为一个共享函数，控制提示与文件结果提示共用；事实本身留在 journal 里，模型上下文与分支基线不受影响，过期的只是人看到的那一份。

**只有文件可能与回退后的会话对不上、且不是用户主动选择时才呈现。** `partially_restored`、`preserved`、`failed` 呈现，说明实际文件状态、涉及文件与失败原因；`unchanged`、`restored`、`kept` 不呈现——前者文件与对话一致，后者是用户在回退弹窗里亲手选定的取舍。`workspace_file_result` 仍是视图里的事实字段，是否打扰用户由前端按效果判定。

**前端不再持有提示的显示状态。** 去掉关闭按钮、本地 `dismissed` 与「运行中自动收起」：提交下一条消息后响应视图即换掉投影结果，运行中收起成为冗余。

## 三、验收

投影层：救援事实之后用户提交消息，文件结果投影为 `None`；控制提示的到期行为不变。组件层：三类对不上的效果呈现且不带关闭按钮，三类一致的效果与空结果不呈现。回归：后端全量、前端 vitest 与类型检查通过。

真实 UI 未复跑：从时间线重开、编辑消息重开两条路径下卡片的出现与消失仍待人工过一遍。

## 四、不做

不做通用通知框架，也不把两种提示合并成带标签联合的单一字段：两者形状不同（结构化结果与一句话），统一的是规则与生命周期，不是长相。不把 `workspace_file_result` 挪出会话视图，不为此新增前端内存槽。

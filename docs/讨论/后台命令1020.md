# 后台命令（2026-10-20）

> 状态：**已实现。** 落地时把结论并入 [执行环境](../架构/能力/执行环境.md)、[打断](../架构/运行/打断.md)、[多活跃会话](../架构/运行/多活跃会话.md) 等现行文档，本篇留作决定的来由。

## 方向

长命令不占着 Agent。命令在前台只等一小段时间：跑完了照常返回结果；没跑完就留在后台继续跑，工具先返回，Agent 这一步随之结束。命令结束时，结果作为一条新事实回到 Agent，叫醒它接着做。

这决定一个长期 Agent 好不好用：它在跑构建、测试、长验证的几分钟里，人找它、同事私信它、群里叫它，都应该能马上得到回应，而不是等命令跑完才一并看到。体验上的参照是 Grok Bot：Bot 承接的工作还在继续，但它已经能接待新的请求。

## 起因

群聊里出过一串修不干净的问题（firetoweak/RED-PANDA#111 的三轮返工）：测试员回执后跑长验证，期间被另一次讨论叫到；命令跑完后，回应请求和命令结果进了同一步，系统只能猜报告在回应谁。那串问题的归属部分已经由显式参数解决（见 [CodingBot 总览 · 群聊](../架构/CodingBot/总览.md#群聊)），不再依赖后台命令；后台命令解决的是响应性和前后台交接，**不承担替模型判断行动归属的职责**。

参照：[Grok Bot 0.18 逆向重建](https://github.com/b-nnett/grok-bot-0.18-reconstructed) 的 shell 前台默认只等 30 秒，到点转后台、不杀进程，结束时在 Agent 自己的会话里排一个新回合唤醒它；[nanobot](https://github.com/HKUDS/nanobot) 的后台子任务按登记时记下的来源投递结果，但长命令只能轮询，没有完成通知。

## 结论一：「已接管」向前台保证什么

前台能放心结束，是因为工作已经被可靠接管，系统承担了后续通知责任；模型不需要靠占着回合、调用等待工具或反复查看来保证自己不忘掉任务。「已接管」保证三件事：

1. **可寻址**：这条后台命令有稳定身份，之后模型和人都能用它查看输出、停止它。
2. **有人负责投递**：它结束时，结果一定作为一条事实回到这个 Agent；即使期间应用重启，也如实报告结果未知、不会重跑，不会悄无声息。
3. **登记了来源**：记下由哪条命令发起，只用于寻址、补投与展示，不用于语义归属。完成后汇报给谁，由模型显式发出（`message_user`、`send_message`、`send_group_message`）。这不解决[长期 Agent 漏发给人消息](长期Agent不用message_user1020.md)的已知交互问题；本能力只保证事实回到 Agent。

不在保证范围内：命令一定成功、一定结束、会自动重试。

## 结论二：应用重启的缝隙

外部进程启动与 Journal 写入不能成为一个事务。缝隙靠两条闭合，不需要两阶段提交：

- **身份先于进程。** 后台命令的身份由发起它的 Command 确定性派生，写下 Attempt 时就已确定；崩在哪一步，恢复时都用同一个身份去问它怎样了。
- **谁活着谁说了算。** 进程由 Host 持有，Host 退出时整棵进程树必然被回收（现有的持续进程保证）。Host 活着，它就是「有没有启动、跑没跑完」的事实源；Host 死了，进程必然已随之结束。不存在「可能还活着但没人知道」的状态。

逐个窗口：

| 崩在哪 | 谁崩 | 恢复 |
|---|---|---|
| Attempt 之后、结果提交之前 | 只有 Worker | 按身份问 Host：还在跑，补交「仍在运行」；已结束，补交真实结果；没有，补交未启动。与私信、一次性提醒的窄恢复同形 |
| 同上 | Host | 结果未知，沿用现行前台命令的规则：可能已部分执行，暂停会话，等人核对 |
| 已转入后台、尚未结束 | Host | 补投完成事实：结果未知 |
| 已结束、尚未送进会话 | 任一 | 见下 |

结果未知的措辞只说能确定的：应用重启时它没有留下结束记录，它不会继续运行，也不会重跑。它可能在崩溃前刚好自然结束、只是结果没来得及落盘，所以不说「被终止」。

**结果先落盘，再投递。** 会话的事实只能由它自己的 Worker 写入，Host 不能直接写。命令结束时，Host 先把退出结果原子地写进这条命令自己的输出目录，再以命令身份作为投递身份，请目标会话接纳一条要求决策的完成事实；Journal 按投递身份只接纳一次，确认接纳后才算投递完成。

**待补投的名单从 Journal 推出**：有「已转入后台」、没有完成事实的，就是待补投的；不另建登记表。Host 启动时逐条处理：有退出记录就投递真实结果，没有就投递结果未知。恢复只补报，从不重启命令，因此不会重复执行。

不需要持久化的进程注册表，也不需要重启后重新盯住进程：命令活不过 Host。Grok 需要重新盯住，是因为它的命令跑在能活过宿主的另一台机器上，这一点不照抄。代价是 Host 重启会中断所有后台命令，是否重跑由模型根据通知决定，与现行「持续进程不随 Host 重启恢复」一致。

## 结论三：进程从一开始归 Host

所有命令从启动起就由 Host 持有。Worker 请 Host 启动进程后在前台等待：期间结束就返回结果；没结束就返回「仍在运行」，进程留在 Host 继续跑。「转入后台」不是一次移交，只是 Worker 不再等了。

不采用「先归 Worker、超时再移交给 Host」：进程树所有权跨进程交接（复制 Job 句柄、转交 subreaper 控制管道）本身会开出一个新的崩溃窗口。

由此：

- **只剩一条执行路径。** 现在前台命令由 Worker 持有、持续进程由 Host 持有，是两套实现；之后只有 Host 持有这一条，持续进程就是前台等待为 0 的命令。按「不兼容旧设计」删除 Worker 持有进程的路径与单独的启动持续进程工具。
- **输出统一走文件。** Host 把输出写进命令自己的目录，前台返回时从文件读取并按现行规则截断，后台阶段读取的也是同一份。
- **Worker 空闲规则自然成立。** 前台等待期间有在途命令，Worker 忙；转入后台后命令已终局，Worker 可以空闲、退出，命令照常在 Host 跑。
- **打断。** 前台阶段打断由 Host 终止进程，Command 得到中断终局，「打断必须真的终止进程」照旧。转入后台后 Command 已终局，打断不停它，与现行持续进程一致；人和模型可以单独停止它。
- **授权不变。** 一条命令授权一次，转入后台不新增授权。

## 结论四：模型看见什么

只表达可观察行为与下一步，不出现进程、Host、超时框架等内部概念。

**工具。** 执行命令的工具只有一个时间参数：前台最多等多久，0 表示直接放到后台；默认值与上限由代码定。另有查看输出、停止、列出后台命令三个以「命令」为中心的工具；删除单独启动持续进程的工具，原有进程工具按命令改名，不保留旧名。不提供延长与阻塞等待。

**转入后台时的返回。** 成功，带命令身份、已运行时间、目前输出的末尾，说明它仍在运行、结束时会收到通知、不需要等待或反复查看，需要时可以查看输出或停止它。

**完成通知。** 一条要求决策的事实：命令原文；结果为完成（附退出码）、失败、被停止或结果未知；耗时、输出末尾与完整输出的读取方式；并说明这是之前转入后台的命令结束了，不是人的新消息。它在源头计数等用途上与一次性提醒到点同等处理，不新增按来源回溯的要求。

**每条转入后台的命令恰好一条完成通知**，包括被模型或人停止的。停止与自然结束走同一条路，待补投名单也只需一条规则。

**没有总时长上限。** 开发服务器、监视器本该一直跑；挂住的命令不会自己结束，也就没有通知可投——它不是悄无声息，仍在后台列表里，人在 Web 上看得到、停得掉。担心挂住时，模型用已有的一次性提醒回来查看输出，再决定是否停止；系统不设默认运行额度。现行「命令期限由模型在参数范围内设置、不建通用超时框架」在后台阶段的含义即此。

**提示。** 命令执行说明加一段可观察的指引：预计耗时较长的命令（构建、测试、安装、长脚本）可以直接放到后台，然后继续做别的或结束这一步，结束时会收到通知；不要为了等结果反复查看输出；后台命令可能挂住不结束，需要确认进展时可以安排一次提醒回来查看，再决定是否停止。

## 与现行结论的关系

落地时需要改写：

- [执行环境](../架构/能力/执行环境.md)：「前台命令有界等待，结束、超时或取消时回收进程树」改为前台等待到点后转入后台；前台命令的进程树改为归 Host；持续进程并入后台命令。「不把后台化当作持续进程入口」说的是 Shell 自己的 `&`，仍然成立：后台由系统提供，不靠 Shell 语法。
- [打断](../架构/运行/打断.md)：范围写明只终止仍在前台等待的命令。
- [多活跃会话](../架构/运行/多活跃会话.md)：Host 重启时对未知命令的暂停规则只覆盖前台阶段；已转入后台的命令按结论二补投结果未知，不暂停。
- [自动化](../架构/运行/自动化.md)「一次性定时与 SubAgent 不合并成『后台任务』机制」仍然成立：后台命令是第三个事实源，三者只共用 Runtime 已有的外部事实投递与幂等，不抽公共框架。
- [交互式资源](../架构/未开始/交互式资源.md)「命令跑完即散，没有任何东西活过一个 Command」已经过时（持续进程早已存在），一并更正。
- SubAgent 没有命令执行与持续进程工具，不受影响。

## 不做

- 不让 Command 在后台期间保持未终局：它会挡住后到的事实、钉住 Worker、重启后变成未知。
- 不在当前一步中途注入完成结果；完成永远是一条新事实。
- 不提供阻塞等待后台命令的工具，不轮询；需要结果才能继续时，结束这一步等通知。
- 不设默认运行额度、不提供延长；不在到期前提醒。实测若发现挂住导致的停摆常见，再带着证据讨论。
- 不做「长时间没有输出就通知」：没有输出不等于挂住，判断归模型；也会打破「恰好一条完成通知」。
- 不按输出内容提前通知（例如服务「已就绪」），那是语义判断。
- 不合并同时到达的多个完成通知。
- 不自动重跑被应用重启中断的命令。
- 不持久化进程注册表，不在重启后重新盯住进程。

## 实现时的选择

- **macOS。** Host 持有进程目前只在 Windows 与 Linux 实现。明确 macOS 不支持后台，命令只在前台等待到结束，不为没有用户的平台预建后台所有权。
- **Web 呈现。** 人需要看到每个 Agent 有哪些后台命令、跑了多久，并能停止。会话中提供后台命令列表，展示状态、已运行时间与单独停止入口。
- **完成通知带多少输出。** 只带末尾一段，完整输出按需读取，与工具结果外置规则对齐；长度由代码定。

## 落地后的边界

现行约束已经并入执行环境、打断和多活跃会话文档。Runtime 的 Step、Command 与单一终局不变；新增能力属于命令领域。原持续进程入口整体移除，没有保留双轨。产品内部工具的有界执行独立保留，不作为工作区命令的回退路径。

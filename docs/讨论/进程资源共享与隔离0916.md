# 进程资源：共享什么，隔离什么（2026-09-16）

> 决策已落地：模型客户端收在 Host，Worker 只持有 LLM Port。当前准绳以[多活跃会话](../架构/运行/多活跃会话.md) 和 [Ferro Gateway 接入](../架构/能力/Ferro%20Gateway接入.md) 为准。下文保留测量与推敲过程，其中「Worker 拥有模型客户端」「尚未决定」等表述已经过时。

这次没有改代码。问题从 Web「编辑用户消息并重新执行」的体感慢开始，落到一条更根本的选择：**一 Session 一进程之后，哪些资源必须按 Session 复制，哪些其实是产品级的。**

## 由何引起

Web 编辑不原地改消息。`POST /api/sessions/{id}/forks` 以目标 `UserMessageReceived` 之前的完整事件前缀物化新 Session，再写入编辑后的文本并执行。源 Session 不变。

最初的直觉是：fork 要带走全部事实，还要恢复渐进加载的动态工具和 MCP 连接，所以慢。

对照实现后，这条直觉只对了一半。

- **必须带走的是事实，不是连接。** 前缀里的 `load_toolset` Outcome 已留下完整工具契约（名称、描述、parameters、`provider_data`）。新 Worker 的 `ToolSurface.rehydrate()` 走 `restore()`，按快照重新绑 handler，不调用 `list_tools`，也不拉起 stdio。MCP 真正握手被推到之后某次 `call_tool`。管理域同样只投影激活集合。
- **fork 的 HTTP 仍是同步整条链。** 物化前缀、重算 Step basis、复制 `artifacts` / `.attachments`、`select` 新 Session、写入编辑文本、再投影 conversation，都挡在返回前。
- **新建空 Session 已经明显慢。** 空 Journal 没有已加载 Toolset，也没有可复制的附件。若它和 fork 体感接近，主因就不是前缀回放或 MCP 重连。

两边共用的门是 `select()`。对还没有 Worker 的 Session，Host 会 `_start()`：Windows `spawn` 一个新 Python 进程，子进程再装配完整 Assistant。HTTP 等到 `resume_session` 结束、`ready` 置位。

## 实测：冷启动贵在哪里

2026-09-16 在本机按 Worker 启动顺序量过一次（已在解释器里的模块不再重复计）：

| 步骤 | 耗时 |
|---|---|
| `import helperme.assistant.host.worker`（整包装配依赖） | 3.4s |
| `import litellm` | **18.7s** |
| `LiteLLMAdapter()` / `Router()` | 0.05s |
| `build_mcp()` | 2ms |

Host 启动时已经付过一次 LiteLLM。`bootstrap_assistant()` 会为管理面建 `management_llm`。但 Worker 是 `spawn` 出来的新解释器，地址空间是空的，用不了 Host 已经导入的模块。

每个新 Session 因此再走一遍：

```text
worker_config()
  → LiteLLMAdapter.__init__
  → import_module("litellm")
  → litellm.Router(...)
```

所以点击新建 / fork 时感觉「超级慢」，主因是：**Windows 上拉起一个完整 Worker，并在子进程里重新冷导入 LiteLLM。** 内存上每个 Worker 也是一份完整解释器加 LiteLLM，不只是耗时。

前缀物化、附件复制、工具 `restore` 都在后面。对话很长、附件很多时它们会叠加上去，但解释不了空 Session 为什么也慢。

## 当前契约把什么放进了 Worker

[多活跃会话](../架构/运行/多活跃会话.md) 的选择是：Session 既是执行隔离单元，也是持久化隔离单元。每个活跃 Session 在独立操作系统进程里拥有一套完整实例：

```text
Runtime
事件循环
模型客户端
工具与 MCP 客户端
Session 投影缓存
只属于它的 Journal
```

一个 Worker 不承载第二条 Session。进程边界要挡住的是：一个 Session 里的同步阻塞、事件循环停顿和未预期异常，不暂停其他 Session。

这次讨论要拆开的，正是这张清单里哪些真的需要「每 Session 一份」，哪些只是跟着进程模型被复制了。

## 判断框架：隔离的是故障域，不是导入缓存

「系统启动时导一次 LiteLLM，Worker 就不用再导」说的是两件不同的事：

1. **把等待挪到启动。** 点击时不再卡十几秒。
2. **全局只留一份。** 内存里不要每个 Worker 再占一份 LiteLLM。

第 1 件是体验分层。第 2 件是改共享边界。Windows `spawn` 不能把 Host 进程里已经导入的模块送给子进程；「开机导一次就全体免费」这条路是断的。

更有用的问法不是「能不能少导入」，而是：

> 这个资源的故障、阻塞和生命周期，是否必须跟一条 Session 绑定？

| 资源 | 跟 Session 绑在一起的理由 | 现在跟着进程被复制的代价 |
|---|---|---|
| Journal / Runtime / Scheduler | 事实与推进必须按 Session 线性、可重放 | 必要。fork 物化新 identity 也是为此 |
| 工具执行、shell、Sandbox | 同步阻塞、权限、工作区副作用按 Session 隔离 | 必要。这是进程模型要保护的东西 |
| MCP 客户端 | 连接是进程内缓存；工具 Schema 已可从 Journal restore | 连接按需建立说得通；启动时不必重连 |
| 已加载 Toolset 的 Schema | 是已提交事实的投影，不是活动连接 | 恢复快照即可，不要为了恢复去握手 |
| LiteLLM / Router | 主要是出站 HTTP。卡住的是 Provider，较少是本地事件循环 | 每个 Worker 冷导入约 20s，并常驻一份大模块 |
| 整包装配（`build_assistant_assembly`） | Worker 里要有决策与工具面 | 子进程再 import 一遍约 3s |

进程隔离换来的，是执行故障不相等。它换不来「子进程免费继承父进程的 import」。把模型客户端写成「Worker 拥有自己的一份」，在 LiteLLM 这种重依赖上，付的是启动税和内存税；防住的，主要是「模型流式或 Router 卡住」这一层，不是 shell / MCP / 工具执行那一层。

## 两条还没选的路

### 预热池：不改共享边界，只改付费时刻

Host 启动后预热 1 个空白 Worker：imports 和 `LiteLLMAdapter` 做完，还没绑 Session。新建 / `select` 领走它，后台再补一个。fork、SubAgent 同理。

- 兼容现行契约：仍是一 Session 一 Worker，Journal、ToolSurface、MCP 都不改。
- 点击不再付冷导入。补池仍会再导一次，只是挪到后台。
- 每个活着的 Worker 仍然各持一份 LiteLLM。省的是等待，不是副本。
- 要另定池子大小：Web 常驻 1 个够不够，SubAgent / compact reader 算不算预热对象。

这是「先把按钮变快」的最小动作。

### 上收模型客户端：真的只导一份

模型客户端离开 Session Worker，放到 Host 或单独的 LLM 进程。Worker 只通过 IPC 发 `chat`。`import litellm` 全局一次。

- 新建 / fork 的子进程会瘦一圈；连那 3 秒的 `import worker` 也有再削的空间。
- 要改[多活跃会话](../架构/运行/多活跃会话.md) 写明的「Worker 拥有自己的模型客户端」。
- 隔离变弱的是模型调用这一层：Host 或 LLM 进程的事件循环、背压、崩溃，会同时影响多条 Session 的决策。工具、shell、MCP 仍可留在 Session 进程里。
- LiteLLM 出站 HTTP 是否值得占用「每 Session 一进程」的隔离，是这步的核心判断，不是实现细节。

这是换进程边界，不是预热的延伸。未想清「模型卡住该不该拖死别的 Session」之前，不宜当作默认优化。

## 明确不必回到的方向

- 不要为了 fork 快而做「只继承消息」的旁路。能力加载、Compact、附件引用必须与前缀事实一致，否则编辑重跑会 silently 丢工具。见 [Web](../架构/入口/Web.md)。
- 不要在 fork / resume 时为了「确认 Server 还活着」而强制重连所有已加载 MCP。现行 `restore()` 已经把连接推迟到第一次调用。
- 不要指望 Host 先 `import litellm` 就能让 `spawn` 子进程免费。

## 还没决定的问题

1. **模型客户端是 Session 私有资源，还是产品级出站端口？**  
   若是前者，预热池就够。若是后者，才值得上收。
2. **进程模型要保护的最小集合是什么？**  
   目前清单把 Runtime、LLM、MCP、投影缓存绑在一起。实测说明 LLM 导入是最贵的副本；它是不是最小集合里的成员，还没有正面回答。
3. **fork / 新建的 HTTP 是否必须等 Worker `ready`？**  
   物化 Journal 必须同步，否则新 Session 还不存在。`select` 与装配是否挡在同一响应里，是体验问题，也可以和预热池分开想。
4. **预热几个、预热到什么程度？**  
   只预热「已 import + 已建 Router」的空白进程，还是预热到 `build_assistant_assembly` 完成。池空时点击仍会掉回今天的慢路径。

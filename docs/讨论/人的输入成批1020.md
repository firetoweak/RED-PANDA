# 人的待处理输入成批进入下一次决策（2026-10-20）

> 状态：**已落地。** 契约已并入 [Runtime](../架构/运行/Runtime.md)「用户输入与后到消息」，本篇留作决定的来由。它重新选择了 [外部事实要不要合并](外部事实合并0918.md) 里「当前选择不做」的一部分。

## 为什么重新选择

0918 那轮的动机是效率：子任务报告成串到达，一条一条决、模型原地打转。当时结论是不值得为此改核心 schema。

这次的动机不同，是正确性：**系统已经接纳了人的更正，却仍然不给模型看，让旧指令继续产生行动。** 例子：

```
A 的发版命令执行中 → 群里的回应请求 B 到达 → 人说「改成 2.1」 → 命令结束
```

现行规则按接纳顺序消费外部事实：下一次决策由 B 触发，带着 A 的命令结果，人的更正还在排队。模型可能照旧指令继续提交、打标签。人先说「发 2.0」又说「改成 2.1」，一次只消费一条时，下一帧也可能只看到前一句。

同一串讨论还定下了两条前提，这次的范围由它们决定（见 [CodingBot 总览 · 群聊](../架构/CodingBot/总览.md#群聊)、[结尾文字的去向](../架构/CodingBot/总览.md#结尾文字的去向)）：

- **行动属于哪件事，由模型用显式参数表达**（群发言的 `reply_to`、私信收件人、`message_user`），系统不从「这一帧由谁触发」反推。因此不需要「一帧一个来源」来保证归属，也不按目的地给不同来源设屏障。
- 剩下要保证的只是：**人的输入及时、完整地进入下一次决策**。

## 范围

只解决人的待处理输入成批进入下一次决策。「人的输入」就是 Runtime 已有的 `UserMessageReceived`，按事件类型判定，不沿 origin 追溯「这项工作最初是不是人发起的」，否则子任务报告、例行任务也会被归进来。其他来源之间仍按接纳顺序逐条消费，不推广合并。

## 契约

**选取。** 冻结下一次决策时，若有尚未消费的人的输入，这一批就是冻结时已经接纳、尚未消费的全部人的输入，按接纳顺序；否则沿用现行规则，取最早的一条外部事实。

**何时进入。** 先确定整批，再判断这一批能否进入决策：任何一条仍被在途操作挡住（「已经开始的旧操作先结束」），整批就一起等。不能因为后到的更正仍被挡住，就先把前面的旧指令单独交出去。

**看得见什么。** 暂缓的只是尚未交给模型处理的决策输入：

- 更早到达、被这一批越过的别的决策输入（例如 B），这一帧不展示，留给之后的决策；
- 已经处理过的历史照常可见；不要求决策的事实（普通群发言等）照常可见；
- 旧命令的结果并进这一帧。可见集合按因果关系纳入：这一帧可见的 Step 发出的命令，它们的结果都在帧里，不按「触发事件之后到达」截取——触发可以被提前，早于这一批到达的结果不能因此漏掉。

这条暂缓只防止系统把同一输入再次交付为待处理事项；模型本来就会反复看到历史，不能保证它不重复行动。行动归属仍靠显式参数。

**每条保持原样。** 一批里每条消息保留自己的身份、原文与顺序，不拼成一条新消息。

**消费的含义。** 消费只表示这些输入已经被一次成功提交的决策共同处理：不表示模型逐条答复了，更不表示工作已经完成。

**提交。** 冻结了哪批，提交时就原子消费哪批：Step 与这一批每条输入的消费记录在同一个事务里写入。Step 显式记录它消费的集合——选取是当时的政策，选取结果是已经发生的事实；回放不重新运行选取规则。

**失败。** 模型调用失败或提交失败，什么都不消费，认领释放。下次冻结重新选取，这一批可能已经变大。批次属于一次尝试，不是固定下来的分组。

**取消。** 取消当前冻结的决策批次：这一批不再自动触发决策；历史保留，并明确记录它们被取消，不记成已由模型处理。取消记录同样显式保存集合。冻结之后到达的输入不在取消范围内。取消与提交竞争同一批：提交先成功，按已提交 Step 关闭续步；取消先成功，旧决策不能再提交。取消的是这一个决策批次，不是系统理解出来的整项任务；之后的独立输入仍可能谈到同一件工作，这不是取消失效。

**调用开始后到达的输入** 留给下一次决策。

**输出标识。** 实时输出用这一批的第一条输入作为标识。它只是展示标识，不表示这一轮的行动都属于它。

## 优先的性质与代价

人的输入优先是明确的产品政策：人设定目标、给出授权，系统按确定的事件类型排序，不读正文，因此不违背「Runtime 不做语义判断」。它与授权规则同样依据来源类型执行，但两者不是一回事：授权决定操作能不能执行，优先决定先给模型看什么。

代价：人持续发消息时，其他来源的决策输入一直排在后面；人停下来，它们按接纳顺序得到处理。

## 由契约推出的 schema

- 认领本来以 Session 为独占单位，一次认领覆盖一个固定的输入集合，不拆成 N 个独立认领。认领记下冻结的集合。
- 消费记录允许多条输入指向同一个结果事件与 Step（放开 `decision_consumptions` 对结果与 Step 的唯一约束）。
- Step 与取消记录携带消费集合。字段形状由实现定，不必沿用单值 `trigger_event_id` 的形状。
- `EVENT_SCHEMA_VERSION` 升版。按「不兼容旧设计」，不迁移旧 Journal：版本不符时照现行行为明确报错。

## 不做

- 不按目的地或来源给不同对话方设合并屏障。
- 不把其他来源（子任务报告、私信、群回应请求、例行任务）推广成批。0918 的「更便宜的探针」仍是那条线的下一步。
- 不把一批消息拼成一条，不从正文判断哪条是更正。
- 不在冻结后把新到的人的输入插进正在进行的模型调用。
- 不为取消的输入自动重新交付。

## 对 0918 未决问题的回答

1. **「一条事实一次决策」是不变量还是默认值？** 默认值。对续跑已经破例，这次再对人的输入破例；其他来源之间仍是默认的逐条消费。
2. **合并前缀该不该在用户消息处断开？** 改为反过来：人的输入优先，自成一批；其他来源不合并。依据是来源类型，不是正文。
3. **N 条 trigger 的原子认领怎么定？** 不做 N 条认领：一次以 Session 为单位的认领覆盖一个固定集合，提交时整批消费，失败时整批不消费。

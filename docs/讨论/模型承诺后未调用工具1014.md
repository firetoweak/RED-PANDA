# 模型承诺后未调用工具

2026-10-14 观察记录。保留现象与待研究判断，不作为架构准绳或已确定的修复方案。

## 现象与证据

用户要求连续安装 `create-verification-skill` 和 `maintain-verification-skill`。第一个安装成功后，助手回复“第一个安装成功。现在安装第二个 `maintain-verification-skill`，使用同样的正确路径。”，随后停止，没有提交第二个安装提案。

核对实际会话 Journal 与决策回放材料（时间为北京时间）：

- 10:09:41，第一个安装的成功事实已提交，并请求下一次决策。
- 10:09:45，模型已经执行下一轮决策；请求中包含安装成功结果，`propose_skill_install` 仍在可用工具列表中。
- 这轮记录的模型响应只有上述文字，工具调用列表为 `calls: []`。因此只产生正文投递，随后等待新的外部事实。

这次记录不支持“安装后没有唤醒”的解释；可以确认的是，模型已获得继续执行的机会，却只表达了行动意图。当前系统提示词已经要求“说要做某个动作，就在同一响应里发出对应的工具调用”，该约束在本次响应中未被遵守。

本地证据定位：Session `session-846242aae3f949b5a79591745db62676`；Journal 目录 `b763ecfa8e00807af1da0b86148fb8f2a6fc04d0907faa242aef31f113e7f8d0`，序号 58 为安装成功事实，序号 60 为后续决策；决策材料 `art_48d38150b31e4414b7a6046e1f1d60a7`。模型为 `stepfun/step-5-preview`。证据保存在本机 RED PANDA 数据目录，未随本文归档。

排查时相关控制面、调度与 Skill 审批测试共 45 项通过；另用内存会话与模拟模型验证了连续两次提案、批准、执行及自动续步。该验证说明这条确定性链路可以连续工作，不代表真实模型一定会持续执行，也不证明所有调度场景都没有缺陷。

## 待研究判断

用户提出：这可能暴露了系统完全依赖模型能力发挥的一处缺陷。运行链路能保证结果回到模型，却不能保证模型将“继续做”的判断落实为工具调用；一次只有正文的响应，可能让尚未完成的任务静默停下。任务推进可靠性因此直接受模型行为影响。

这是一例真实样本，尚不能确定发生频率，也不能归因于某个模型、上下文表达或工具描述。后续研究应区分“未唤醒”“工具不可见”和“模型未调用”，再评估是否需要显式的完成核验。不能据此让 Runtime 根据回复文字猜测任务未完成、替模型选择动作，或无条件重复唤醒。本次只记录，不修改运行行为。

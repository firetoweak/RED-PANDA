# 版本操作分层

> VFS 管理操作事实，Git 管理开发成果之间的关系。操作记录高频、可恢复；Git 版本对象只在明确的业务节点创建。

2026-10-09 的分层依据与一项合并决策记录。本篇是讨论记录，不是准绳；已落地的准绳是[文件操作与回退](../架构/Sandbox/文件操作与回退.md)与[子任务文件交换](../架构/Sandbox/子任务文件交换.md)，落地后的结论并进那两份，本篇不重复它们。

## 阅读时点

## 问题：把 Git 当操作日志的成本形状

所有 Session 的版本操作在同一个 workspace 上完全串行，而每一次操作都要把整棵工作树重新哈希一遍。子越多，这条串行队列上的工作量线性叠加，于是越加越慢。

放大器不在并发，在复制：子的工作树是父树的全量副本，每个子每步的快照成本都相当于一次父树规模的全量扫描。并行没有把工作量摊薄，而是把同一份规模重复了 N 次。

成本由两件事决定：版本操作的频率（每个 Step 一次）和单次的代价（整树）。降频不成立——回退要能指回每一次助手操作；剩下的路只有把单次代价从「整树」改成「变更集」，这正是分层做的事。

## main 的方案修的是什么，没修什么

main 的 `52e7126` 把工作区版本操作收到 Host 端口统一排队执行：串行队列、锁外发布、取消安全收尾。它修的是**队列在并发与取消下的正确性**，没有动成本模型——record 仍是整树，子仍是全量副本。队排得更稳了，越加越慢还在。

它的取消安全语义在本分支已有对应实现（ReviewWorktrees 的执行收尾是同一套模式），Host 端口排队则与 VFS 操作账本（sqlite owner 加进程内串行锁）职责重叠。**不跟这笔提交没有实质损失**，这是本次合并中止后记录的决策。

## 分层：两条轨道各管什么

- **VFS 的操作记录对应 Command / Step**，可频繁创建和恢复。归因、候选、发布、恢复证据都在这一层。
- **Git 的版本对象对应需要比较、合并的成果**，只在明确的业务节点创建：委派冻结基准、子交回、父验收合入。
- **SubAgent 的工作区隔离由文件视图实现**，Git 不必负责物理复制。
- **Git 合并的结果重新进入 VFS**，成为一次可追踪、可恢复的文件操作。

无需重新实现 Git 的三方合并算法，也无需再让 Git 承担它并不擅长的高频操作日志职责。

## 当时现状：准绳落地到哪，成本还剩哪

已落地：父子各自的每步操作都走 VFS，按操作身份（Session 乘 Command）落账、按身份授权恢复；子的每步不产生 Git 提交。Git 只在三个业务节点出现——建子时从冻结基准物化子工作树、交回时 record、验收时 compare/merge——三方合并用 Git 自己的算法。

没走完的按成本从大到小：

1. **建子仍是全量物化**：从基准 checkout 整棵落地。N 个子就是 N 份父树规模的拷贝，落在产品数据目录下等父验收。
2. **交回仍是整树走查**：record 逐层收集全部路径再 write-tree，哈希量与仓库规模成正比，N 个子排队时线性叠加。
3. **合入结果没有以操作身份落账**：今天 merge 直接写进任务根。准绳承诺「合入是一次普通写入……正常留下新的一版」，缺口在它不进操作账本，因此不能像普通助手操作那样被指回、恢复和投影。

## 当时提出的迁移顺序

1. **交回改用 VFS 变更集驱动**。交回仍然是 Git 节点——compare/merge 需要它——但 record 不再整树扫描，只处理账本里记下的变更路径。单次代价从「仓库规模」变成「本次 diff 规模」，串行队列上的总量随之塌下来。
2. **建子改文件视图**。子不再持有物理工作树，改为父视图上的文件视图；交回时把变更文件按需物化成 Git 提交——每次委派一份 diff 的物化，不是每步一份整树。验收坐标不变。
3. **合入落账**。把「普通写入」升级为带操作身份的 VFS 操作，恢复与投影自动覆盖它，不新开入口。

三步都落在既有 process 测试的验收网内，不需要新机制。

## 前提与风险

三步依赖同一条不变量：**文件工具和命令使用同一文件视图**，账本因此知道全部助手写入。任何绕过视图的写入本来就不属于可回退范围，但必须显式排除，或在交回时回退到全树核对，不能静默漏掉。第 2 步还留着一个老问题：长期活着的父仍会攒下未验收的物化树，回收取舍见《可写子会话》已接受的决定。

## 不做

- 引入 Host 端口版本队列：与 VFS 操作账本职责重叠，且不降低单次成本。
- 把 Git 请回会话初始化或 Step 收口。
- 用工作树隔离换执行权限，或做「受限的 execute_command」。
- 承诺零拷贝隔离的落地时间：当前 checkout 成本已被接受，按上面的顺序，疼了再做。
